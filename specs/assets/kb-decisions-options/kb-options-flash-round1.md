# Knowledge base pane: design options

Generated by Gemini 3.8 Flash High via agy; unreviewed first pass.

## Option 1: Classic Minimal SERP (Linear Flow)

A pure single-column layout honoring 1998 Google minimalism where the dead-centre search box docks at the top upon query entry. It presents an emphasized top result card with indented passage snippets followed by compact sub-results, with model synthesis injected directly above the hits.

**Tradeoffs:** Pros: Maximum horizontal line-length (100 chars) prevents awkward wrapping of code paths and spec snippets; zero cognitive clutter; feels fast and predictable like early Google. Cons: Requires round-tripping into the full-screen reader to preview documents; vertical scrolling needed for deeper hit sets. At 80x24: Search box narrows from 54 to 42 cols; sub-line stats condense to 'specs 31 · ctx 212 · mem 64'; results list caps at 3 items with snippets wrapped to 2 lines.

## Option 2: The Split Dossier (Two-Column Inspector)

A synchronized two-column workbench pairing a dense ranked results list on the left with an instant zero-navigation live preview inspector on the right. 'Summarize for me' replaces the inspector with a structured synthesis dossier without hiding the search hit list.

**Tradeoffs:** Pros: Highest operator scanning velocity—previews excerpts, file metadata, trust badges, and git provenance instantly with arrow keys without navigating away; keeps context alive during summarization. Cons: 58-column inspector width requires soft-wrapping for wide code lines; higher visual density than early Google minimalism. At 80x24: Two-column split collapses into a single pane with left list full width; pressing space or right-arrow slides the inspector in as an overlay.

## Option 3: Command Card Stream (Modal Synthesis Drawer)

A modern developer card stream with an elevated Golden Hit card carrying inline single-key action chips. Summarization expands an inline synthesis drawer directly beneath the search bar, keeping the card stream intact below.

**Tradeoffs:** Pros: Clear cognitive chunking with self-contained cards; explicit inline action chips eliminate keystroke guessing; collapsible synthesis drawer preserves query context and scroll position. Cons: Lowest hit density per viewport (only 2-3 cards visible without scrolling); visually busier than pure text lines. At 80x24: Cards compress by hiding secondary action chips behind an '[enter: actions]' prompt, and synthesis drawer height caps at 4 lines.

## Recommendation

Recommend Option 1: Classic Minimal SERP (Linear Flow). It perfectly aligns with the operator's core brief ('something like early Google: search bar dead centre and super simple') and respects Delphi's strict aesthetic rule that body structure must come from indentation and weight rather than boxes. It offers the cleanest full-width reading experience for code and specs. However, Option 1 should steal two key ideas from the others: (1) Option 3's explicit action chips on the top result for instant keystroke discoverability, and (2) Option 2's granular trust and security isolation diagnostic block when delegating media/PDFs to the system browser.

## Open questions

- Should 'summarize for me' support scoped synthesis (e.g., summarizing only the top 3 hits vs. the entire candidate set of 14) to control token spend?
- When a markdown document is opened inline, should follow-up queries in its prompt bar default to asking the orchestrator about the active document, or searching the knowledge base?
- For media and PDF files, should Delphi attempt to extract and display textual passages in the terminal reader first, with browser launch as a secondary action, or always delegate directly to the system viewer?
- Should 'both' mode (offline + online) perform federated ranking that interweaves external web results with local specs, or keep them strictly segregated in separate sections to preserve trust boundaries?
- When an online search is active and untrusted results are retrieved, should 'summarize for me' be permitted to synthesize across untrusted content, or require an explicit operator override before passing untrusted text to the model?
