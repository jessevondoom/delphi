# Spec 092: Operator-authorized tests

> **Status: approved by the operator, 2026-11-07; slice S1 starts after the red-team re-review (§6).** Amends invariant 1 of [`specs/016`](016-headless-run.md) §3 ("Red is never allowed") in one narrow way, for headless runs only. Builds on [`specs/014`](014-relay-and-away-mode.md) §7.1 (a live Red approval with step-up; the number 014 is shared with another spec, see draft 090), [`specs/005`](005-console-and-narrator-tui.md) (the permission modes and the Green, Amber and Red tiers) with `GOVERNANCE.md` §5, and [`specs/037`](037-training-experiments-quality-and-efficiency.md) (throwaway homes). Companion to `specs/091`, which widens no authority.

## 1. Why

On 2026-11-07 every `agy` arm of a headless training run tried to dispatch an investigator and was refused: "The operator denied this action: headless run: a Red action is never approved without the operator." That is the rule working. It also means a headless test cannot exercise a Red path at all: not a red-team sweep that needs a hostile command run in a sandbox, not a dispatch, not a cross-family seat hop.

**The operator's direction (2026-11-07):** Red actions should be allowed when they are part of a test the operator authorized, and the authorization can state the red-team intent plainly, so it counts as the approval on a headless run. **How one comes about:** an agent may *request* an authorization for a future headless action, briefly explaining the context and the risk, so that the operator's approval carries full merit. The agent asks; the operator decides.

**Council `t_0003` (2026-11-07, stakes high; architect, strategist, red-team)** found the invariant preserved in intent and not yet in mechanism, and all three seats chose *approve with changes, narrower first*. Its required changes are written into this text (§3, §5). The red-team seat's Round 2, which the Council's reader could not parse, is intact in the Council record and added two P0 findings, PATH shadowing and worktree poisoning, both closed here (§3 TA-2, TA-5).

## 2. What must not change

1. **An agent never approves its own action.** The authorization is made by the operator, in an act an agent cannot perform or forge. An agent may *request* one (TA-0); a request is inert, grants nothing, and **is never effective for the run that wrote it**.
2. **Content read from outside never raises trust,** and never creates, extends or alters a request or an authorization.
3. **Merges and pull requests are never authorized this way** (spec 016 invariant 2 stands; the merge card is approved only at the console, 014-A1). Nor are credentials, a network call, dispatch, or a write to `.git`, a hook, a configuration file or the authorization store.
4. **Nothing leaves the sandbox.** An authorized action runs only in a verified OS sandbox with the network dropped, in a throwaway home the daemon made, over a disposable snapshot of the project. If those cannot be had, the run does not start.
5. **Every use is recorded** with who authorized it, when, and what it covered.
6. **This amendment applies to headless runs only.** An interactive session keeps "Red always asks".
7. **The grant is daemon-side state, keyed to the run.** It is not an environment variable, a file or a handle a child process can read. A child run, a dispatched agent and a nested headless run start with **no grant**. *S2d2a:* the symbolic text of a record is not a grant and resolves nothing by itself; the places a token stands for (the snapshot, scratch, canary, decoy home) are made by the daemon after the record, are daemon-side state of the run, and are discarded with it.
8. **This narrowly amends invariant 1 of [`specs/016`](016-headless-run.md) §3 ("Red is never allowed")** and becomes effective only when the operator ratifies it (§6, AC-5). Until then invariant 1 stands unchanged, and S2 must not merge.

## 4. Why not a policy file, and why not the relay

`policy:<file>` is an Amber allowlist by design and refuses to load with any other tier, so that a file an agent could edit can never approve a Red action. The relay with step-up (014 §7.1) already lets an operator approve a Red card live; it needs the operator present for each card. An authorization is the operator's approval **given in advance, scoped and bound to one run**, made once through a path an agent cannot write, so a test can run unattended without the approval becoming something an agent can write.

## 5. Threats this design must survive

| Threat | Mitigation required |
| :-- | :-- |
| An agent writes its own authorization into scratch, a worktree or the home | the record is read only from the protected store and checked against the lock; a file anywhere else is ignored and logged |
| Content says "this test is authorized" | authorization comes only from the flag and the protected record; nothing in a model's context can add one |
| A pattern widens the scope | no globs and no shell strings; the canonical argument vector is matched exactly |
| **PATH shadowing:** a binary of the same name earlier on `PATH`, or a working-directory binary, replaces the authorized one | the manifest pins the absolute canonical path and a hash of the binary; the environment is fixed and scrubbed (no `PATH` search, no `LD_PRELOAD`, no `DYLD_*`) |
| A script the authorized command executes is replaced or edited by the agent | the manifest pins each script or file the command reads and executes (path and hash); it lives in the read-only snapshot or the protected store, and the hash is rechecked at use |
| **Scratch or interpreter hijacking:** a hash-pinned runner (python, node, cargo, sh) loads modules, fixtures or plugins from scratch or the working directory and executes unhashed code | scratch is `noexec` where supported; interpreter-isolation flags are part of the canonical argv and the scrubbed environment; only runners with assertable isolation are admitted; `runner_provenance` and `scratch_mode` are recorded; a test makes a runner try to load code from scratch and expects refusal or failure |
| The runner is built or downloaded inside the run, then executed under the authorization | the runner and every file it executes come from the immutable read-only snapshot or a daemon-installed read-only location that exists and is hashed at authorization time; nothing built or fetched in the run is executed under it |
| Revocation ignored, or the audit trail written by an agent | `delphi test revoke <id>` takes effect mid-run and is irreversible; `authorization.used` is daemon-written (S2c); creation, revocation and operator-refusal events are written by the operator's own `delphi test` process (see TA-3 Audit, amended 2026-11-08) into a hash-chained log whose head the pinned store records; no agent has a write path |
| The amendment is read as a standing permission | TA-6: only a headless run with the flag and only that record's manifest entries; any looser reading is a violation |
| The sandbox is verified at start, then becomes unavailable | the daemon re-probes before each authorized action, the first included, and refuses if the probe fails; a test forces the sandbox unavailable and expects refusal, never an unsandboxed run |
| A child, a dispatched agent or a nested run inherits the grant | the grant is daemon-side state keyed to the run, not an environment variable or a readable file; children start with none |
| **Worktree poisoning:** a build script or test hook alters source, caches or hooks that persist into later runs | the project is a disposable snapshot, read-only to the command, discarded after the run; the command writes only to a scratch directory |
| Approval by composition: write a payload with an Amber tool, run it with the authorized command | no file-write tool is offered in an authorized run (TA-5); the snapshot is read-only |
| The "throwaway" home is a label: symlinks or mounts reach real data | the daemon creates it fresh and checks for symlinks, mounts and credentials at start and at each use; the OS sandbox is mandatory or the run does not start |
| Replay of the record: another run, another day, another machine or home | expiry, `max_uses`, a **required** run binding, home and machine binding, a daemon-kept use counter |
| Time of check versus time of use | the run pins the record hash at start and re-verifies at each use; a counter decrement precedes the action |
| An agent starts, or nests inside, a headless run that carries the flag | a run started by an agent, or nested, may not carry `--on-card authorization:` |
| An agent edits the authorization store, the configuration or the flag of a later run | those paths are in the deny-list and unwritable by agents (TA-5) |
| A persuasive or misleading request | the operator sees the manifest and the dry run first; the agent's prose is collapsed, labelled as data, and cannot change the manifest |
| Prose and manifest disagree | both are shown and the difference flagged; the manifest wins |
| A request written by a span that read hostile outside content | taint is computed by the daemon from the span, never from the requester's text; refused at staging at `federated_peer` taint or lower; otherwise shown at the top; below `internal_empirical` the operator retypes or confirms the literal argv |
| Request flooding and operator fatigue | caps (5 manifest entries per record, 3 pending per run, 5 per mission), de-duplication by manifest hash, a rate limit, a refusal that is not re-staged, and prose collapsed by default |
| A request approved, then edited by the agent | an approved record is a new operator-made file bound to the request's hash; a changed request is a new request |
| Escape sequences in the request aimed at the operator's terminal (line overwrite that hides the true scope) | stripped on staging and on display; the manifest is rendered by Delphi from structured fields, never from agent text |
| A relay-forwarded request approved through the relay (confused deputy) | authorization needs a local terminal and step-up; a relay cannot approve |
| Alias ambiguity: two names for one tool | tool names are canonicalised before matching and before display |
| A grant outliving its purpose | a maximum lifetime (OD-2); expired records reported in `delphi doctor`; revocation |
| A used authorization erodes "Red always asks" in interactive runs | the amendment is headless-only; every use appears in the operator's summary |

(c) **`run_authorized`** (`Grant::run_authorized`, `authorization_run.rs`), given a command that equals a manifest entry: ignores the call's working directory and environment and uses the record's (the event says so); re-checks everything the dry path checks (one shared function, `verify_entry_at_use`: store pin, audit chain, launch hash, revocation, expiry, run, home, machine, the deny-list, the interpreter and every pinned file re-hashed) plus the throwaway home (re-walked), the snapshot (re-hashed), the scratch directory and the ledger anchor; copies the pinned script into a private 0500 directory made at use time beside the snapshot and hashes THAT copy; probes the sandbox, then takes one use from the REAL ledger (fsynced before the action, hash-chained, under the writer lock with the 250 ms retry; the ledger must be exactly where this run last saw it), then logs `authorization.used` (id, record hash, entry, index, uses left, tree hash, purpose), then re-hashes the copy and the interpreter and probes again immediately before exec, and runs the command only through S2b's sandbox (`authorized_spec`: no network, no-exec scratch, `file-map-executable` denied, the one literal `/bin/bash`, `scrubbed_env()` exactly, the snapshot as cwd, the real limits and a real scratch quota with kill-over-quota, the session killed on timeout), with the script argument replaced by the private copy. It never calls `exec.run`, never runs unsandboxed, and refuses (the use not taken) when the sandbox is unavailable or any probe fails; a failure after the decrement (a failed second probe or log write) leaves the use consumed. stdout, stderr and the exit status are captured, size-capped and returned; `authorization.ran` follows. **Residual windows:** the gap between the last hash of the private copy and bash opening it (a process of the same user outside the sandbox could swap a 0400 file in a 0500 directory; the sandboxed command cannot); the interpreter is hashed and then exec'd by path (a swap needs a write to the sealed volume); `fexecve` would not help for a script, which bash opens by path. **Test-only until S2d2:** the `authorization_run` module is `#[cfg(test)]` in `lib.rs` (as is `take_use_anchored`), so no product code can call `run_authorized` by construction; the workspace scan stays as a second line. **A limit, not widened:** the script runs from a private copy in its own directory, so a script that finds sibling files by a path relative to `$0` finds none; other pinned files are re-hashed at their original paths and are readable only where the snapshot is. **What the throwaway-home daemon exposes:** it is the operator's user, so it can read the operator's store, audit chain and ledger and append to the ledger, only through the path the grant carries (S2c); as traced (not red-teamed), no model-facing tool reaches that path: the granted tools are the read tools of the allowlist, the path guard refuses `operator/` and paths outside its roots, and the sandbox profile excludes both homes; so the exposure is a defect in the daemon itself, not a reach of the model. The throwaway workspace's `projects` line points at the SNAPSHOT (a configuration without exactly one such line refuses the run) and the launcher opens the mission from the snapshot's path, so a read tool that resolves the project reads the disposable copy and the real project's path is not sent to the daemon; the one remaining use of a path outside is the copied workspace registry (`specs/058`), which holds only what the operator registered. **The granted daemon's environment** is an allowlist (`spawn::granted_env`): `PATH`, `HOME` (the launcher's real one, because the claude CLI finds its login through it), `USER`, `LOGNAME`, `SHELL`, `LANG`, `LC_ALL`, `TERM`, `TMPDIR`, `XDG_CONFIG_HOME` and the release stamp; no API key, token or other variable reaches it or a seat it starts (tested with a planted secret, read from the running daemon). Consequence: an API-key endpoint cannot serve a granted run; only harness logins do. **The throwaway configuration** is rewritten, not copied (`run_granted::granted_config`): the tables `auth`, `connectors`, `relay`, `search`, `library`, `hooks`, `update`, `federation`, `mcp`, `web`, `rag` and `kb` are dropped, every key whose name says api_key, token, secret, password, passphrase, private_key, bearer or authorization is removed at any depth, `[workspace] projects` is the snapshot, the pinned access blocks are sealed again over what is left, `local/kb` is not carried, and a configuration that does not parse or has no `[workspace]` refuses the run. `[access]`, `[endpoints]`, `[harness]` and `[exec]` stay because routing and the sandbox need them. The walker also refuses `.docker`, `.kube`, `.git`, `.gitconfig`, `hosts.yml`, `kubeconfig*`, `*.keychain`, `*.keychain-db` and any name containing `credentials`; the snapshot holds tracked files only and never a `.git` entry (tested with a token in `.git/config`). The first re-hash of the private copy in `run_authorized` is intentionally redundant with the second (defence in depth). **Open for S2d2:** an entry's fixed arguments are pinned text, so a script that must be told per-run paths (the snapshot, the scratch directory, a host port) can only be authorized for paths known in advance; the acceptance run builds those paths first and then the record, which a real launch cannot do. (d) **The ledger anchor.** The launcher, which is the operator's own process, appends an `authorization.run.launch` event (the real ledger's count and head, `after_crash`) to `operator/audit` through the same writer lock and the same pinned-head update that `authorize` and `revoke` use, and `authorization.run.end` (count and head) when the run ends (also on every early exit); the next launch compares the ledger with the last of these and REFUSES, naming the reason, if the ledger is shorter, its head differs, or (after a clean end) it is anything but exactly what the end recorded, or if it holds uses with no recorded run at all. The daemon keeps the count and head in memory (the launcher's record at boot, then after each use it took) and takes each use under the ledger's lock only if the ledger is exactly there. Tested: a cut tail, a deleted directory, an older copy put back, a ledger edited mid-run, a crash with no `run.end`, and a cut audit log. **What it does not cover:** a same-user attacker who rewrites the store, its pin, the audit log and the ledger consistently (the exposure TA-3 states); a cut between the daemon's check and its append (one locked read-and-append, and the attacker holds no lock); and a run that crashed (no `run.end`): the next launch can only require the ledger to be at least as long as at that run's launch and to contain its head, so uses taken in the crashed run and then cut off are not seen. That launch is allowed, prints a notice and records `after_crash: true`, and the record's remaining uses should be read as an upper bound. One live run per record is the working rule (a second launch moves the ledger under the first daemon, whose next use refuses). (e) **Carry-overs from the S2c reviews.** `inspect_system` is off the granted allowlist. The daemon captures its parent pid once at boot and uses that one value for the launcher check and for the watcher, and refuses a grant when the parent is pid 1, so a launcher that dies after the check can no longer leave a daemon holding the grant that never exits. The seat check no longer rests on the environment: the launcher also reads its process ancestry (`ps`) and refuses when an agent seat (`claude`, `agy`, `codex`, `gemini`, `copilot`) or Delphi's daemon is an ancestor, or when the ancestry cannot be read, and still requires a controlling terminal and checks the environment markers; the daemon still refuses a grant that did not come from the launcher it names. **The claude seat** (from a probe of the real CLI 2.1.319): with the S2c flags its init tool list is exactly the bridge tools and a native tool it is asked for gets "No such tool available" and never runs. A tool_use of ANY name that is not Delphi's bridge tool (or `StructuredOutput` with a schema) ends the span AT THE CALL: a native tool, a connector, a plugin tool, an unknown name, a name differing only by case. Nothing is tolerated as an "attempt" and nothing waits for a result (an earlier draft tolerated a refused native attempt for 250 ms; a tool that would have run could finish inside the window, so it was removed). A refused attempt therefore costs the run, which is accepted. The init-list check is unchanged. A granted claude launch also passes `--disable-slash-commands`, `--disallowedTools` naming the native tools, and `--max-turns 12` (the profile's own cap wins); all three exist in 2.1.319, and a CLI that does not know one refuses to start rather than run without it. What the CLI lists at init besides tools (slash commands, skills, agents, plugins) is recorded in an `authorization.launch_note` event (a separate event, not a field of `would_use`/`used`, which are written by the engine and not by the seat) and is never a reason to stop. **The accepted bound:** none of these proves a human; they close the known ways an agent seat or a daemon child reaches the flag. The dry ledger stays separate and keeps observing. (f) **The end-to-end acceptance** (an engine-level test, macOS only, skipped with a printed reason elsewhere; the GitHub macOS runner runs it): a real record for `/bin/bash <red_team_sweep.sh>` with the script in the snapshot, a real grant through the launcher's payload, a fresh home and snapshot; the sweep exits 0 with all 22 attempts blocked, there is exactly one `authorization.used`, the real ledger holds 1 and the dry ledger 0, the snapshot is unchanged and the home is discarded; negative controls: a weakened profile reports the sweep FAILED and names the attempt, a tampered script is refused with no use, a revoked record is refused with no use, a forced-off sandbox is refused (before the use, and after it when it fails only at the second look), two concurrent calls on a one-use record run exactly one. **What S2d1 cannot do:** approve a card, make a run call `run_authorized`, change `decide()`, `specs/016` or `AGENTS.md`. S2d2 connects the engine to `run_authorized`, flips the constant and amends `specs/016` §3 and `AGENTS.md` (AC-5), with the operator's ratification.

## 7. Acceptance criteria

- **AC-1** A headless run with a valid authorization approves a matching Red card and records `authorization.used`; the same run without it denies the card.
- **AC-2** Every row of §5 has a test that fails against a version without its mitigation.
- **AC-3** A merge, pull-request, credential, network, dispatch or `.git` card is denied under any authorization.
- **AC-4** Without a verified sandbox the run does not start, and a test that makes the sandbox unavailable after start (and at the first use) sees the action refused, never run unsandboxed.
- **AC-5** This narrowly amends invariant 1 of `specs/016` §3, and the amendment is effective only when the operator ratifies it as a constitutional change under `GOVERNANCE.md` §5.7 ("any change to this file, REVIEW.md or `context/heuristics.md` ... is staged as a proposal and applied only after the operator approves the diff"). §5.7 names those files, not spec invariants; the spec invariant and `AGENTS.md` are not listed, so the ratifying act is the operator's explicit approval of the amended text, recorded in this spec's `amendments:` entry, and of the `GOVERNANCE.md` diff if S2 touches §5.4 or §5.10 (then §5.7 applies in full). **Until that ratification S2 must not merge.** `AGENTS.md` and `specs/016` §3 are amended in the same pull request that builds S2, so the text says what the code does: "Red actions are asked of the operator, live or, in a headless run only, through an authorization the operator ratified for that run."
- **AC-6** A runner that tries to load code from scratch or the working directory is refused or fails; a runner built or fetched inside the run is not executable under the authorization; the record stores `runner_provenance` and `scratch_mode`.
- **AC-7** `delphi test revoke <id>` stops the next use mid-run and the record cannot be re-enabled; `authorization.used` exists only as a daemon-written entry in the event log, and creation, revocation and operator-refusal events only as entries written by the operator's own `delphi test` process into `operator/audit` (TA-3 Audit); a use outside TA-6 is denied.

## 8. Non-goals

Authorizing anything for an agent's own benefit. A standing "allow red" mode. Authorizing anything in the operator's real home or outside the sandbox. A shared or exported authorization. Any change to interactive runs.

## 9. Decisions

**Direction from the operator, 2026-11-07:** a test the operator authorizes may run Red actions headless; an agent may request one with context and risk. **Council advice (`t_0003`):** staged approval, the sandboxed-shell slice first, with the P0s above written in before implementation. **Decided by the operator, 2026-11-07 ("approve all of the above"): OD-0 approved and the recommended answers to OD-1 to OD-5 accepted:**

- **OD-0** The sandboxed-shell-only first slice, with the P0s above closed in this text. **Approved.**
- **OD-1** Which commands the first authorization may name. **Decided:** offline test runners, nothing else. *Reworded 2026-11-07 (the earlier "already built in the throwaway home" cannot be hashed at authorization, because the home does not exist before launch):* the runner binary, and every script or file it executes, must come from the immutable read-only project snapshot or a daemon-installed read-only location that exists at authorization time, and is hashed there; nothing built or downloaded inside the run may be executed under the authorization.
- **OD-2** Maximum lifetime and uses. **Decided:** 24 hours and 50 uses, shorter for the first slice. *Confirmed by the operator, 2026-11-07 (reply "confirm" on PR #559):* the first-slice default is 2 hours and 10 uses (24 h and 50 uses stay the maximum), so that rubber-stamping long grants is not the path of least resistance.
- **OD-3** Whether creating an authorization requires the operator's step-up. **Decided:** yes. *Confirmed by the operator, 2026-11-07 (reply "confirm" on PR #559):* the review card (TA-0r) always shows the dry-run summary, so the step-up is given on evidence.
- **OD-4** Whether one authorization may cover several runs of a study. **Decided:** no: a run binding is required, so a study needs one per run or a launcher that mints them from one operator act. The launcher is decided with S3. *Design (S2d2a, not ratified, nothing built):* see TA-4, a batch minted from one operator act as N ordinary one-run records.
- **OD-5** How many requests may be pending, and for how long. **Decided:** five per mission, expiring after seven days.

## 10. Known limits

An authorization is only as strong as the protected store, the OS sandbox and the lock around them, and the launch code is only as strong as the privacy of the authenticator secret: that secret sits in the operator's login keychain, readable without a prompt by any process running as the operator (see TA-2), so a same-user agent with a shell can compute valid launch codes; if an agent can write to the store, or the sandbox is weaker than assumed, nothing here helps, which is why the sandbox is mandatory and the store is tested for forgery before anything else is built. A test runner that loads fixtures or configuration can execute arbitrary code; the sandbox, the read-only snapshot and the dropped network are what contain that, not the manifest. It authorizes an *action*, not an *outcome*.
