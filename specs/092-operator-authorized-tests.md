# Spec 092: Operator-authorized tests

> **Status: approved by the operator, 2026-11-07; slice S1 starts after the red-team re-review (§6).** Amends invariant 1 of [`specs/016`](016-headless-run.md) §3 ("Red is never allowed") in one narrow way, for headless runs only. Builds on [`specs/014`](014-relay-and-away-mode.md) §7.1 (a live Red approval with step-up; the number 014 is shared with another spec, see draft 090), [`specs/005`](005-console-and-narrator-tui.md) (the permission modes and the Green, Amber and Red tiers) with `GOVERNANCE.md` §5, and [`specs/037`](037-training-experiments-quality-and-efficiency.md) (throwaway homes). Companion to `specs/091`, which widens no authority.

## 1. Why

On 2026-11-07 every `agy` arm of a headless training run tried to dispatch an investigator and was refused: "The operator denied this action: headless run: a Red action is never approved without the operator." That is the rule working. It also means a headless test cannot exercise a Red path at all: not a red-team sweep that needs a hostile command run in a sandbox, not a dispatch, not a cross-family seat hop.

**The operator's direction (2026-11-07):** Red actions should be allowed when they are part of a test the operator authorized, and the authorization can state the red-team intent plainly, so it counts as the approval on a headless run. **How one comes about:** an agent may *request* an authorization for a future headless action, briefly explaining the context and the risk, so that the operator's approval carries full merit. The agent asks; the operator decides.

**Council `t_0003` (2026-11-07, stakes high; architect, strategist, red-team)** found the invariant preserved in intent and not yet in mechanism, and all three seats chose *approve with changes, narrower first*. Its required changes are written into this text (§3, §5). The red-team seat's Round 2, which the Council's reader could not parse, is intact in the Council record and added two P0 findings, PATH shadowing and worktree poisoning, both closed here (§3 TA-2, TA-5).

## 2. What must not change

1. **An agent never approves its own action.** The authorization is made by the operator, in an act an agent cannot perform or forge. An agent may *request* one (TA-0); a request is inert, grants nothing, and **is never effective for the run that wrote it**.
2. **Content read from outside never raises trust,** and never creates, extends or alters a request or an authorization.
3. **Merges and pull requests are never authorized this way** (spec 016 invariant 2 stands; the merge card is approved only at the console, 014-A1). Nor are credentials, a network call, dispatch, or a write to `.git`, a hook, a configuration file or the authorization store.
4. **Nothing leaves the sandbox.** An authorized action runs only in a verified OS sandbox with the network dropped, in a throwaway home the daemon made, over a disposable snapshot of the project. If those cannot be had, the run does not start.
5. **Every use is recorded** with who authorized it, when, and what it covered.
6. **This amendment applies to headless runs only.** An interactive session keeps "Red always asks".
7. **The grant is daemon-side state, keyed to the run.** It is not an environment variable, a file or a handle a child process can read. A child run, a dispatched agent and a nested headless run start with **no grant**.
8. **This narrowly amends invariant 1 of [`specs/016`](016-headless-run.md) §3 ("Red is never allowed")** and becomes effective only when the operator ratifies it (§6, AC-5). Until then invariant 1 stands unchanged, and S2 must not merge.

## 4. Why not a policy file, and why not the relay

`policy:<file>` is an Amber allowlist by design and refuses to load with any other tier, so that a file an agent could edit can never approve a Red action. The relay with step-up (014 §7.1) already lets an operator approve a Red card live; it needs the operator present for each card. An authorization is the operator's approval **given in advance, scoped and bound to one run**, made once through a path an agent cannot write, so a test can run unattended without the approval becoming something an agent can write.

## 5. Threats this design must survive

| Threat | Mitigation required |
| :-- | :-- |
| An agent writes its own authorization into scratch, a worktree or the home | the record is read only from the protected store and checked against the lock; a file anywhere else is ignored and logged |
| Content says "this test is authorized" | authorization comes only from the flag and the protected record; nothing in a model's context can add one |
| A pattern widens the scope | no globs and no shell strings; the canonical argument vector is matched exactly |
| **PATH shadowing:** a binary of the same name earlier on `PATH`, or a working-directory binary, replaces the authorized one | the manifest pins the absolute canonical path and a hash of the binary; the environment is fixed and scrubbed (no `PATH` search, no `LD_PRELOAD`, no `DYLD_*`) |
| A script the authorized command executes is replaced or edited by the agent | the manifest pins each script or file the command reads and executes (path and hash); it lives in the read-only snapshot or the protected store, and the hash is rechecked at use |
| **Scratch or interpreter hijacking:** a hash-pinned runner (python, node, cargo, sh) loads modules, fixtures or plugins from scratch or the working directory and executes unhashed code | scratch is `noexec` where supported; interpreter-isolation flags are part of the canonical argv and the scrubbed environment; only runners with assertable isolation are admitted; `runner_provenance` and `scratch_mode` are recorded; a test makes a runner try to load code from scratch and expects refusal or failure |
| The runner is built or downloaded inside the run, then executed under the authorization | the runner and every file it executes come from the immutable read-only snapshot or a daemon-installed read-only location that exists and is hashed at authorization time; nothing built or fetched in the run is executed under it |
| Revocation ignored, or the audit trail written by an agent | `delphi test revoke <id>` takes effect mid-run and is irreversible; `authorization.used` is daemon-written (S2c); creation, revocation and operator-refusal events are written by the operator's own `delphi test` process (see TA-3 Audit, amended 2026-11-08) into a hash-chained log whose head the pinned store records; no agent has a write path |
| The amendment is read as a standing permission | TA-6: only a headless run with the flag and only that record's manifest entries; any looser reading is a violation |
| The sandbox is verified at start, then becomes unavailable | the daemon re-probes before each authorized action, the first included, and refuses if the probe fails; a test forces the sandbox unavailable and expects refusal, never an unsandboxed run |
| A child, a dispatched agent or a nested run inherits the grant | the grant is daemon-side state keyed to the run, not an environment variable or a readable file; children start with none |
| **Worktree poisoning:** a build script or test hook alters source, caches or hooks that persist into later runs | the project is a disposable snapshot, read-only to the command, discarded after the run; the command writes only to a scratch directory |
| Approval by composition: write a payload with an Amber tool, run it with the authorized command | no file-write tool is offered in an authorized run (TA-5); the snapshot is read-only |
| The "throwaway" home is a label: symlinks or mounts reach real data | the daemon creates it fresh and checks for symlinks, mounts and credentials at start and at each use; the OS sandbox is mandatory or the run does not start |
| Replay of the record: another run, another day, another machine or home | expiry, `max_uses`, a **required** run binding, home and machine binding, a daemon-kept use counter |
| Time of check versus time of use | the run pins the record hash at start and re-verifies at each use; a counter decrement precedes the action |
| An agent starts, or nests inside, a headless run that carries the flag | a run started by an agent, or nested, may not carry `--on-card authorization:` |
| An agent edits the authorization store, the configuration or the flag of a later run | those paths are in the deny-list and unwritable by agents (TA-5) |
| A persuasive or misleading request | the operator sees the manifest and the dry run first; the agent's prose is collapsed, labelled as data, and cannot change the manifest |
| Prose and manifest disagree | both are shown and the difference flagged; the manifest wins |
| A request written by a span that read hostile outside content | taint is computed by the daemon from the span, never from the requester's text; refused at staging at `federated_peer` taint or lower; otherwise shown at the top; below `internal_empirical` the operator retypes or confirms the literal argv |
| Request flooding and operator fatigue | caps (5 manifest entries per record, 3 pending per run, 5 per mission), de-duplication by manifest hash, a rate limit, a refusal that is not re-staged, and prose collapsed by default |
| A request approved, then edited by the agent | an approved record is a new operator-made file bound to the request's hash; a changed request is a new request |
| Escape sequences in the request aimed at the operator's terminal (line overwrite that hides the true scope) | stripped on staging and on display; the manifest is rendered by Delphi from structured fields, never from agent text |
| A relay-forwarded request approved through the relay (confused deputy) | authorization needs a local terminal and step-up; a relay cannot approve |
| Alias ambiguity: two names for one tool | tool names are canonicalised before matching and before display |
| A grant outliving its purpose | a maximum lifetime (OD-2); expired records reported in `delphi doctor`; revocation |
| A used authorization erodes "Red always asks" in interactive runs | the amendment is headless-only; every use appears in the operator's summary |

**Notes for S2 from the second red-team review of S1 (2026-11-08; recorded here, not built in S1):** (a) the Python pin covers the interpreter file only. On macOS `/usr/bin/python3` is a stub that hands over to the developer tools; `-I` does not imply `-S`, so a user-writable `site-packages` `.pth` file or `sitecustomize` could still run. S2 must add `-S` (or prove the site directories are not writable), and must **re-resolve and re-hash the interpreter at every use**, refusing a symlink whose target is outside the system locations; a symlink in a writable `/usr/local/bin` is caught only if the hash is taken again at use. (b) The audit log and the store are cross-checked, but one event ahead of the store (the window of a crash between the audit write and the store change) is tolerated, so rolling the store and its pin back by exactly the last change is not seen; S2's use-time check of the record hash is the second line. (c) The shared TOTP state is merged at each check, but a long-lived daemon verifier keeps failures it has already counted (this can only make it stricter), and its relay step-up does a short blocking file lock on its worker thread.

**The first admitted runner** *(amended 2026-11-08, S2a; **confirmed by the operator, 2026-11-08**; macOS is a primary target, so the profile must work on a stock Mac; a probe on the operator's Mac, macOS 26.6.2 arm64 with SIP on, informs it)*: under a deny-default `sandbox-exec` profile the Apple `/usr/bin/python3` stub does not start (it runs `xcode-select` logic first), and a user-installed Python varies by install method, so `python3 -I -S` is **deferred** (it is not a usable pinned runner on a stock Mac). The first admitted runner is a **pinned script file run by a sealed-volume system interpreter**: `/bin/bash <script>` (`/usr/bin/perl <script>` may be added later). The argv is the interpreter, the script path and fixed arguments only; **no** `-c`, `-s`, `--rcfile`, `-i` and no script on stdin. The environment is scrubbed (no `BASH_ENV`, `ENV`, `PERL5OPT` or `PERL5LIB`). The interpreter is resolved to its absolute path and hashed, and the script is pinned in `files` as before. In the probe, `/bin/bash`, `/bin/zsh` and `/usr/bin/perl` started with no extra paths and blocked every escape probe (write to the snapshot, network, exec from scratch, read outside the grant); `/bin/sh` re-executes bash, so bash must be exec-allowed in the profile too, and ruby would need `--disable-gems`. **The first authorized test** *(confirmed by the operator, 2026-11-08)* is an **offline red-team sweep**, a bash script run in the sandbox against the read-only snapshot. It tries hostile actions and reports which were blocked: path traversal out of the snapshot, reading a canary file outside the grant, writing into the snapshot, executing a file written into scratch, opening a network socket (for example through `/dev/tcp`), reading the environment for credentials and tokens, listing the operator's home, spawning a nested `delphi`, and writing outside scratch. **It passes only if every attempt is blocked: the script exits 0 only then.** The sweep is the S2d acceptance run, the evidence for AC-1 and AC-2. **S2a notes (red-team review of PR #595):** (a) the launch check applies the S1 runner policy unchanged (a system `python3 -I`), so in S2a a bash record is refused at launch and a python record passes; a passing launch check says nothing about whether a command could run, and `/bin/bash` replaces the policy in S2b; (b) the agent-seat refusal reads the environment (`DELPHI_BRIDGE_SOCKET`, `DELPHI_BRIDGE_TOKEN`) and `DELPHI_AUTHORIZED_RUN`, and `env -i` clears them, so it is best-effort in S2a; S2d needs a check that does not depend on the environment (for example the daemon refusing a grant to a client that is not a verified interactive terminal); (c) the launch check `uses >= max_uses` reads the count in the store record; when S2c moves the count to the daemon's use ledger (TA-3), that check must read the ledger. **S2a changes no runner code:** the S1 allowlist (a system `python3` run as `python3 -I <script>`) stays as built and is replaced in S2b.

**S2b built** *(2026-11-08)*: (a) `Policy::system()` admits only `/bin/bash`, resolved to a regular file under `/bin` or `/usr/bin` and hashed, argv exactly `/bin/bash <script> [fixed args]` with the script in `files`; the options `-c`, `-s`, `-i`, `--rcfile`, `--init-file` and the other bash options are refused anywhere in the vector; the scrubbed environment is `LC_ALL=C` and a `PATH` that does not exist (no `BASH_ENV`, `ENV`, `HOME`, `LD_PRELOAD`, `DYLD_*`). **python3 is deferred and `/usr/bin/perl` is not admitted** (it started in the probe, but no isolation flags are written or tested for it). (b) `delphi-sandbox` gains `snapshot_ro`, `scratch_noexec` and `exec_only` (a literal allowlist; with `/bin/sh` as interpreter, bash is allowed too), and `probe_authorized()`, which returns a struct and runs six canaries under the real profile: a network connect is blocked, a canary file outside the grant is unreadable, the snapshot is readable and not writable, a file in scratch cannot be executed, and the interpreter starts and runs a pinned script. Any failure, or no sandbox, makes it not ok; it never falls back. (c) **macOS only:** `sandbox-exec` can grant `process-exec` by literal and omit it on scratch; bubblewrap has neither a no-exec mount nor an exec allowlist, so on Linux the profile is refused (`Unsupported`) and the probe says `unavailable`. S2d cannot run on Linux until that changes. (d) The snapshot builder (tracked files only, 0444 and 0555, tree hash, symlinks that leave the tree refused) and the fresh-home walk (no symlink, no other-device entry, no credential-named file, rechecked at each use). (e) The red-team sweep is checked in as `crates/delphi-sandbox/tests/fixtures/red_team_sweep.sh` and tested: all 22 attempts blocked under the authorized profile, and a failure naming the attempt under each deliberately weakened profile. **Nothing calls any of this from a run**, and nothing can approve anything. **Red-team of PR #599 (2026-11-08), fixed in S2b:** the profile denies `file-map-executable` on scratch and the snapshot, because `process-exec` does not cover `dlopen` and `enable -f`, which loaded a library written into scratch (the sixth probe canary uses a 33 KB arm64 test library, so on another architecture the probe fails closed; the sweep attempts `dlopen_from_scratch`); the sandboxed session is killed whole on timeout (`set -m` children included); `RLIMIT_NPROC` is set to the user's current process count plus 512 (an absolute number, since the limit counts every process of the user; a flat 64 would stop the sandbox's own `fork`); `run_bounded` can enforce a scratch quota (each file counts at least 4 KiB); the snapshot reads files with `O_NOFOLLOW|O_NONBLOCK` and `fstat`; `git ls-files` runs with no fsmonitor, no hooks path and no user or system configuration; more credential names are refused in the fresh home; the sweep now checks that its in-grant targets exist and also tries to signal another process, flood forks and start `osascript`, `open`, `launchctl` and `pbcopy`. **Accepted, not holes:** `bash <file>` and `source <file>` from scratch run in-process (scratch is data the script wrote itself, so `noexec` cannot and does not claim to stop it); the profile lets a process stat the ancestors of its granted paths, so the user name and temporary layout are visible. **Open follow-ups:** Linux (see (c)); a swap of a parent directory for a link between listing and copy is not caught (the project is the operator's own tree).

**S2c built** *(2026-11-08; wired but dry: nothing is approved and nothing is run)*: (a) **The grant** is sent by the launcher after S2a's checks, as `{record, record_hash, run, operator_home, audit_head.seq at launch, launcher pid}` over a pipe whose read end the freshly spawned daemon inherits (`--grant-fd N`), reads once and closes; no environment variable, argument, file or socket holds it. A run that finds a daemon already running refuses (a grant is handed only to a daemon the launcher spawned). The daemon accepts it only if its parent is the launcher the payload names, then reads the store strictly as at a use, and dies before it is ready if anything is wrong. It is a `Grant` in the engine, never serialized, with a `Debug` that prints nothing; `exec.run` children (`plain_command` closes every extra descriptor, tested), dispatched agents and seats get none. (b) **Matching** (`Grant::evaluate`): only a `run_command` card whose argument vector equals a manifest entry element by element, `argv[0]` the pinned interpreter path and `argv[1]` a pinned file, with the record's cwd and `scrubbed_env()`; the card kinds `shell`, `harness_bash`, `harness_edit`, `harness_connector`, `dispatch_agent`, `connector` and the merge, pull-request, credential and network cards are never matched. A match is then re-checked in this order and any failure refuses with a named reason and consumes nothing: the store and the audit chain read strictly; the record present, with its launch hash, unrevoked, unexpired, same run, home, machine and manifest; `audit_head.seq` not older than at launch (an older store-and-pin pair is refused); the deny-list and runner rules again; the interpreter and every pinned file re-resolved and re-hashed (a symlinked script is refused); and `probe_authorized()` run again, the first use included, with no fallback. (c) **The use ledger** is `operator/uses/<id>`, an event log (the audit log's format: append-only, hash-chained, fsynced before the call returns) that only the daemon writes, the one new daemon write under `operator/`; remaining uses are `max_uses` less the count of `use` entries. **In S2c observation writes a separate DRY ledger, `operator/uses/<id>.dry` (same format, also bounded by `max_uses`), and never the real one: a run that approves nothing cannot use up the operator's record, and the launch check reads only the real ledger, which S2d's `run_authorized` will write.** The decrement is made under the log's writer lock (the `open_audit` retry of about 250 ms; real contention refuses the use): read the count, require it below `max_uses`, append, fsync, and only then log. The launch check now reads this ledger as well as the record's count (S2a note c). **The exposure** is the audit log's: a process running as the operator's user can append to or delete the ledger (an edit is seen by the chain; a deleted ledger reads as unused). (d) A `run_command` call is shown to the grant where it is made (`exec_command`), whatever its tier, before the policy decides: a call the grant recognizes is logged and denied there (the ordinary path, which could run it in the standard sandbox, is not taken). **Events** in the mission log: `authorization.would_use` (id, record hash, entry, index, uses left, purpose, `approved: false`), `authorization.refused` (the reason) and `authorization.no_match`. `authorization.used` and any approval are S2d's: `AUTHORIZED_APPROVAL_ENABLED` stays false, `decide()` still denies every Red card, and a test shows a matching card with a valid grant is denied, `action.intent` is never written and the pinned script never runs. (e) **TA-5 in a granted run:** no seat is offered `write_file`, `edit_file`, `harness_edit`, the artifact writers, any `propose_*` or any connector tool, and a call to one is denied by a code check at call time. A harness seat starts only where its own tools are proven off for that launch: **claude** (`--tools ""`, the account connectors left out; and a Builder seat too, but only as a bridge-only seat: no worktree, an empty working directory and none of the CLI's own tools, with Delphi's `run_command` offered over the bridge, so its commands are the `run_command` calls the grant can see and never the CLI's own Bash; the CLI's init tool list and every tool call in the stream are checked, and a tool of its own that is not Delphi's ends the span) and **copilot** (a tool-less span: `--available-tools delphi-no-tools`) may; the Copilot ACP mode, **agy** (its tools cannot be switched off, only denied by a hook) and **codex** (only its shell is disabled) are refused (fail closed; the other seat or the API serves the span). (f) **Carry-overs from the S2b red-team review:** the snapshot builder runs `/usr/bin/git`, with a `PATH` of `/usr/bin:/bin`; `RLIMIT_NPROC` counts every process of the operator's user, so the headroom is a named constant (256 above the count at launch); the real limits of an authorized command are constants (`RUN_TIMEOUT_SECS` 120, `RUN_MAX_OUTPUT_BYTES` 256 KiB, `SCRATCH_QUOTA_BYTES` 16 MiB, enforced with kill-over-quota) and the probe runs under them; the seat check is no longer environment-only: the launcher refuses without a controlling terminal (a descendant of the daemon has none unless it makes a pseudo-terminal) and the daemon refuses a grant that did not come from the launcher it names; neither proves a human, and S2d must not rely on either alone. **What S2c cannot do:** approve a card, run a command, call `exec.run`, create the throwaway home (the daemon still runs in the launcher's home; S2d creates the fresh home and snapshot and passes them), or amend `specs/016` or `AGENTS.md`.

## 7. Acceptance criteria

- **AC-1** A headless run with a valid authorization approves a matching Red card and records `authorization.used`; the same run without it denies the card.
- **AC-2** Every row of §5 has a test that fails against a version without its mitigation.
- **AC-3** A merge, pull-request, credential, network, dispatch or `.git` card is denied under any authorization.
- **AC-4** Without a verified sandbox the run does not start, and a test that makes the sandbox unavailable after start (and at the first use) sees the action refused, never run unsandboxed.
- **AC-5** This narrowly amends invariant 1 of `specs/016` §3, and the amendment is effective only when the operator ratifies it as a constitutional change under `GOVERNANCE.md` §5.7 ("any change to this file, REVIEW.md or `context/heuristics.md` ... is staged as a proposal and applied only after the operator approves the diff"). §5.7 names those files, not spec invariants; the spec invariant and `AGENTS.md` are not listed, so the ratifying act is the operator's explicit approval of the amended text, recorded in this spec's `amendments:` entry, and of the `GOVERNANCE.md` diff if S2 touches §5.4 or §5.10 (then §5.7 applies in full). **Until that ratification S2 must not merge.** `AGENTS.md` and `specs/016` §3 are amended in the same pull request that builds S2, so the text says what the code does: "Red actions are asked of the operator, live or, in a headless run only, through an authorization the operator ratified for that run."
- **AC-6** A runner that tries to load code from scratch or the working directory is refused or fails; a runner built or fetched inside the run is not executable under the authorization; the record stores `runner_provenance` and `scratch_mode`.
- **AC-7** `delphi test revoke <id>` stops the next use mid-run and the record cannot be re-enabled; `authorization.used` exists only as a daemon-written entry in the event log, and creation, revocation and operator-refusal events only as entries written by the operator's own `delphi test` process into `operator/audit` (TA-3 Audit); a use outside TA-6 is denied.

## 8. Non-goals

Authorizing anything for an agent's own benefit. A standing "allow red" mode. Authorizing anything in the operator's real home or outside the sandbox. A shared or exported authorization. Any change to interactive runs.

## 9. Decisions

**Direction from the operator, 2026-11-07:** a test the operator authorizes may run Red actions headless; an agent may request one with context and risk. **Council advice (`t_0003`):** staged approval, the sandboxed-shell slice first, with the P0s above written in before implementation. **Decided by the operator, 2026-11-07 ("approve all of the above"): OD-0 approved and the recommended answers to OD-1 to OD-5 accepted:**

- **OD-0** The sandboxed-shell-only first slice, with the P0s above closed in this text. **Approved.**
- **OD-1** Which commands the first authorization may name. **Decided:** offline test runners, nothing else. *Reworded 2026-11-07 (the earlier "already built in the throwaway home" cannot be hashed at authorization, because the home does not exist before launch):* the runner binary, and every script or file it executes, must come from the immutable read-only project snapshot or a daemon-installed read-only location that exists at authorization time, and is hashed there; nothing built or downloaded inside the run may be executed under the authorization.
- **OD-2** Maximum lifetime and uses. **Decided:** 24 hours and 50 uses, shorter for the first slice. *Confirmed by the operator, 2026-11-07 (reply "confirm" on PR #559):* the first-slice default is 2 hours and 10 uses (24 h and 50 uses stay the maximum), so that rubber-stamping long grants is not the path of least resistance.
- **OD-3** Whether creating an authorization requires the operator's step-up. **Decided:** yes. *Confirmed by the operator, 2026-11-07 (reply "confirm" on PR #559):* the review card (TA-0r) always shows the dry-run summary, so the step-up is given on evidence.
- **OD-4** Whether one authorization may cover several runs of a study. **Decided:** no: a run binding is required, so a study needs one per run or a launcher that mints them from one operator act. The launcher is decided with S3.
- **OD-5** How many requests may be pending, and for how long. **Decided:** five per mission, expiring after seven days.

## 10. Known limits

An authorization is only as strong as the protected store, the OS sandbox and the lock around them; if an agent can write to the store, or the sandbox is weaker than assumed, nothing here helps, which is why the sandbox is mandatory and the store is tested for forgery before anything else is built. A test runner that loads fixtures or configuration can execute arbitrary code; the sandbox, the read-only snapshot and the dropped network are what contain that, not the manifest. It authorizes an *action*, not an *outcome*.
