Built 2026-11-25 on the local branch `build/143-a` (not pushed, no pull request; the lead integrates).

**Routing (§2.1).** `RouteRequest` has `single_call` and `harness_room`. A harness is refused a turn-by-turn request unless it is a single call, `[routing] single_call_harness` is not `off`, its CLI can run one prompt with its tools off (`route::single_call_cli`: `claude` yes; `agy` never; `codex` and `copilot` not until slice C probes them), **and a subscription token is named for it** (`[bridge.claude] credential`, a credential reference; §2.9 item 4). So an install that names no token routes exactly as before this slice: nothing changes there until the operator names one. Under `auto` (the default) a harness that would serve is set aside when any other allowed endpoint is eligible. Between harnesses the existing ranking leaves level, the one with more room in its window serves, then the endpoint id. Both keys are in `config.rs`, the schema, the config reference and the example config; a pasted token in place of a reference is refused and not shown.

**The marked callers** (`route::SINGLE_CALLERS`, each read): `summary.rs` (the session summary), `decision_run.rs` (a brief, a reply), `page_run.rs` (the writer), `library_page_validate.rs` (the page validator), `fact_judge.rs` (the judge), `library_acquire_run.rs` (the library scout), `research.rs` (`scout_route`, the scout's key). None loops over tools: every one sends a prompt with no tool definitions and reads one answer. No caller was left unmarked.

**The call sites of `one_shot_raw` and `one_shot`** (`summary::CALL_SITES`, 16 in 11 files; a test reads the sources and fails on one that is not listed): `consolidate.rs` 1, `decision_run.rs` 2, `emergency_run.rs` 1, `engine.rs` 2 (the checkpoint's two `one_shot` calls), `fact_judge.rs` 1, `library_acquire_run.rs` 1, `library_page_validate.rs` 1, `page_run.rs` 1, `research.rs` 1, `research_host.rs` 3 (plan, claims, answer), `summary.rs` 2 (`summarize_session`, and `one_shot` itself).

**The Result (§2.2 item 4).** `one_shot_raw` and `one_shot` return `Result<Written, CallError>`; `CallError` is `NoRoute`, `Budget`, `Quota`, `Timeout`, `HarnessTool`, `Launch`, `Empty`, `Provider`, and holds no text. Every call site carries it: into its own error text, and, when the task runs as a background job (`daemon_notice::in_job`: the idle rebuild, background validation, the session summary, consolidation), into that job's notice with the matching cause. A `no_route` notice names `[routing] single_call_harness` when the key is `off` and an allowed harness could have served.

**The tier (§2.2 item 5).** `one_shot_raw` takes the lowest tier of its inputs from its caller and returns it in `Written.tier`, capped at `internal_generated`; a caller that does not say gets `external_untrusted`. Every call site passes `None` today, so every answer is `external_untrusted`.

Not verified, and what waits for slice B:
- **A harness key has nothing to launch yet.** With a token named, routing sends a single call to an allowed `claude` harness, and `one_shot_raw` on that key returns `CallError::Launch` until slice B builds the call. With no token named (every install today) nothing is routed to a harness, the jobs raise `no_route` as in slice D, and the doctor warns and names the key.
- Routing reads only whether a token is **named**; whether the reference resolves is found at the launch (slice B), as `launch`.
- `harness_room` is read by routing and filled by nobody: the ledger is slice B's. Every harness counts as having its whole window.
- `Budget`, `Timeout` and `HarnessTool` are in the closed list and nothing returns them yet (the admission function and the bridge are slice B's). `Launch` is returned only for a harness key.
- "Stored at that tier" (AC-14) is not wired: `Written.tier` is returned, and no caller's store reads it yet. AC-14 and AC-25 (redaction of bridged text) are slice B's criteria in §4.
- A call made from a task the job spawns (not awaited inside it) does not see the job, so its failure would raise no notice. No caller does that today.

Deviations and corrections for the spec:
- **§2.9 item 4 is built here, not in slice G.** "Without a stored token the bridge for that CLI is not eligible" is a routing rule, and AC-21 puts it in slice G with the setup command. Left for later, this slice would have changed a harness-only install at once: the scout's research run (which today is handed to the host when no model seat serves it, `specs/119` §17) would have gone to a bridge that cannot launch. So the rule and the key `[bridge.claude] credential` are here; the command `delphi bridge setup claude`, the keychain write and the test call stay slice G's. Until then the doctor names the key, not the command.
- **`specs/119` §17 and this spec meet, and neither says so.** With a token named and the bridge on, a harness-only install has a scout seat, so a `runner: "daemon"` research request is no longer switched to the host's own tools. That follows from O2 (the scout's calls are among the callers the bridge serves); 119 §17's test still holds as written, because its install names no token.
- **§2.2 item 4 and §2.7 item 1 do not agree.** The closed error list has eight members and "maps one to one onto the notice causes", which are six, one of them (`check_failed`) not a failed call. AC-24 asks for a matching cause for a failed launch and an empty answer. Built: the notice causes gain `launch`, `empty` and `provider`, so the map is one to one from errors to causes, and `check_failed` stays the one cause with no error. §2.7 item 1 needs the three added.
- **AC-13, "a caller that makes more is not marked".** Read here as: no caller feeds a tool result back to the model. The scout's research run makes several single calls in a row (a plan, one per page, an answer) with the daemon's own work between them, and consolidation makes one for each role; each is one prompt and one answer with no tools, and each is marked. If the spec means that a job of several calls may not use the bridge, `research.rs` (which serves `research_host.rs` and `consolidate.rs`) must be unmarked.
- **§2.1 item 6, the ranking.** "The existing ranking" already orders two endpoints of one family (their order in `[access] order`, or the config), so room and endpoint id decide only where it leaves a tie: under an explicit `[routing.pool] order`, or across families. Built that way.
- **§2.4 item 1, ratification.** The new key is read like the rest of `[routing]`; it was not added to the keys the daemon reads only from the ratified copy (`max_cost_class` is the one such key today). If it must be pinned, that is a line in `lock::PINNED_KEYS`.
- A rate limit (`ModelError::Throttled`) is reported as `Quota`, with spent quota.
- An answer that is empty, or only white space, is now `CallError::Empty` from `one_shot_raw`; before, the caller got the empty text and said so itself.
