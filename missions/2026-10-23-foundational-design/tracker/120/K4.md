| 120 | K4 | the `request` grant: four methods, ids and typed text only, limits, events; the gate file's check | built and merged (#743) except the gate file itself: `app.research_continue {topic_id, section?, note?}`, `app.research_ask {question, follows?}`, `app.page_rebuild {slug}`, `app.page_dispute {claim, note}` are the `request` row of `app_keys::GRANTS` (27 methods in all). The server hands them to the engine through an entry of their own (`Extension::app_request`, with the session's key name), only for an app session whose key holds the grant at that call; the engine's ordinary entry never sees them, so the console, narrator, relay and host sockets answer "unknown method". **Revocation (found in K1):** the server runs each request as a task of its own, so a key revoked mid-request closes the session at once and the request still runs to its own end; a research run is queued in the one queue and a rebuild is its own task, so no work is held inside a call. Each runs the code of the terminal's command as the operator's (`continue_as_operator`, `launch_research`, `topic_rebuild`, `dispute_claim`). A parameter outside the method's list, or one that is not a string, refuses the call before anything is counted. **Chose:** limits are per key, 30 an hour counted for every well-formed request whether or not the daemon then starts it, 4 running at once, kept in memory (a restart forgets the hour); a request past a limit writes no event, so the log cannot be flooded; `app.request` is written again at each change of state (`queued`, `running`, `done`, `failed`, `cancelled`, `refused` with the daemon's sentence) and never holds typed text; a section is named in the run's note as `(section: <anchor>)` after the daemon finds a heading with that anchor on a page that follows the topic, so the one page-derived thing a request carries is at most 80 lowercase letters, digits and hyphens; a follow-up question is researched in the project of the topic it follows and the id it follows is recorded only in the event; a rebuild already running for the app is not started twice. **Found:** the 2,000-character bound of §4.2 item 5 is never the binding one, since the terminal's own rules still apply (a note 120 characters, a question 200, a dispute 500); the console allows one research run at a time, so a second research request while one runs is refused by that rule, not queued; AC-8 is shown only as "no request method answers a card and the app scope is refused `approval.resolve`", since no run of these four raises a card today. **The gate file** (`crates/delphi/tests/app_grants.toml`) and its line in `merge-gates.toml` are gate paths and are in a pull request of their own for the operator to merge at a terminal; until then `crates/delphi/tests/app_grants.rs` holds the table to a copy in the test, and once `merge-gates.toml` names the file its absence or any difference fails |
