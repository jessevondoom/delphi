## 2. Shape

- A new crate **`delphi-xenia`**: pure functions, no network, no LLM, no clock reads except through an injected `Clock`. It holds the record and roster types, the verify-before-parse pipeline, the history walk over an abstract commit list, tier computation and tombstone resolution. Pure code is what the 31 + 23 spec tests and the fuzzers need.
- **`delphi-core`** (the daemon) owns what must not be reachable by an agent: the signing key, `state/` (pins, sticky state), the store clone under `$DELPHI_HOME/xenia/<org>/<store>/`, and the git network operations.
- **`delphi xenia ...`** is a new CLI family; the console gets the endorsement card and the quarantine read.
- A **test-store builder** (`xenia-testkit`, inside the crate's tests) builds signed stores, forks, reverts, takeovers and rewrites. Without it the spec's tests 12–15 and 27 cannot be written.
- **Humans sign, agents don't** is enforced structurally: the sign operation exists only behind a console approval of the exact bytes, and no tool in `tools.rs` can reach it.

### Built so far

- **X0 (2026-10-25):** banners, D-29 item 4 lifted, 007-A1 and 007-A2 applied. `ratified.lock` hashes are not refreshed; `delphi update` in the operator's home does that.
- **X1 (2026-10-25):** crate `delphi-xenia` (34 tests) and `delphi xenia whoami`. Choices the spec left open, recorded here:
  - Every hash anywhere (sidecar `hash`, roster `prev_hash`, the hash inside the roster and freshness signing domains, `target_hash`) is spelled `blake3:` plus 64 lowercase hex. Spec 012 §3 wrote "blake3 of `<n>.json`" for the roster domain without a spelling.
  - A signature can only be made over a `Domain`, which only the three validated constructors can build. The install key cannot be asked to sign free text, and a newline in `org`, `store` or `id` cannot shift the signed fields.
  - Key custody is a `0600` file in a `0700` directory under `$DELPHI_HOME/xenia/`, refused if group- or world-readable, a symlink, or damaged, and never overwritten. An OS-keychain backend is later (R4).
  - The strict-verification tests include a check that a lenient verifier accepts the identity-key forgery, so the test proves it discriminates.
- **X2 (2026-10-26):** `record.rs`, `frontmatter.rs`, `pointer.rs`, `limits.rs` in `delphi-xenia`; one new dependency edge (`unicode-normalization`, already in the workspace, for `is_nfc`). `validate_record` is spec 012 §6 as an explicit pipeline (steps 1-3 via `verify_record` plus a caller-supplied `standing` check, then `check_parsed` for steps 4-10); a `Validated` can only be obtained by passing all of it. The parser counts its calls (`frontmatter::parse_count`) and test 12 asserts the count does not move for an oversized file, a bad hash or signature, a small-order-key forgery, or a non-active signer. Tests: unit tests per module, `tests/record_pipeline.rs` (012 tests 1-5, 10, 12, 18, 20 and both sides of every limit), `tests/record_attacks.rs` (homoglyph/NFC, forged rev, nested trust keys, alias bomb, CRLF, overlong UTF-8, invisible characters), `tests/record_fuzz.rs` (about 24,000 seeded mutants per run against an independent oracle, plus a "would a lenient parser have accepted this" control). Choices the spec left open, recorded here:
  - **The frontmatter is not YAML.** It is a small language that is valid YAML for what it accepts (risk R1, about 300 lines): keys `[a-z][a-z0-9_]{0,31}`; values are double-quoted strings (escapes `\"` and `\\` only), plain scalars (no `# , [ ] { } & * ! | > % @ " ' \`` anywhere, no `: `, no leading `- ? :`), or one-line flow lists; nested maps and block lists of maps (`- key: v`) to 4 levels; two-space indent, LF only, no tabs, comments, blank lines, trailing spaces, `---` or `...` inside the block. No implicit typing: the parser keeps text and "was it quoted", and the schema decides (an integer is unquoted canonical digits; `null` only where the schema allows it).
  - Whole-file hygiene runs before tokenizing and covers the body too: valid UTF-8 (overlong forms and surrogates are not), NFC, no control character but `\n`, no bidi controls, no `U+E0000`-`E007F`. Beyond the spec's list it also refuses zero-width and invisible formatting characters (`U+200B-200F`, `2060-2064`, `FEFF`, `00AD`, `034F`, Hangul fillers, `U+2028/2029`), variation-selector tags (`E0100-E01EF`) and noncharacters. All are the same class of "a reviewer and a machine disagree about what this says".
  - **Required vs optional** (spec 012 §2 marks only some keys OPTIONAL): the whole common envelope is required on every kind, including `title`, `summary`, `tags`, `source_ceiling`, `confidence`, `status`, `redaction`, `body_kind` and `pointers` (`pointers: []` is the empty spelling). Optional: `evidence`, `related`, `expires`, `supersedes` (absent or `null`), `access_hint`, `bytes`, `range`, `hash`, memory `applies_to.paths`, and a tombstone's `note`. `review_by` is required for `memory` and optional elsewhere. An endorsement's `note` is required for `dispute`; `scope` must be non-empty for `endorse`; `redaction.result` must be `passed`.
  - `body_kind: none` requires an empty body and `markdown` a non-empty one (one spelling of "no body").
  - **Pointers.** Locators are printable ASCII only (no IDN or look-alike hosts), lowercase hosts, no userinfo (this also refuses `ssh://git@host/...`; spec 012 §4 says "no embedded credentials" and a username is the part that is one), no `;`, `=`, `&`, `\`, no `%`-encoded dot, slash, `@`, `?`, `#`, colon or controls, no `.`/`..`/empty path segments, and known credential shapes (`ghp_`, `github_pat_`, `glpat-`, `xox*-`, `AKIA...`, JWT) anywhere. **Any query string or fragment is refused on `https`** (stricter than the spec's "no query tokens": a denylist of parameter names would always miss one). `git` pins need a full lowercase 40- or 64-hex object id; `https` pins are `content-hash` or `none`; `xenia` pins are `none` only. A pin of kind `none` has no `value` key. `drive` parses and its pin and id rules are checked, then it is refused for Phase 1 as 012 §6 step 9 says (012 §4 "accepted by the schema" and §6 "rejected in Phase 1" are both honoured). `range` only on git/https text.
  - **Bounds the spec does not name** (all in `limits.rs`, marked "not in spec"): `applies_to` lists 16 items of 120 characters, locator 512, pin value 128, handle 48, scope 12, `rev` at most 10^9, `bytes` at most 2^40, frontmatter line 2560 bytes, 160 lines, 40 keys per map, 64 flow-list items, 16 block-list items. Relaxing any is safe, tightening is breaking.
  - `kind` in the frontmatter selects the schema; the path is checked against it in step 6, so a tombstone-shaped file at a memory path is a `mismatch`, not a smuggled kind. A record that lists itself in `supersedes`, `related` or as its endorsement/tombstone target is refused.
  - Version: the `xenia` value is read before the schema so `xenia: 2` is `unsupported-schema` even with fields this client does not know. The six trust keys are searched at every depth (including inside `pointers` and `applies_to`) before the strict schema runs, giving the specific `forbidden-key` reason; only keys count, so a tag spelled `tier` is allowed.
  - Dates: `created`/`updated` are the 20-character UTC form and must be real calendar days (`is_utc_timestamp` alone accepts February 30th); `review_by`/`expires` are `YYYY-MM-DD`. "In the future at publish" is `Record::check_future_dates(today)` with the caller's injected clock; ingest never calls it, because a record past its review date is shown as stale, not refused.
  - **Spec observations.** (1) 012 §6 step 1 puts the 4 KiB body check "after step 5"; done that way (`BodyTooLarge`, reason `oversize`). (2) 012 §6 step 7 lists the string rules after the schema; the hygiene screen runs earlier over the whole file and the plain-text rules (no Markdown links, no HTML or character entities, one line, no surrounding space) stay at step 7, so a hostile string never reaches schema code. (3) 012 §2 does not say whether `pointers`, `redaction` or `supersedes` may be omitted; chosen as above. (4) The `content_hash` recipe in `redaction` ("body + pointers as scanned") is not defined anywhere; X2 checks only that it is a hash, and X7 must define and recompute it.
  - **Known weaknesses.** Mixed-script confusables inside titles and summaries are allowed (Cyrillic prose is legitimate; confusable detection is a display concern for X6/console). A secret in a URL path is caught only by the prefix list. The body is data and not sanitized here (the 007 §3.2 sanitizer is X6). Monotonic `rev`, ownership, author-state transitions, endorsement scope-vs-areas and target resolution are deliberately not per-record checks: they belong to X4a/X4b/X5 (a test pins that an older valid `rev` passes per-record validation).
  - Deferred: a record serializer (X7 writes records; X2 only reads), the roster `standing` implementation (X3 supplies the closure), and wiring into `delphi-core` (X4a onward).
- **X3 (2026-10-26):** `roster.rs` (epoch files, strict parser, chain rules, `verify_chain`), `pins.rs` (`pins.toml`, `join`, atomic write), `testkit.rs` (signed-roster builder, behind `cfg(test)` or the `test-support` feature). One new dependency edge: `toml` (already in the workspace) for `pins.toml` and the advisory `org.toml`. Choices the spec left open, and where the code departs from or tightens the text:
  - **Trust anchor.** The spec says "pinned trust anchor" without a type. `verify_chain(org, store, files, &Anchor)` takes a non-empty map of epoch to hash (a joiner's single head pair, or an install's pins) and requires the chain to contain every anchored hash exactly; an empty anchor is refused (`no-anchor`), because a chain verified only against itself proves nothing. A chain that stops before the highest anchored epoch is refused as a stale view (`pinned-epoch-missing`), a different file under an anchored number as `pin-mismatch` (equivocation).
  - **Join checks the named admin at the pinned epoch, not at genesis.** The task brief said "genesis matches the fingerprint"; spec 011 §3.3.3 says the pinned admin must be an `active` admin *in the pinned epoch* (a founder-only rule would break joining after the first rotation), and the code follows the spec. `org` and `store` are read from genesis (the operator does not type them) and enforced on every file; they are trusted only because the hash pin covers the chain. Pins record the hash of **every** epoch of the verified chain, not just the head pair ("every install persists the hash of every epoch it has accepted"), as a contiguous `1..=n` map.
  - **Quorum is computed from the previous epoch, never the file being checked**; only `active` admin DIDs of epoch n-1 count, one per person; a bad signature from an admin key is ignored, not fatal; duplicate entries count once. Genesis is signed by every admin **DID** it names (the spec says "every founding admin"; per DID is the stricter reading when one person holds two admin keys).
  - **Spec 011 §3.2 and spec 012 §7 disagree on the entry fields**; the code requires the union: `did, person, handle, roles, steward_areas, added_at, status` plus optional `successor, removed_at_epoch, voids_tombstones` (012 has `added_at`, 011 omits it). `roles` is a non-empty subset of `member`, `admin` (a steward is a member with non-empty `steward_areas`; the spec never lists the role strings). `person` is a slug of at most 32 characters, `handle` is `[A-Za-z0-9._-]{1,32}` (display text that reaches terminals gets a narrow alphabet), `steward_areas` is tags, or `["*"]` alone. Genesis has `"prev_hash": null` (key required, null required; the spec does not say how genesis spells it). `null` for an optional key is refused (a second spelling of "absent").
  - **Transition rules the spec implies but does not enumerate**, all enforced by `check_transition`: status only moves `active -> retired -> removed` (a returning human gets a new DID); once an entry is not `active` its handle, roles and areas are frozen (including in the epoch it leaves, so an exit cannot also rewrite its authority), and its `successor` never changes; `removed_at_epoch` must equal the epoch of removal; `voids_tombstones` may turn on later (for cause) but never off (clearing it would bring a thief's withdrawals back); new entries must be `active` with no successor, removal or voiding; `successor` is allowed only on non-active entries, must exist in the same epoch with the same `person`, and chains may not cycle; every epoch keeps at least one active admin (otherwise the roster deadlocks; recovery is a new genesis, §8.4).
  - **Spec gap, not silently picked:** the spec does not say how a list position, the number inside a file, and the number in the signatures file relate. The signatures file's `epoch` must equal the epoch; a file whose own number is ahead of its list position is an `epoch-gap`; a repeated number is `epoch-fork` (different bytes) or `epoch-replay` (same bytes).
  - `Pins::check_org_toml` implements spec 011 test 6 for the advisory file (only `org` and `store` are compared; other keys are ignored there because the file is advisory by design). The pin URL is validated narrowly (printable ASCII, no quotes or backslashes, not starting with `-`, no password) because it will be passed to the VCS by X4a; the transport allowlist belongs to X4a.
  - `PinStorage` is the injected disk abstraction (`FilePinStorage` for the daemon, `MemoryPinStorage` for tests). `join` refuses to overwrite existing pins and writes only after every check passed, so a refused join leaves no file and no directory. `write_atomic` (temp file `0600` in the same directory, fsync, rename, fsync of the directory; refuses a symlink target) is the helper the daemon should use for sticky state too.
  - **Testkit deviation:** the brief asked for `pub(crate)`; a `pub(crate)` item cannot serve other crates, so `testkit` is `pub` behind `cfg(any(test, feature = "test-support"))`. API: `key(seed)`, `MemberSpec`, `EpochSpec` (`to_json`, `hash`, `sign`), `sign_bytes`, `sigs_json`, and `TestOrg` (`three_admins`, `empty`, `who`, `key`, `did`, `fingerprint`, `draft`, `push_signed`, `advance`, `rotate`, `upto`, `fork_at`, `takeover_with`, `pin_head`, `head_pair`, `anchor_all`, `verify`). It builds invalid chains on purpose and holds keys in memory; never enable the feature in a release build.
  - Known limits: the verifier reads no clock (`added_at` is informational and not ordered); the 4096-epoch and 256-member caps are guesses; handles are not required to be unique within an epoch (display only).

- **X4a (2026-10-26):** pure rules in `delphi-xenia` (`store.rs`, `sticky.rs`), git and disk in `delphi-core` (`xenia_store.rs`), and a reusable git test remote (`xenia_testkit.rs`, behind `test-support`). Choices the spec left open, and deviations:
  - **Layout.** Spec 011 §3.3.5 puts the clone at `$DELPHI_HOME/xenia/<org>/<store>/` and §3.5 puts `state/` at `.../<store>/state/`: those collide (state inside the attacker-filled tree). Resolved as siblings: `<store>/clone/` (bare repository), `<store>/state/` (`sticky.json`, and X3's `pins.toml`), all `0700`. Spec text should say so.
  - **Bare clone, nothing checked out.** Files are read by object id (`git cat-file`), so hooks, filters, `.gitattributes` conversions, symlink creation and submodule handling have nothing to act on; `.gitattributes` is still checked at every sync as the spec requires (012 test 16: bytes read back exactly even with `core.autocrlf=true` in the clone's config).
  - **One git command builder** (`git_command`): cleared environment, empty `HOME`, `GIT_CONFIG_GLOBAL=/dev/null`, `core.hooksPath` to an empty directory, fsmonitor/symlinks/autocrlf/credential helpers/LFS filters off, `protocol.allow=never` plus the single transport of the store URL (also `GIT_ALLOW_PROTOCOL`), `GIT_CEILING_DIRECTORIES` so git never discovers a repository from the working directory, `fetch`-time `--no-recurse-submodules`. The remote URL is passed on the command line, never stored in the clone's config (no credential or URL at rest in the clone).
  - **Accepted URLs:** `https://`, `ssh://` (no embedded `user:password`), and local paths or `file://` only when the caller opts in. `http://`, `git://`, `ext::` and all other helpers are refused. The ssh transport gets the operator's `HOME` and `SSH_AUTH_SOCK` and `-o BatchMode=yes -o StrictHostKeyChecking=yes -o ProxyCommand=none`; it is built but not exercised against a real ssh server.
  - **Caps (the spec gives none for git objects):** 512 KiB per object, 64 MiB per fetch (the fetch is killed when the clone grows past it), 100,000 new objects, 20,000 new commits, 20,000 tree entries, 255-byte paths, depth 6. Measured on every new object reachable from the fetched head and not from the accepted one, so a huge blob hidden in history and deleted at the tip is refused too. A refused fetch removes its objects (`gc --prune=now`).
  - **Tip tree rules (refused outright, whole sync):** symlinks, gitlinks/submodules, executable files, any `.git*` name other than the root `.gitattributes` (case-insensitive, Windows trailing dots, `git~1`), `..`, backslash, colon, control characters, non-UTF-8, oversize file. Refusing instead of ignoring is the fail-closed reading; a store host that wants to be synced does not ship these.
  - **`.gitattributes`:** must contain a `* -text` line and may otherwise only add `-text`, `binary`, `-diff`, `-merge` or `linguist-*`. `filter=`, `text`, `eol`, `crlf`, `ident`, `working-tree-encoding`, `export-subst`, `diff=`, `merge=`, `[attr]` macros and CR bytes are refused. Only the root file is allowed.
  - **Fast-forward only:** the fetch lands in `refs/xenia/fetched`; the accepted head lives in `state/sticky.json` (install-owned state stays out of the clone; `refs/xenia/accepted` only anchors history against gc). A head that is not a descendant is a typed `NonFastForward { accepted, fetched, kind }` with `kind` `Diverged` (rewrite) or `Behind` (the host went back in time); nothing is applied and the staging ref is left for X4b's recovery path to inspect.
  - **Sticky state:** per path `Rev(n)`, `Immutable` (roster epoch files: any other hash is equivocation) or `Present` (sidecars, `*.sigs.json`, `freshness.*`: must not disappear, content may change; their validity is X3/X4b). Spec 011 §3.5 says "highest `rev` per path" but only records have a `rev`, so this is X4a's reading. The update rule is pure (`sticky.rs`): new path, higher rev supersede; lower rev, same rev with another hash, deletion, or a stored path whose file no longer verifies are refusals.
  - **A sync with any sticky refusal applies nothing** (no state change, accepted head unchanged, report lists the paths). The spec says the stored version of a tampered path keeps its effect (§3.5) and that a failed check 3 rejects the whole sync (§4.3); applying the clean paths while refusing the others would let a host smuggle new records past a withheld deletion. Cost: a store stays stuck on its last accepted head until the recovery path (X4b) is used. The state file is only written, atomically (`0600`, fsync, rename), when something changed; a second sync of an unchanged host reads and writes nothing.
  - **Classifier hook.** `sync` takes a classifier `(path, bytes) -> Tracking | quarantine reason`. X2/X5 pass the verifier (signature first, then `rev`); a file that fails it is quarantined and can never raise a stored `rev` and lock the real record out. X4a ships `classify_by_layout` with a caller-supplied `rev` reader for tests.
  - **Damage is an error:** a missing sticky file is a fresh install; a damaged, wrong-store, group/world-readable or symlinked one stops the sync (it is never treated as empty, which would let an attacker reset it).
  - **Known weaknesses:** (1) a delta-compressed pack object that inflates huge is measured only after `index-pack` resolved it (git streams large objects to disk, and the fetch byte cap and timeout bound the damage); (2) the history walk, signature checks, freshness and rewrite recovery are X4b, not here: X4a alone only guarantees the clone and fetch are inert, the head only moves forward, and no path regresses; (3) `PATH` is inherited to find `git`; (4) syncs of one store are serialised with an advisory lock, but nothing stops two different `$DELPHI_HOME`s sharing a clone directory.

- **X4b (2026-10-26):** pure rules in `delphi-xenia` (`freshness.rs`, `walk.rs`, `time.rs`, test builders in `testkit_records.rs`), orchestration in `delphi-core/src/xenia_sync.rs` (`Store::sync_verified`, `freshness_status`, `plan_rewrite`, `accept_rewritten_head`, `GitSource`).   - **Order of one sync:** fetch (X4a) -> roster chain against the pins -> freshness -> history walk -> real classifier -> sticky rules. The walk and the sticky rules agree by construction (both reject deletion, lower `rev`, same-`rev` swap) but not by coincidence: a test shows a `2, 5, 3` history whose tip passes the sticky rule alone and is caught only by the walk. Findings from both are reported once per (path, reason). Pins are extended with every accepted epoch, before the sticky file is written.
  - **Authentic is not current.** A statement is *authentic* when it names the verified chain head epoch and hash, the right org and store, and enough active admins of that epoch signed these exact bytes (one; a per-person majority when `rewrite_of` is present). It is *current* when the local cap (default 14 days, `Policy`), the 5-minute skew rule and expiry hold. Only a current statement lets endorsements count. An authentic one, even expired, is the **trust base** of a fresh install's walk (`store_head`), because only an admin of the head epoch can sign it: a departed admin cannot sign a base. A statement for an older epoch is stale and not authentic. Spec 011/012 say a statement that breaks the cap is "rejected"; here every non-current statement is `Stale{reason}` and the sync is still accepted (spec 011 §4.3 reserves whole-sync rejection for checks 2 and 3). Check 2 (fetched head descends from `store_head`) runs whenever an authentic statement exists, current or not.
  - **A fresh install with no authentic statement accepts nothing** (`no-trust-base`). The spec never says what a fresh install does without one. X8 must write a statement at genesis.
  - **Walk rule.** Every commit is compared with **each** of its parents (a merge shows a deletion against the parent that still had the file; a merge that picks an older version on one side is tampering, which is stricter than necessary on purpose). For each changed path: deleted (unless the old file never verified), roster epoch file changed or not equal to the verified chain's, a record that no longer verifies, signer not active, and the edge rules (signer same or in the successor chain, `rev` not lower, equal `rev` equal hash, `withdrawn` never back to `active`). "Active at that point" means active in the **highest epoch file in that commit's tree**, never the sidecar's `roster_epoch` (spec 011 §3.4: author-chosen). Each intermediate commit must be valid on its own, so a publisher must commit a record and its sidecar together.
  - **Spec ambiguities:** 011 §4.1 `store_head` "the commit the admin verified" cannot name the commit that contains the statement, so it names an ancestor (usually the parent) and the walk covers the commits after it. 012 test 7 only forbids `withdrawn -> active`; `superseded -> active` is allowed (not specified). The quorum for `rewrite_of` is the named epoch's admins (the spec says "the epoch's admins"). Spec 011 §8.4's `rewrite_of` "the replaced head" is matched as: the install's accepted head equals it or is its ancestor in the clone.
  - **Standing vs tracking.** A verified record whose signer is a roster member that is no longer `active` stays tracked by sticky state (so retiring a member is not tampering and its rollback still is) but comes back quarantined `not-active`; the fail-hidden exceptions (a `withdraw` tombstone, an endorsement `withdraw` or `dispute`) are not quarantined unless the entry sets `voids_tombstones`. A signer not in the roster is not tracked.
  - **Rewrite recovery** (`plan_rewrite` shows, `accept_rewritten_head` applies): needs an authentic, current statement with `rewrite_of` signed by a per-person majority, the walk clean from its `store_head`, and an approval that names this exact fetched commit and **exactly** the paths the plan lists (every stored path the new head deletes, reverts, swaps, no longer verifies, or hands to another creator; a sidecar is its own path). Fewer paths -> `NotApproved`, extra paths -> refused, nothing applied either way. Sticky entries of approved paths start over from the new head, every other entry is kept and re-checked, pins are untouched, and one JSON line per path goes to `state/rewrite-log.jsonl`. **The same path also recovers a tampered fast-forward** (the "stuck store" X4a left), which spec 011 §8.4 does not mention; a host that went **back in time** (`Behind`) cannot be recovered, because its older tree cannot contain a statement about a later head.
  - **Mutation checks** (35 guards flipped one at a time, each killed by a test): takeover, rollback, swap, state regression, standing, deletion of records/sidecars/roster files, no-longer-verifies, epoch in effect, retired/voided exceptions, quorum, validity cap, expiry-too-far, future skew, expiry, older epoch, epoch hash, scope, statement-head ancestry, no-trust-base, approval coverage/extras/head binding, statement current, `rewrite_of` ownership, recovery walk, creator change, sticky `without`. Three survivors are equivalent mutants: the sticky-refusal report (the walk covers the same cases), `classify` requiring an epoch file to match the chain (the chain is built from the same files), and the "reset sticky on recovery" mutation (every difference is already a listed, approved path). One mutation (non-admin signers) did not compile and is covered by its test directly.

  - **Scan.** Blocks (the `[REV-SEC-05]` classes): secret/token/private key (the `Redactor` pattern list, plus registered credential literals raw/base64/URL-encoded), local user path, session trace. Flags (spec 011 §7.1 says flags do not block): URL in prose, long high-entropy string, e-mail, workspace identifier, customer/account id. **Departure from the bundle scan:** an e-mail address is a flag here and a failure in `bundle validate` (an org memory may name a contact; a bundle may not). `delphi-bundle` depends on `delphi-core`, so its scanner cannot be imported; the three small expressions only the bundle scan had are repeated and `delphi-bundle/tests/xenia_scan_agreement.rs` pins that both agree on a canary of each class. A finding never carries the value.
  - **Promotion has no state in code yet.** `Origin::Content{scope, promoted, file}` is what the caller attests; operator scope and unpromoted content are refused before any build. Commands (`endorse` ...) use `Origin::Command`; `republish --resign` uses `Origin::Resign` (the content was promoted once and is in the store; it is still scanned and previewed). A memory cannot come from `Command`, a non-memory cannot carry content provenance.
  - **No model turn between preview and sign, by construction.** `prepare` yields `Prepared` (not `Clone`; `sign` consumes it). The only code between preview and signature is `Approver::decide(&Preview)`: immutable plain data, no key, no store, no `Prepared`. `Prepared::sign` recomputes the digest from the bytes it holds (never from the `Preview` a caller could have edited), checks flags were acknowledged, re-reads every `WatchedFile`, then signs. A test reads `xenia_publish.rs` itself and fails if it mentions a client, spawn, hub, server, network, async or a direct `git` spawn, or if any struct holds an `Identity`. The sidecar's `signed_at` and `roster_epoch` are fixed at prepare and are in the digest.
  - **Delivery.** No local branch (spec 011 §7.1 item 4 says "commits on a local branch"): the commit is an **unreferenced object** built with git plumbing through a private temporary index, so a failed publish adds no ref, sticky entry or pin. A record and its sidecar go in one commit (the history walk requires it). The first push uses the head verified at prepare time; only a rejected push triggers a verified sync, a rebuild on the new head, a full re-verify and another push (3 times at most). The candidate is verified before every push with the verifier's own code (`validate_record` with the signer's standing for each new file, and `walk::walk` from the verified head). The push has an explicit `<commit>:refs/heads/<branch>` refspec and no `--force`, `+` or lease (`push_command` is tested for that). A same-id race where the store now holds an equal or higher `rev` stops with `raced`. A remote that rewrote history is `remote-rewrote-history`. The verified syncs that precede an attempt are ordinary syncs and may advance the accepted head, as `delphi xenia sync` would.
  - **A store that went back in time is not an error for a publish**: our commit descends from the head we verified, so pushing it is a fast-forward that restores what the host withheld. Refusing happens at the next sync, as before.
  - **Commands.** Local checks mirror `tier::compute` so the operator hears "outside your areas" before signing something every verifier would ignore: steward role, areas cover the target's tags, scope inside areas and tags, no self-endorsement (person or `successor` chain), a hidden target is refused. A changed verdict is a higher `rev` of the signer's own record for that revision; one tombstone per (signer, target). `restore` is refused when the author withdrew or superseded the record (author-set `withdrawn` is terminal), when a `sensitive` steward hold stands and the signer is not that steward, and when the record is not hidden. A `sensitive` withdraw adds the `rotate-secrets` reminder to the preview. A new id always starts at rev 1; the gate does not believe a rev for an id it has not seen. Tombstone area checks use `Publisher::prior_tags` (the union over revisions) when the caller supplies it, otherwise the tip's tags only (stricter locally, equal to X5's behaviour).
  - **`republish --resign` (spec gap).** The spec says the successor "re-publishes" records and "re-issues" endorsements. Chosen: the **same id, next `rev`, signed by the successor** for every record kind (signer continuity through the `successor` chain is what the walk already accepts, and a second file would be a duplicate under X5's rules). After a rotation the old key's memories are quarantined and a tombstone aimed at one finds no target, so effective withdrawals are found by computing tiers on the roster **as it stood before the rotation** (old key set `active` again). Only records in force are re-signed: visible memories, endorsements that counted (or only lacked freshness), tombstones and disputes; hidden or author-hidden memories are skipped. It is one batch: one preview, one approval, one commit. It refuses a compromise rotation (`voids_tombstones`), a key that is not the successor, a different person, and an empty batch.
  - **Similar records.** `SimilarRecords` trait (`NoIndex` default, a fake in tests); hits are capped at 5, never include the record itself, and are stripped of control characters. X6 implements the trait; nothing here builds search. The list is information and is not part of the digest.
  - **Mutation checks (15 guards flipped one at a time on a very loaded machine, each killed):** serializer escape, serializer structural self-check, verifier content-hash check, recipe body region, recipe evidence region, operator scope, unpromoted content, scan result enforced, approval digest compared, flag acknowledgement, source-change detection, wrong key, record ownership, standing re-checked at delivery, `--force` in the push. **Not run for lack of machine time (tests exist for each, not shown to fail without them):** non-fast-forward rebuild, candidate re-verify, outside-areas, self-endorsement, restore of an author-withdrawn record, sensitive hold, compromise refusal, resign skipping hidden memories, rev advance, author-state regression, future-date check, similar-list self exclusion and control stripping, scan local-path and URL-flag detection, memory-from-command origin.
  - **Known weaknesses.** (1) `Approver` is a trait the caller implements; the gate guarantees what happens in its own module, and the console wiring (X9) must give the approver no model access. (2) TOCTOU protection covers files the caller registers as `WatchedFile`; content that did not come from a file is protected only by the in-memory digest. (3) The scan is patterns and an entropy heuristic: a novel secret format passes as a flag at best. (4) Push rejection is recognised from git's English stderr (`LC_ALL=C` is set); anything else is reported as `push-rejected`. (5) ssh pushes are built but not exercised (as in X4a). (6) A store lock is not held across commit and push. (7) `prior_tags` is still the caller's to keep. (8) Large resign batches are one commit with no paging.
  - **Deferred:** CLI (`delphi xenia publish|endorse|dispute|withdraw|restore|republish`) and the console approval card (X9); the similar-records implementation (X6).

  - **Spec gap: where a signature lives.** Spec 011 §3.2 says each admin "commits their signature entry".   - **Hostile proposals are judged before anyone is asked.** `check_candidate` = the verifier's parser + org/store + number + `prev_hash` + admin policy + `check_transition`. ## 4. Risks that decide the estimate

- **R1 Strict YAML.** The spec requires rejecting anchors, aliases, tags, merge keys and duplicate keys. `serde_yaml_ng` does not. Recommended: do not use a general YAML parser at all; define the frontmatter as a small subset (scalars, flow lists, nested maps for pointers and `applies_to`) and write a ~300-line parser fuzzed from day one. This is within X2's 14 h, but if the subset proves too small for `pointers`, add 4 h.
- **R2 Git as an attack surface.** A hostile store can carry hooks, filters, submodules, symlinks and huge objects. X4a pins git's config for every call (`core.hooksPath` to an empty dir, `protocol.allow` list, `core.symlinks=false`, no `--recurse-submodules`) and caps object size. This is the part most likely to grow.
- **R3 History-walk cost.** The walk runs from the signed `store_head`; a store with thousands of commits makes sync slow. Phase 1 stores are small. Cache the last accepted head and walk only the delta; measure in X10.
- **R4 Key custody.** The key is the org's trust anchor for one human. Keychain on macOS is straightforward; on Linux a `0600` file is weaker. The roster allows rotation, so a lost key is recoverable, a stolen one is `rotate --compromised`.
- **R5 People, not code.** Council 010's biggest remaining risk is steward endorsement latency and admin refresh cadence. No test measures that; X11 does.

## 5. What Xenia changes elsewhere

### 5.1 The librarian (spec 013)

Vectors and hybrid search are built (004-A1, 004-A2), so 013 §7 steps 1–3 are done and the librarian no longer waits on retrieval quality. What Xenia changes:

1. **Build trigger 4 will fire.** 013 §6 lists "the Xenia shared-memory work lands and the corpus is no longer one person's." The other three are not met: `context/`, `memory/` and `skills/` hold 78 Markdown files against the ~150 guess, `context/index.md` is still hand-written, and no span-turn measurement exists. So the librarian's trigger is Xenia's X11, not corpus size. (The operator waived §6 on 2026-10-24, so this is information, not a gate.) Decision the operator may want: build the librarian after X11, when there is a corpus that is not one person's; 011 already puts it in Xenia Phase 3.
2. **The index gains a zone.** Xenia records enter `state.db` as a derived zone (X6). Tier is a pure function recomputed on every sync, so vectors must be keyed by content hash and tier carried in `source_type` / the `trusted` column, never baked into the vector row. Otherwise every roster change re-embeds the store. `kb.rs` already separates the two (`trusted` and `scope` skip rows; the embedding does not depend on them).
3. **Two tag systems must not merge.** 013 §2 has the librarian merge near-duplicate tags and write `context/taxonomy.md`. In Xenia, `tags` are not labels: they decide which steward may endorse or tombstone a record (011 §2.3). A librarian that "normalizes" tags on org records would change authority, and it cannot anyway, because records are signed. Rule: the local taxonomy may hold **aliases used at search time** for Xenia tags; it never rewrites a signed record; a change to the vocabulary of `steward_areas` is a roster epoch, signed by admins.
4. **The `summary` field disagrees.** 013 §5 proposes an optional local `summary` of at most 160 characters; 012 has a required `summary` of at most 500. Decision for the operator when 013 §5 is amended: keep the local field at 160 and map a Xenia record's local `summary` to a deterministic truncation, with the full 500 in the body of the cache entry. (013 §5 item 4 already asked for this coordination.)
5. **A third category beside scout and librarian.** 013 §3 splits external (scout) from internal (librarian). An endorsed org record is neither: it is internal to the org and external to the install, at most L2. Answers that mention it must show the tier and the store. This is a wording fix in 013 §3 when the role is built.
6. **A cheap win now, no role needed.** The publish preview (X7) lists the existing records most similar to the draft using the hybrid search. This is deterministic, local, and is the first piece of the librarian's dedupe duty done by plain code.
7. **Taint.** A librarian span that reads L2 Xenia summaries has its ceiling lowered to L2, which `specs/001` §5.2 allows to write; one that quarantine-reads L1 does not. The librarian should read pointer indexes (path, heading, summary), not bodies, which keeps its ceiling where it was.

### 5.2 Federation, spec 007

1. **007-A1 is already in the 007 table as "proposed".** X0 changes it to accepted. L2 now has two routes: the original (pinned teammate DID plus commit and CI attestation) and a steward endorsement of a Xenia `memory` record. The first has no implementation and no verifier; the second does, and is the only L2 that will exist for a while.
2. **Xenia is the first implementation of 007 §2.1's identity.** The DID, fingerprint, strict verification and key storage built in X1 are the code Plane 1's Agent Card and Plane 2's `DelphiCap` would reuse, so the 60+ h estimate for Planes 1–2 shrinks by the identity work (my guess: 8–10 h). **Recommendation: separate keys by purpose.** Xenia's key signs content a human approved; a peer-transport key authenticates a daemon. One key doing both lets a transport-signing bug become a content-signing bug. Domain separation (`xenia/1`) already protects the bytes; separate keys protect the custody. This is a decision for the operator and an amendment to 007 §2.1 when Plane 1 is specified for building.
3. **The roster could become Plane 1's peer allowlist.** 007 §2.1 asks the operator to paste standing grants per peer DID. With a roster, "who is a peer" is a signed, revocable, per-person fact. This is a possible simplification, not a plan: Plane 1 peers need not be Xenia members. Park it until Plane 1 is scheduled.
4. **Plane 3 (`delphi sync`) overlaps and is weaker.** 007 §4 item 4 merges `context/domains/**` and `specs/**` with ordinary Git semantics and stamps them `federated_verified`. Nothing verifies a signature there, so a teammate's unsigned file gets the same tier that Xenia only gives to a signed, endorsed, fresh record. Once Xenia exists that is the inconsistent door. **Amendment 007-A2 (ratified and applied 2026-10-25):** Plane 3 keeps only the rule-file proposals of §4 items 1–3, which all end in operator ratification anyway; non-prompt shared knowledge moves to Xenia; files that Plane 3 still stamps from plain git are stamped `federated_peer` (L1), not `federated_verified`. This shrinks `delphi sync` (the ~30 h rough estimate; my guess is about half) and keeps one definition of L2.
5. **Plane 2 stays out of Xenia.** 012 §4 rejects `delphi://` pointers and the reserved `xenia://cap/` capability URIs (D-32), and 011 §6.2 forbids treating "our own" locators as trusted. Plane 2 must not become the Xenia pointer resolver of 011 §11.2; that resolver needs its own SSRF-guarded fetcher with a pointer content tier of L0.
6. **The case for Planes 1–2 gets narrower.** Sharing knowledge, the main driver for federation, is now met by Xenia without live transport (that is O-5: Xenia first). What Planes 1–2 would still add is live delegation of tasks and ad hoc line-scoped slices. `delphi needs federation` ("a second operator or machine") should stay the gate; its evidence will be clearer after X11.
7. **Taint ceiling interplay.** 007 §3.1 clamps a payload to `min(payload, PeerTrustCeiling)`. Xenia's 011 §5.1 clamps to `min(class tier, source_ceiling)` and caps at L2. If Plane 1 ever carries a Xenia record, the lower of the two applies; nothing in either spec lets a peer raise a Xenia tier.

### 5.3 One URI scheme: `xenia://` (D-32, 2026-10-29)

The operator decided that the protocol has one URI scheme, named for the protocol. Record references became `xenia://<kind>/<id>[@rev]` (the bare form is gone; no records are deployed). Plane 2's deferred capability URI became the reserved `xenia://cap/...`; `cap` is never a record kind and 5.2 item 5 still holds (same scheme, separate resolver, tier and authority). `delphi://` is rejected everywhere with "use xenia://". `delphi-bundle://` stays: it is spec 025's local MCP resource scheme. Touched: `pointer.rs` and its tests, the bundle frontmatter check, `schemas/xenia-record.schema.json`, specs 007, 011, 012, OVERVIEW, SPEC, `context/`. Spec 007 is under federation review, so the Plane 2 name may be revisited.
