## Round 1 stances (blind)

### architect

> OPTION: Delegate drafting to Claude, ground it, review
> 
> The README is a user-facing document, so under the charter it counts as an artifact, not software. It needs no spec, and the Writer role owns it. The real question is how to make it accurate, not who types it. I'd split the work this way.
> 
> 1. **Use a model to draft, but not from memory.** Whether the model is me (Architect) or Claude through Delphi's Writer role matters less than what it reads. Give the drafter the real inputs: SPEC.md, the specs/*.md files, GOVERNANCE.md, the CLI's actual `--help` output, and the config schema. A README written from those is reliable. One written from the model's general sense of "what a system like this does" will confidently describe features that don't exist.
> 
> 2. **Pick the role by task, not by prestige.** Writer is the natural author because its counterweight is "truth before harmony": it should never document unbuilt features as working. Architect can supply a structure outline (audience, install, quickstart, concepts, limits). Then Writer fills it in. That also lets the operator ask for a different model family as the reviewer, which fits H-008. The author's family shouldn't be the only one checking its own work.
> 
> 3. **Add a verification pass.** Every command, flag and path in the README should be checked against the code or the CLI output. Where possible, make that check deterministic. For example, extract the code blocks and run them in a sandbox, or grep each flag against the source. Anything that can't be verified gets cut or marked "planned".
> 
> 4. **Keep it regenerable.** If "writes its own readme" means it should stay current, put a short generation recipe in the repo (inputs, prompt, checks). Regeneration then produces a diff for the operator to review. Don't have it silently overwrite the file.
> 
> 5. **Operator approves the final text.** The README is the public face of the project, and the operator should read it before it ships.
> 
> In short, the choice of "me or Claude" is mostly a false fork. Use a model for drafting, ground it in the real files, and have a different model or a script verify it.
> 
> **Risks**
> - **Hallucinated features.** The drafter may describe planned or imagined behavior as shipped. This is the biggest risk.
> - **Staleness.** A one-off README drifts from the code unless regeneration is wired in.
> - **Self-review blind spot.** If the same family drafts and checks the README, it can miss its own errors.
> - **Leaked paths or secrets.** Local user paths or config values can leak into the text (§5.3).
> - **Over-automation.** Auto-regeneration that lands without review turns inaccurate prose into the project's official statement.

### red-team

> OPTION: Delphi writer with red-team review
> 
> Standalone models like Claude operating in an unconstrained single-agent loop suffer from classic single-agent failure modes when generating project documentation: sycophancy, narrative smoothing, and aspirational hallucination. A standalone agent will readily document intended designs, non-existent CLI flags, unmerged features, or idealized happy paths as functioning reality to produce a polished narrative. It lacks an internal counterweight to verify claims against actual source code or flag security boundaries.
> 
> Delphi should generate the README because Delphi enforces structural counterweights and role separation:
> 1. **Truth Before Harmony:** The `writer` role operates under a strict governance mandate to never document unbuilt features as working and to preserve adversarial caveats.
> 2. **Grounding in Code:** Delphi leverages `investigator` and `scout` to extract exact, verified code pointers, CLI schemas, and existing test assertions rather than guessing from conversational context.
> 3. **Adversarial Audit:** The draft must survive `red-team` review, ensuring every documented command, setup step, and security assumption is tested for failure scenarios, permission boundaries, and accurate operational caveats before presentation to the operator.
> 
> Using Claude alone guarantees high stylistic polish with zero verification; using Delphi guarantees an accurate, falsifiable operational artifact.
> 
> Risks:
> - **Ungrounded drafting:** If `writer` drafts from high-level conversational context rather than direct inspection of source code and test outputs, it can replicate the same hallucinations as a standalone model.
> - **Accidental complexity and bloat:** Delphi's multi-role rigor can produce an overly dense, spec-laden manual instead of a concise, accessible README tailored to outside developers.
> - **Snippet drift:** Example commands and configuration blocks will rot unless coupled with deterministic verification scripts in CI.

### strategist

> OPTION: Delphi drafts it, Claude reviews
> 
> Reasoning: The question has a false either/or. Delphi's agents (Writer, with Scout/Investigator for facts) are the system, so having Delphi write its own README is the point of the exercise, and it is the better test of whether the system works. But the Writer's known blind spot is polish over truth, and a self-description is where that hurts most: the system will tend to describe what the specs intend rather than what is built. A different model family, such as Claude via the host, makes a good independent critic. That also fits [H-007] and [H-008]: author and critic on different families.
> 
> Sequencing I'd recommend:
> 1. Scope the README first. Name the audience (new operator vs. contributor), a short section list, and a length cap. This is the main defense against scope creep.
> 2. Delphi's Writer drafts from pointers to the real specs, GOVERNANCE.md and the code, not from memory. It marks each capability as "built" or "planned".
> 3. The host (Claude) does a truth-pass. It checks every claim against the repo, such as commands, flags and features. Better still, it runs the quickstart commands as written.
> 4. The operator approves the final text. A README is an artifact or markdown note, so no spec is needed under §1.3. If it sits in a governed path, it goes through ratification.
> 
> If you must pick one, pick Delphi for the draft. The costs of that choice are small and are caught by the review step. Picking Claude alone gives a cleaner first draft, but it skips the self-documentation test and gives you no check on what Delphi says about itself.
> 
> Risks:
> - Self-description drifts from reality (Writer's polish-over-truth, and unbuilt features documented as working).
> - Single-family homogeneity if Delphi's Writer and the reviewer share a lineage. Label the verdict if so.
> - Scope creep into a full manual instead of a README.
> - Self-referential taint. If the Writer ingests its own earlier output, errors compound. Source claims from specs and code only.
> - The review loop never ends. Cap it at one revision round.

## Verdict

**No deterministic escalation:** no unresolved P0 and the Round 2 recommendations agree. The decision is the operator's.

> The Council recommends a hybrid. Delphi's Writer drafts the README, and a different model family checks it. It is not a choice between "me" and "Claude".
> 
> A README is an artifact, so it needs no spec. Writer is the natural author because its charter duty is to never document unbuilt features as working. Having the system describe itself also tests whether it works. The draft must come from real inputs: SPEC.md, `specs/*.md`, GOVERNANCE.md, actual CLI `--help` output and the config schema. It must not come from a model's general sense of what such a system does. Each capability should be marked built or planned.
> 
> All three seats agreed on these points:
> - Fix the audience, section list and length cap before drafting.
> - Draft only from specs and code, never from the Writer's own earlier output.
> - Have a different family review the draft, per H-007 and H-008, and label the verdict homogeneous if only one family is available.
> - Cut anything that can't be verified, or mark it planned.
> - Cap review at one revision round.
> - The operator reads and approves the final text, and local paths and secrets are scrubbed (§5.3).
> 
> Disagreements:
> - **Regeneration recipe and CI snippet checks:** Architect wanted them. Strategist called them over-engineering for a first README. I side with Strategist and defer them.
> - **Running quickstart commands:** Strategist proposed running them on the host. Red-Team objected, and I side with Red-Team: they run only inside the OS sandbox, or are checked by grepping flags against source.
> - **Host review text:** Red-Team also objected to feeding it straight back into Delphi context. It should arrive as untrusted data and be applied only through operator-approved edits.
> 
> Red-Team did not concur, and its open P1 items go to the Minority Report as recorded.
