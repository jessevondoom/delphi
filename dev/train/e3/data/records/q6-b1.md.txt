### architect

> OPTION: Approve with amendments; defer launcher
> 
> I could not read spec 071 or any of the pointer files. They were unavailable or denied, so this ruling comes from the question's description alone and is not validated against the text.
> 
> **D-1 (one repo, generated `ecosystem/` plus a root `.claude-plugin/marketplace.json`): approve.**
> - Generating the folder from the existing `mcp_hosts.rs` snippet generator keeps a single source of truth.
> - A drift test in CI is the needed enforcement (§5.6): the generated output must match what is checked in, or the build fails.
> - Amendment: the marketplace manifest and plugin contents are derived artifacts. Hand edits must fail the drift test.
> - Amendment: the manifest must pin the plugin version to the Delphi release, so a marketplace update can't silently change behavior.
> 
> **D-2 (operator-run `delphi mcp --install` editing host configs outside the workspace): approve only with amendments.**
> - It touches files outside the workspace, so §5.4 applies. It needs an explicit, previewed diff and a synchronous operator confirmation. It must never run from an agent or MCP call; it must be a human-invoked CLI only, and it must refuse when stdin is not a TTY unless an explicit `--yes` is given.
> - It should be idempotent and make a timestamped backup before it edits.
> - It should write only the Delphi server entry, with a fixed command path and no env secrets (§5.3). It must never overwrite an existing entry of the same name that it didn't create. It should have an `--uninstall`.
> - It must use atomic writes and parse the config rather than splice text. It must keep file permissions and refuse symlink targets that leave the home directory.
> - The entry must not widen authority. It should point at the same read-only or scoped MCP surface as 062, not add tools.
> 
> **D-3 (a launcher script inside a plugin): defer.**
> - It is executable content that the host runs outside Delphi's sandbox (§5.5). It is also a supply-chain vector, because a marketplace update can swap the script.
> - A plain MCP server declaration with `command: delphi` is enough, so the script isn't needed.
> - If the script is ever allowed, it should be a few lines, hash-pinned, and covered by the drift test.
> 
> **Q-1..Q-5:** I can't judge them without the text. I would treat as blocking any question about what the plugin can reach, about where the installer writes, or about trust in the marketplace source. Anything cosmetic or about naming can follow later.
> 
> **Risks**
> - The installer widens the authority of a host process. A compromised or prompt-injected host could trigger it, so the human-only gate must be enforced in code.
> - A plugin update path can change behavior after the operator approved it.
> - A host config that already points at a different `delphi` binary could be hijacked or shadowed.
> - Content from an untrusted marketplace feeds into the host's context, so it should be treated as tainted.

### red-team

> OPTION: Approve E1-E2; defer installer and launcher
> 
> Draft spec 071 introduces authority-widening capabilities that breach host isolation boundaries. While static marketplace cataloging and schema generation (E1–E2) present minimal risk, the automated external installer (E3) and executable launcher scripts (E5) introduce critical attack surfaces governed by Charter §5.1, §5.4, and §5.5.
> 
> Specific rulings on decisions:
> - **D-1 (Approve):** A single repository containing a drift-tested `ecosystem/` directory and root `.claude-plugin/marketplace.json` is acceptable. Deterministic CI drift testing verifies manifest integrity without expanding execution authority.
> - **D-2 (Defer E3):** Having `delphi mcp --install` edit host configuration files outside the workspace violates least privilege (§5.1) and state-mutation safeguards (§5.4). Even operator-invoked tools must not silently modify global user state without atomic transactions, explicit interactive diffs, and guaranteed rollbacks.
> - **D-3 (Reject/Defer E5):** Allowing executable launcher scripts within plugins violates the core invariant that worktrees and external plugins are not sandboxes (§5.5). Shell wrappers invite unvalidated command execution and argument injection outside Delphi's deterministic runtime. Plugin declarations must remain strictly declarative, specifying fixed argument lists against pre-verified binaries.
> 
> On Q-1 through Q-5: Q-1 (unbounded host file mutation) and Q-5 (launcher script privilege containment) are blocking architectural flaws. They introduce ambient authority widening and must block full approval until remediated.
> 
> Risks and Falsifiable Critiques:
> 
> 1. **Host Configuration Corruption and Hijacking (D-2 / E3)**
>    - *Failure Scenario:* `delphi mcp --install` mutates `~/.claude.json` or host configs without file locking. A race condition or ill-formed JSON write clobbers existing host agent settings, or an untrusted local workspace tricks the installer into repointing global host MCP definitions to a malicious binary.
>    - *Remediation:* Defer E3. Require atomic temp-file replacement, pre-write schema validation, mandatory `.bak` creation, explicit console diff confirmation before disk commit, and a default `--dry-run` flag.
> 
> 2. **Arbitrary Code Execution via Plugin Launcher Scripts (D-3 / E5)**
>    - *Failure Scenario:* A plugin provides a `launcher.sh` script that executes in the host environment without OS sandbox containment. An untrusted plugin update injects shell metacharacters into environment variables, yielding arbitrary code execution on the operator's machine.
>    - *Remediation:* Defer and strip E5. Prohibit executable scripts in plugin packages. Enforce declarative JSON configurations that execute only allowlisted, statically resolved binary targets.

### strategist

> OPTION: Approve E1-E2; gate installer, launcher
> 
> I could not read spec 071, spec 062 or mcp_hosts.rs. All three came back not found or denied. This stance rests on the question as framed, and I have not audited the text. Treat it as a scope and sequencing view only.
> 
> **D-1 (one repo, generated and drift-tested `ecosystem/` plus root `marketplace.json`): approve.** It is the smallest change that delivers the marketplace value. A drift test makes the generated folder a derived artifact, which matches the Tier 3 rule. Condition: the generator must be the only writer, and CI must fail on drift.
> 
> **D-2 (operator-run `delphi mcp --install` editing host config outside the workspace): defer.** This is the largest scope jump in the spec. It is the first time Delphi would write outside its workspace, into files that govern what another tool executes. Governance §5.4 and §5.5 treat system state outside the workspace as an approval-gated, Red-tier action. §6.2's safeguards may be adequate, but I cannot confirm that. The install flow also makes the "durable enablement" problem (Q-5 in spec 062) harder to avoid, so it should get its own spec and its own Red-Team pass rather than ride along with a docs and marketplace change.
> 
> **D-3 (small launcher script in a plugin): defer, or decline for now.** A plugin that ships an executable runs unsandboxed on the user's machine. It is the same trust class as the executable files §5.5 flags at merge. If a static MCP config entry can do the job, the launcher is gold-plating (REV-ARCH-01). Approve it only if someone shows a concrete case that static config cannot cover.
> 
> **Q-1..Q-5:** I haven't seen them. Any question that touches D-2 or D-3 should block approval of those parts and not E1-E2. Open questions on E1-E2 should be resolved before approval, not left as follow-ups.
> 
> **Authority-widening checks to require in the amended spec:**
> - The installer is operator-invoked only, and no agent can trigger it.
> - Show a diff and require explicit confirmation before any write.
> - Make a backup, support an idempotent uninstall, and restrict writes to a named allow-list of paths.
> - Never write secrets or tokens into host config.
> - The launcher is pinned by hash and has no network fetch.
> - Plugin text is never treated as ratified configuration.
> 
> **Risks:**
> - Bundling E3 and E5 with E1-E2 puts the low-risk work behind the high-risk review.
> - Host config formats change without notice, so any installer needs ongoing maintenance.
> - A drift-tested folder can give false assurance if the test checks only structure and not content.
