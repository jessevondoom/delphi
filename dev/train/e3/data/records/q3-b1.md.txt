## Round 1 stances (blind)

### architect

> OPTION: Staged inbox tool plus auto-capture
> 
> **Reasoning (architect view):**
> 
> The root problem is that capture depends on agent discipline and operator effort. Option 4 (instructions only) is prose-only enforcement, which GOVERNANCE §5.6 treats as unenforced, and it fails silently. It also fixes nothing for MCP callers whose host agents don't read Delphi's role files. So it can't be the primary path.
> 
> The right design separates three concerns: **capture** (automatic, cheap), **trust** (computed by the daemon), and **promotion** (operator ratification).
> 
> 1. **A single inbox primitive in the daemon.** Add one MCP tool, `propose_kb_entry`, that is write-only into a quarantined `kb/inbox/` and does nothing else. It takes a title, a body, source pointers (URL or path with a content hash) and tags. It cannot write to `context/`, and it grants no read-back authority. This fits the "MCP is read-only" limit because the write is append-only staging, and the daemon assigns the taint label itself. The caller never declares it (§4.3). Anything that touched external or federated input gets the lowest tier. Internal-source research gets `internal_generated`, not `internal_empirical`.
> 
> 2. **Reuse, don't multiply.** Option 2 (stretching `record_session_summary` or `propose_note`) mixes lessons, summaries and research into one channel with different promotion rules. Keep those separate, but have all of them write the same inbox record schema. The simpler alternative is one tool, one schema.
> 
> 3. **Auto-capture as a daemon behavior, not a TUI feature.** Option 3 puts capture in the TUI only, so MCP sessions miss it. Instead, the daemon should stage any research-role output (Scout, Investigator) into the inbox at mission close. That hook is deterministic. Agents can still call the tool for ad hoc findings. The TUI and an `inbox` CLI then provide the one-key batch ratify, plus per-item reject.
> 
> 4. **Provenance.** Every record carries mission id, role, model family, source list with hashes, and daemon-computed taint. A validated promotion runs `validate_claims` first; failures stay marked `not validated`, which is acceptable, since most items may remain pending.
> 
> **Risks:**
> - Inbox flooding and operator fatigue: needs dedupe by source hash, a size cap and expiry.
> - Batch ratify becomes rubber-stamping, which launders low-trust content. Mitigate by showing taint and blocking one-key promotion of anything below `internal_empirical` into always-loaded files (§4.3).
> - Prompt injection through staged content: it must be inert data, never loaded into prompts until ratified.
> - Auto-capture of sensitive internal material: it needs a secret scrub (§5.3) before staging.
> - The MCP write surface widens. Rate-limit it and make it append-only.

### red-team

> OPTION: Add dedicated propose_research staging tool
> 
> ### Reasoning
> 
> From an adversarial and anti-poisoning perspective, introducing an explicit, typed MCP staging tool (`propose_research` or `propose_kb_entry`) is the only option that preserves Information Flow Control (IFC) and architectural boundaries:
> 
> 1. **Rejection of TUI auto-capture with "one-key batch ratify":** Auto-capturing unbounded output combined with single-click bulk ratification is an acute security hazard. It induces extreme operator verification fatigue, guaranteeing sycophantic rubber-stamping. This directly exposes Delphi's memory to prompt-injection and poisoning attacks (AgentPoison, MemoryGraft) by allowing unscrubbed external artifacts into the central knowledge base under operator authority.
> 2. **Rejection of prompt-only instructions:** Enforcing capture via agent descriptions or system prompts violates Governance §5.6 ("Enforcement Is Code, Not Prose"). External host agents (such as Claude Code) will hallucinate formatting, drop provenance metadata, or skip staging entirely when under context pressure.
> 3. **Rejection of overloaded summary/note tools:** Conflating factual research staging with operational session logs or Rule of 25 coaching notes degrades schema integrity and pollutes distinct retrieval scopes.
> 4. **Deterministic ingress and taint enforcement:** A dedicated staging tool provides a strict schema boundary. The daemon can deterministically record provenance (session ID, caller identity, source URLs, span lineage) and quarantine the payload into an isolated inbox at the lowest trust tier (`external_untrusted` or `internal_generated` at L0). It guarantees that no staged finding enters indexed, always-loaded context or higher lattice tiers without explicit, individual validation or operator ratification (Governance §4.3).
> 
> ### Risks
> 
> 1. **Denial of Service via Inbox Flooding:** An unconstrained or loop-bound host agent could flood the staging inbox with hundreds of redundant or verbose entries, exhausting the operator's review capacity and inducing rubber-stamp ratification. *Remediation: Enforce strict rate limits, size caps, and deduplication on staged submissions.*
> 2. **Taint Smuggling and Source Spoofing:** A compromised or confused caller might label untrusted third-party scrape data as "internal sources" in prose. *Remediation: Taint must be computed deterministically by the daemon based on ingress channel boundaries, never self-reported by the caller.*
> 3. **Premature Retrieval Leakage:** If the KB inbox is readable by default `kb_search` routines before validation, unvalidated L0 material will pollute downstream agent contexts. *Remediation: Inbox items must be strictly partitioned and excluded from default knowledge base indexes until formally ratified or corroborated.*

### strategist

> OPTION: Daemon-side KB inbox, auto-captured
> 
> Reasoning (scope and ROI view):
> 
> The goal is "research always fills the KB with minimal friction." That is a reliability requirement. Options that depend on agent compliance (4, and largely 2) fail it by construction: prose rules are the weakest enforcement (GOVERNANCE §5.6), and agents will forget, especially under context pressure. Governance's own "two strikes → script" principle points the same way: don't rely on prompts.
> 
> So the capture mechanism should be deterministic and daemon-side, not agent-initiated. The daemon already sees research tool calls (fetches, kb_search reads, request_research outputs). It can write an inbox record automatically, with provenance it computes itself: sources, timestamps, the role, the mission, and taint computed from the lowest-trust input. Agents never declare trust, which fits §4.3. This is option 3's capture half, with option 1's staging shape.
> 
> Sequence by phase:
> 1. Phase 1 (smallest standalone value): the daemon auto-stages research outputs into an L0 inbox, marked "not validated," with computed provenance. No new authority is granted. MCP stays read-only for ratification, and staging is a daemon write, not an agent write.
> 2. Phase 2: a batch review in the TUI (one-key accept, reject or defer per group, grouped by mission/topic). Ratification stays with the operator. Items from untrusted sources route through the existing validate_claims/ratify_fact path rather than being bulk-accepted.
> 3. Phase 3, optional: an MCP propose_kb_entry tool for agents to add curated notes. It's additive, and it also lands in the inbox, never past it.
> 
> Explicitly out of scope: any auto-promotion past L0, and any change to the "MCP read-only" rule. Pending entries are acceptable and should be the default, so friction falls on review, not on capture.
> 
> Risks:
> - Inbox flooding: auto-capture of everything buries the valuable material. Mitigate with dedupe, grouping by mission, and expiry of unreviewed items.
> - Taint laundering: a one-key batch ratify could lift external-source claims to a trusted tier. Batch accept should keep the computed tier or require per-item validation below `internal_empirical`.
> - Secrets or local paths in captured text (§5.3): scrub before staging.
> - Prompt injection: captured text is data and must never be loaded as instructions.
> - Defining what counts as a "research output" is fuzzy, and it could lead to scope creep. Start with a narrow, explicit definition.
> - An MCP-originated session may not pass through the TUI. The daemon capture must therefore cover both paths.

> The Council did not reach consensus and escalates to the operator.
> 
> **Where the seats agreed.** Prompt-only instructions (option 4) are unenforced under GOVERNANCE §5.6, and they fail silently for host agents that never read Delphi's role files. Taint must be computed by the daemon and never declared by the caller. The inbox must be quarantined from default `kb_search` and from prompt loading until ratified. Staged text is inert data. Secrets and local paths must be scrubbed before staging. The inbox needs dedupe by source hash, size caps, rate limits and expiry. Overloading `record_session_summary` or `propose_note` (option 2) mixes different promotion rules, so a shared record schema is better. Nothing below `internal_empirical` goes into always-loaded files without per-item validation.
> 
> **Where they diverged.**
> - *Capture mechanism.* Architect and Strategist want the daemon to auto-stage research outputs, so that TUI and MCP sessions are both covered. Red-Team distrusts heuristic auto-capture. It fears the capture will include debris and injected content. It also holds that host agents need an explicit, typed `propose_kb_entry` tool.
> - *Sequencing.* Strategist ships daemon auto-stage alone first and defers the MCP tool and the batch UI. Architect keeps the tool as an additive path.
> - *Batch ratify.* Red-Team's P0 is that one-key batch ratify causes rubber-stamping and launders low-trust content. The other seats would allow it only if it keeps the computed tier.
