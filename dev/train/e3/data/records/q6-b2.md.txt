### architect

> OPTION: Approve with amendments; defer launcher
> 
> I could not read the draft. Spec 071, spec 062, `mcp_hosts.rs` and the guide all came back unreadable to me. This stance rests on the question as framed and not on the text, so I'm not validating any claim about what the spec says.
> 
> **D-1 (one repo, generated `ecosystem/` folder, root `.claude-plugin/marketplace.json`): approve.**
> - It is the simpler design. The generated folder is a derived artifact (Tier 3), so the generator must stay the single source of truth.
> - The drift test has to run in CI as a hard failure.
> - Generated files should carry a "generated, do not edit" header.
> - The marketplace entries should pin to a ref or commit, so a later push cannot silently change what an operator has already added.
> 
> **D-2 (operator-run `delphi mcp --install` editing host config outside the workspace): approve only with safeguards.**
> - It crosses §5.4 (changing system state outside the workspace). The operator running the command is the approval, but only if the command is never reachable by an agent or by an MCP tool call.
> - Required safeguards:
>   - Print the exact diff and require interactive confirmation. A `--yes` flag must not exist, or must be refused when stdin is not a TTY.
>   - Back up the file before editing, write atomically, and make the edit idempotent.
>   - Only add or update the one `delphi` entry. Never touch other servers.
>   - Provide `--uninstall` and a `--dry-run`.
>   - Refuse to follow symlinks outside the host's config directory.
>   - Write only an absolute path to the delphi binary, and no secrets or tokens into the host config.
>   - Install the server with the narrowest scope. The host-facing MCP surface should not gain tools merely because it is now persistent.
> - Persistence is the authority-widening point. Once installed, every session of that host can reach Delphi without a per-session opt-in. Spec 062's tool allow-list and taint rules (host input is `federated_peer` or lower) must therefore still apply unchanged, and the spec should say so explicitly.
> 
> **D-3 (launcher script in a plugin): reject for now.**
> - A plugin that ships an executable runs unsandboxed code on every host start, and it arrives through a supply-chain path (marketplace update). That is the largest risk in the draft.
> - If a launcher is needed at all, it should be a static, a few-line script with no network access and no `eval`. Its hash should be checked by the drift test, and it should be deferred until the E1–E2 and installer experience shows the need.
> 
> **Q-1..Q-5:** I haven't seen them. Any question that touches the installer's write scope, the launcher, or the trust level of host input blocks approval. Cosmetic or naming questions do not.
> 
> **Risks**
> - Persistent enablement quietly widens what a host can ask Delphi to do.
> - Marketplace updates can change plugin content after the operator has approved it.
> - Edits to config outside the workspace are hard to reverse without a backup.
> - Hosts differ in their config formats, so a single code path may corrupt one of them.

### red-team

> OPTION: Approve with amendments
> 
> **Amendments Required:**
> 1. **D-1 (Approve):** The single-repo structure with a drift-tested `ecosystem/` folder and root `.claude-plugin/marketplace.json` is acceptable; CI drift tests must deterministically block unverified manifest updates.
> 2. **D-2 (Amend/Constrain E3):** Prohibit `delphi mcp --install` from silently or automatically mutating host configuration files outside the workspace (e.g., `~/.claude.json`). Downgrade E3 to output verified configuration snippets/diffs by default. Direct file editing must be an opt-in flag requiring interactive operator confirmation, strict schema validation, atomic writes, and pre-image backups.
> 3. **D-3 (Reject E5):** Reject custom launcher scripts inside plugin bundles. Execution must rely strictly on declarative binary invocations (`delphi serve`) to prevent unvetted code execution outside the OS sandbox.
> 4. **Q-1..Q-5:** Any open question involving ambient credential harvesting, unsandboxed execution, or unauthenticated remote endpoints blocks approval.
> 
> **Reasoning:**
> From Red-Team's adversarial perspective, Spec 071 introduces significant authority widening under the guise of developer ergonomics. While centralizing marketplace metadata (D-1) carries minimal operational risk when protected by deterministic CI drift checks, D-2 and D-3 breach core safety boundaries established in [GOVERNANCE.md](GOVERNANCE.md) (§5.1, §5.4, §5.5).
> 
> Permitting Delphi tools to rewrite configuration files across the host user profile creates a cross-tool privilege escalation and tampering vector. A corrupted write, symlink attack, or malformed JSON payload could brick external agent configurations or inject malicious tool definitions into the host environment. Restricting the installer to generate validated diffs and configuration snippets respects operator sovereignty and avoids mutating system state outside the workspace.
> 
> Allowing arbitrary executable launcher scripts within plugins (D-3) creates an unverified execution vector. Shipped scripts bypass sandbox auditing, complicate supply-chain provenance, and invite persistence or injection attacks. Host invocations must remain strictly declarative, pointing directly to ratified binary entrypoints.
> 
> **Risks:**
> - **Host Config Corruption & Hijacking:** Direct host file mutation risks race conditions, syntax corruption, symlink traversal, or injection of unauthorized flags into host agent tooling.
> - **Supply-Chain Remote Execution:** Bundled launcher scripts offer a direct mechanism for executing unmonitored commands outside runtime sandbox protections.
> - **Erosion of Least Privilege:** Automating cross-boundary tool installation conditions operators to accept ambient external modifications without rigorous line-by-line inspection.

### strategist

> OPTION: Approve E1-E2; defer installer, launcher
> 
> I could not read spec 071, spec 062 or the other pointers. All four came back unreadable or denied. This stance rests on the question as framed and is not validated against the draft text.
> 
> **Reasoning.**
> 
> - **D-1 (one repo, generated `ecosystem/` plus root `marketplace.json`): approve.** It is the smallest step that delivers standalone value: discoverability. Drift-testing the generated folder against `mcp_hosts.rs` keeps one source of truth. The scope condition is that the folder stays declarative, meaning manifests and snippets only. It must not grow into a second product.
> 
> - **D-2 (`delphi mcp --install` editing host config outside the workspace): defer.** This is the largest authority widening in the draft. It moves Delphi from "prints a snippet the operator pastes" to "writes into other tools' config". Those files can run commands, since an MCP entry is an executable launch line. The §6.2 safeguards may be sound, but the installer is not needed to ship E1-E2. It also has a much bigger test surface, because every host has a different config format and path. Its value is convenience, not capability. Treat it as a separate spec increment with its own Red-Team pass.
> 
> - **D-3 (launcher script inside a plugin): defer or reject for now.** A script shipped in a plugin is code that executes on the host, outside the sandbox and outside Delphi's approval gates. It is also the supply-chain surface (§5.5). If the launcher exists only to locate the binary, a documented `command: delphi` entry does the same job with no new executable artifact.
> 
> **Q-1..Q-5.** I cannot judge them without the text. As a rule, any open question that touches D-2 or D-3 should block those parts only, not E1-E2. Questions about the generated folder or the marketplace file should be settled before approval.
> 
> **Amendments if the Council proceeds with the full spec.**
> 
> - Installer is opt-in and operator-run only. An agent must never be able to call it.
> - Show a diff and require explicit confirmation before each write.
> - Back up the original file and write atomically.
> - Support `--dry-run` and an uninstall path.
> - Touch only Delphi's own key.
> - Install never widens the tools the MCP server exposes.
> - A plugin never auto-enables the server without an operator action.
> - Record each install in the log.
> 
> **Risks.**
> 
> - Scope creep from a docs-and-packaging change into a config-mutation tool.
> - A silent change to a host config file that the operator did not expect.
> - The launcher becoming an unreviewed execution path.
> - The generated folder drifting from `mcp_hosts.rs` if the drift test is weak.
> - Host config formats changing and breaking the installer later.
