Artifacts and Markdown are inert, so they don't need it. The log is a good counterweight. A daemon-written record of operator prompts replaces pre-approval with after-the-fact audit, and that suits low-risk output.
> 
> The amendments below follow from that split.
> 
> 1. **Closed allow-list, default is software.** Exempt only listed artifact types, and treat anything unlisted as software. Governance §1.3 already says this. Never exempt by extension alone. SVG and HTML can carry script, and a "document" can embed macros. The write tools should reject active content in exempt types, or reclassify the file as software.
> 2. **No laundering.** An artifact flow may not write executable, loaded or governed paths (`specs/`, `memory/`, `agents/`, `skills/`, `themes/`, CI files). Scaffolds must contain no executable content. A Markdown file that a loader or prompt consumes is a loaded type, so it is not exempt.
> 3. **Log integrity.** The daemon writes the log and agents cannot. It is append-only and the entry is made before the write, so a failed write still leaves a record. Each entry holds the verbatim operator prompt, a timestamp, the artifact path and a content hash. It holds no agent text, so injected content can't enter through the log. Secrets in prompts need a redaction rule that keeps the original verbatim in a sealed form. This tension should be stated openly.
> 4. **Boundary tie-break.** Where an item could be software or artifact, treat it as software.
> 
> **D-1 (log location):** daemon-only, under `local/` next to the proposals, per `specs/001` §2.2. It is not in `missions/` or `context/`, so agents can't read or write it. Add a per-mission index pointer for the operator.
> 
> **D-2 (external spec location):** `specs/external/<project>/`, as §1.3 already says. Keeping the spec in the Delphi workspace means the external repo can't approve its own spec.
> 
> **D-3 (log `(system)` entries):** log them in a separate, clearly typed field. `(system)` entries cover daemon-initiated writes, such as compaction and scaffolds. They must never be mixed into the operator-prompt stream, so the "operator prompt only" promise stays literally true. Any system entry should reference the operator prompt that caused it.
> 
> **Risks.**
> - Verbatim prompts may hold secrets or personal data, which conflicts with §5.3.
> - Allow-list drift: each new type needs a spec amendment, or people will bypass the list.
> - Log growth and a weak link from prompt to artifact when one prompt makes many edits.
> - Multi-turn edits may make the "operator prompt" ambiguous.

### red-team

> OPTION: Approve with mandatory security amendments
> 
> Exempting declarative artifacts (documents, slide decks, media) from formal specification unblocks operational throughput while keeping "No Spec, No Build" strictly enforced for Delphi core, scripts, and software tasks. However, loosening spec gates creates an immediate threat surface for payload smuggling, prompt-injection laundering, and audit erosion. Approval must be conditioned on resolving D-1, D-2, and D-3 with rigid invariants:
> 
> 1. **D-1 (Log Location):** The verbatim prompt log must be maintained exclusively by the daemon in an append-only, daemon-owned store (e.g., `.delphi/logs/artifact-prompts.log` or `.delphi/audit/`), entirely outside agent-writeable directory trees and isolated from Git worktree checkouts. If stored in regular workspace files, agents can truncate, overwrite, or forge log entries.
> 2. **D-2 (External Project Spec Location):** External project specs must reside in Delphi's central governed repository at `specs/external/<project>/`. Housing specs inside the external project checkout creates an untracked boundary where specs can be modified, deleted, or branched without Delphi's daemon enforcing the Tier 1/Tier 2 ratification lattice and Red-Team review gates.
> 3. **D-3 (Log System Entries):** System-generated synthetic prompts must never be mixed into the operator-prompt log without strict, unforgeable structural separation. A unified log creates an attack vector where subagent or synthetic turns launder automated actions as operator-directed requests. The log must either be strictly restricted to raw console inputs from the operator or enforce a cryptographically distinct `[SYSTEM:DISPATCH]` schema that cannot be emitted by agent tools.
> 
> Furthermore, the "closed allow-list" for exempt artifacts must be enforced deterministically by the daemon via content-sniffing and strict sanitization (e.g., stripping active JavaScript from HTML/SVG exports), ensuring that executable software or macros cannot be disguised as passive media.
> 
> ### Risks and Failure Scenarios
> 
> 1. **Active Payload Smuggling via Passive Artifacts:**
>    - *Failure Scenario:* An agent writes an exempt SVG, HTML report, or office file embedding executable script tags or macro vectors that execute upon operator opening.
>    - *Remediation:* Daemon-enforced MIME sniffing and mandatory AST stripping of executable script blocks from all exempt artifact types prior to disk write.
> 
> 2. **Governed Path Exfiltration / Scratch Escalation:**
>    - *Failure Scenario:* Agents exploit scratch or artifact exemptions to write functional code or configuration into governed directories (`skills/`, `memory/`, `specs/`).
>    - *Remediation:* Hard daemon path-level check: any write target inside governed prefixes triggers the software spec gate regardless of file extension.
> 
> 3. **Provenance Laundering via Synthetic Turns:**
>    - *Failure Scenario:* Ingress from an external MCP or untrusted peer triggers a synthetic system task that generates software-adjacent assets while citing the artifact exemption log as human authorization.
>    - *Remediation:* Require explicit operator token binding on every prompt log record, disallowing autonomous synthetic prompts from satisfying the artifact audit log.
