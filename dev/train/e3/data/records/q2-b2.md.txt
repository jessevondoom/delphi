> 
> 1. **RAG over the full knowledge base (highest priority, tools).** Retrieval has to be a typed, citable tool, because prose guidance can't make an agent retrieve well. I'd want these:
>    - A search tool that returns pointers (`path#Lx-Ly`), a validation label, a trust tier and a score, in line with [H-002].

A "consult role X" tool that returns an answer in that role's voice is the useful part. It must stay advisory and read-only, so it doesn't let a host bypass the governance rules. Because of H-001 and H-008, a Council-style ruling tool should route across model families, and the single-family case should be labeled `homogeneous`.
> 
> 3. **Research reporting and strategy (mostly tools, with existing artifact writers).** Needed here:
>    - A "request research" tool. It is already approval-gated, which is correct.
>    - Report and decision artifact outputs.
>    - A strategy flow that returns a structured handoff: objective, pointers, constraints, output contract.
> 
> 4. **Spec-driven development guidance (prompts and resources, with a few tools).** This goal is mostly guidance. I'd offer:
>    - MCP prompts for the flow: spec authoring, then the review loop (Strategist, Red-Team), then build.
>    - Resources for the spec template, including the mandatory `Simpler Alternative Considered` section.
>    - The "No Spec, No Build" rule exposed as a check. The `check` tool kinds (`spec`, `dag`, `brief`) are a good base.
>    - The implementation stays in Delphi. Hosts shouldn't be able to skip the gate.
> 
> **Priority:** (1) retrieval, (2) the spec-driven flow and its checks, (3) role expertise resources, (4) research and strategy workflows, (5) plugin guidance last. Guidance alone is the cheapest option but the weakest, because nothing enforces it ([GOVERNANCE §5.6](GOVERNANCE.md): enforcement is code, not prose).
> 
> **Risks**
> 
> - **Taint and prompt injection.** New read surfaces feed content from outside into the host's context. Retrieval results must carry computed taint, and the host must be told they are data.
> - **Authority leakage.** A host calling Delphi roles may treat advice as approval. Every new tool should be read-only or sit behind approval.
> - **Surface sprawl.** Too many tools degrade host tool selection. I'd cap the additions and prefer resources and prompts where they are enough.
> - **Unverified premise.** If specs 062 and 064 already define these tools, the real gap may be implementation, not design, and the answer would then be "finish building what is specced."

### red-team

> OPTION: Close gaps via new tools/resources
> 
> ### Reasoning
> The current MCP surface exposes raw utility tools (`kb_search`, `read_doc`, `check`, `write_report`) but fails to expose Delphi’s defining architectural strengths: role specialization, multi-agent dialectics, and taint-tracked spec lifecycles. Relying on "prompts and plugin guidance only" is security theater; client-side system prompts in a foreign host agent cannot enforce IFC boundaries, cannot emulate isolated role counterweights, and cannot deterministically govern execution against hallucinated spec bypasses. 
> 
> To bridge the four functional domains safely, Delphi requires targeted, schema-enforced MCP tools and resources rather than open-ended prompt guidance:
> 1. **Agent Specialties & Council Access:** The host agent cannot invoke canonical roles or convene diverse Council rounds. Exposing a structured consultation endpoint (e.g., `consult_role` or a bounded `run_council` tool) provides host access to orthogonal counterweights without leaking internal orchestration mechanics.
> 2. **Knowledge Retrieval & RAG:** `kb_search` and `recall_memory` provide text snippets but lack deterministic resource schemas (MCP resources for `context/`, `specs/`, and mission lineages). Without structured resource templates and citation verification, host agents ingest search fragments without provenance metadata.
> 3. **Spec-Driven Governance:** While `check` validates specs deterministically, the host lacks tools to query spec lifecycle state, stage spec amendments, or retrieve invariants. 
> 4. **Research & Strategy:** External research requests (`request_research`) stall at operator approval cards; the surface needs asynchronous polling or subscription primitives for long-running deliverables.
> 
> New tools must be narrow, read-biased, and strictly mediated by the daemon’s taint lattice (`specs/001` §5) to prevent external prompt injection from traversing into Delphi's core state.
> 
> ### Risks
> - **Confused Deputy & Taint Smuggling:** An external host running untrusted code can use Delphi’s MCP tools to query internal memory or write artifacts. Ingress from the host must be pinned to `external_untrusted` (L1), preventing indirect prompt injections from escalating to `internal_empirical` or modifying heuristics.
> - **Bypassing Council Counterweights:** Direct tool invocation risks an external agent querying only compliant personas, avoiding Red-Team scrutiny and producing sycophantic consensus.
> - **Resource Exhaustion via Unbounded Council/RAG Dispatch:** Without strict token budgets and concurrency limits on host-initiated Council runs or knowledge traversals, a host agent loop can starve daemon compute and exhaust rate limits.

### strategist

> OPTION: Close gaps via new tools, sparingly
> 
> **Caveat:** the specs I was pointed to (062, 064, 041, 003) could not be read in this session. I could not verify the MCP tool surface either. What follows is a scope and sequencing view, not a gap audit. It is not validated against the specs, and the host should check each point against them.
> 
> **Reasoning**
> 
> The three options are a false trichotomy. "Sufficient" is unlikely to hold across all four goals. "Prompts and plugin guidance only" fails where a capability is missing, but it is the right and cheapest answer where the capability already exists and the host just doesn't know how to chain it. I would split by goal:
> 
> 1. **RAG over the full knowledge base.** This is the only goal that is plausibly a real tool gap, and it should go first. Delphi has `kb_search`, which returns pointers, a status label and a short claim, so the question is whether the MCP endpoint exposes retrieval with the same trust semantics. The check is whether a host can get passages with a path, a tier and a validated/not-validated label, and can read the full file by pointer. If it can't, add a tool or resource for it. If it can, this goal needs guidance only. Either way, taint labels must reach the host, so that unvalidated material is never presented as fact.
> 
> 2. **Agent specialties and expertise.** Mostly a discoverability problem. Expose the role registry (spec 041) as a read-only resource, with each role's scope, blind spot and counterweight. Then ship prompts that route to roles. A new dispatch tool is not needed unless one is missing.
> 
> 3. **Research reporting and strategy.** Delphi already has `request_research` and the report, deck and chart writers. This is a prompt and workflow gap, solved with templates. Add no tools.
> 
> 4. **Spec-driven development guidance.** Mostly prompts. Encode "No Spec, No Build", the spec template and the review gates as MCP prompts. The one non-prompt piece is a `check`-style spec validation tool, which exists already.
> 
> **Priority:** (a) verify retrieval parity, (b) role registry resource, (c) prompt pack for goals 3 and 4, (d) new tools only for gaps that survive (a) to (c).
> 
> **Risks**
> - **Scope creep.** Every new MCP tool is permanent surface that has to be maintained, secured and documented, so the bar for adding one should be high.
> - **Governance.** Exposing write, dispatch or ratify paths to a host agent could bypass operator sovereignty (§1) and the taint gates (§4.3). The host is untrusted input, so keep the exposure read-mostly and Red-tier for anything outbound.
> - **Taint.** Host-supplied text is lower-trust, and anything written back from it must not be promoted.
> - **Unverified premise.** The host's claim that Delphi falls short is itself unproven until someone runs the use cases end to end.
