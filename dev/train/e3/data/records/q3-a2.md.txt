### architect

> OPTION: Keep propose_kb_entry; close the adoption gap
> 
> Reasoning (architect). The question names no pointers, so I read the repository directly. Option 1 is not a proposal. It is already the approved design and it is built. specs/068-research-capture-and-summary-pages.md (status: approved, 2026-11-02) sets up one inbox with two doors. The first is `propose_kb_entry`: MCP, staging only, an L0 entry with `inclusion: staged`, kept out of kb_search until the operator keeps it. The second is `delphi kb import`, plus TUI `/save` and drag-in, for the operator. The code matches the spec. crates/delphi-engine/src/mcp_host.rs exposes the tool. crates/delphi-engine/src/service.rs `host_kb_entry` redacts secrets, sets author and taint from the span, enforces caps, and returns `{staged, tier: L0, searchable: false, next: delphi kb review}`. crates/delphi/src/kb_review.rs does the batch keep-or-discard, and keeping grants inclusion but never validity. Research that Delphi's own scout does (`request_research`) already stages claims as `noted` (research_host.rs `stage_claim`). The authority limits in the question all hold. MCP writes go only to L0. The daemon overwrites author, taint, inclusion, validation and origin. Only the operator ratifies.
> 
> So the real gap is the word "always". Calling the tool is optional for the host agent. The fix is behavioral and measurable, not a new tool. The skills/delphi-attribution/SKILL.md file already tells hosts to call `propose_kb_entry` after research of their own. Make that instruction prominent in the role and skill packs (Option 4 as a complement, not a substitute). Then measure the capture rate with `kb review stats` before building anything else.
> 
> The other options:
> - Option 2: reject. Spec 068 §5 explicitly says "Not an overload of propose_note (lessons) or record_session_summary." Overloading would mix lessons and research under different trust rules.
> - Option 3: TUI auto-capture with one-key ratify. Auto-staging the last answer is acceptable, because `/save` already exists. But a single key that ratifies a whole unread batch defeats ratification and moves toward the forbidden watched-folder path ("none may be added that ratifies", §3).
> 
> Risks
> - A host agent can ignore the skill, so capture stays partial. Mitigation: measure, then consider a reminder in the tool result of research-type calls.
> - The inbox can flood and the operator stops reviewing. Rely on the existing caps and the expiry of untouched entries, and keep review batches small.
> - Internal-source research may carry secrets beyond what the scrubber catches.
> - Readers may treat unvalidated pages as authoritative. The label is mandatory in every renderer.
> - The question's framing implies a build that is not needed. Redoing spec 068 would duplicate stores and slices.

### red-team

> OPTION: Dedicated MCP tool with L0 staging
> 
> From an adversarial and information-flow control (IFC) perspective, a dedicated, strongly typed staging tool (`propose_kb_entry` / `propose_research`) is the only viable path. 
> 
> The alternative proposals fail critical security and governance invariants:
> - **TUI auto-capture with batch ratify** actively manufactures sycophancy and operator fatigue. "One-key batch ratification" transforms a vital security gate into a rubber stamp, opening the front door to memory poisoning (e.g., AgentPoison, MemoryGraft).
> - **Relying on agent instructions/skills** violates Governance §5.6 ("Enforcement is code, not prose"). Prose guidelines offer zero structural guarantees against prompt injection or silent omission.
> - **Overloading `propose_note` or session summaries** conflates role-private episodic memory and telemetry with shared knowledge base truth, corrupting schema validation and muddying provenance.
> 
> A dedicated tool establishes an explicit security boundary:
> 1. **Deterministic IFC enforcement:** The daemon, not the calling host, computes the taint lattice level (`source_type`) based on inputs and callers, tagging unvalidated external/host research strictly at L0 (`external_untrusted`).
> 2. **Strict isolation at rest:** Staged items must reside in an unindexed, quarantine staging inbox (e.g., `local/staging/kb/`). They must remain completely invisible to `kb_search` and model context compilations until formal operator ratification.
> 3. **Structured schemas:** Requiring discrete fields (explicit source pointers, specific claims, timestamp, caller ID) prevents raw conversational dumps and makes adversarial auditing possible.
> 
> ### Risks
> 1. **Batch Approval Fatigue:** Even with a staging inbox, accumulating large backlogs incentivizes operators to mass-ratify without scrutiny, neutralizing operator sovereignty.
> 2. **Quarantine Leakage:** If search tools or indexing routines inadvertently index the staging directory before ratification, untrusted payloads will poison active agent context and lower execution taint.
> 3. **Prompt Injection via Staged Metadata:** Malicious external content inside "summary" or "source" fields could exploit the operator's review interface or poison subsequent retrieval passes once approved.
> 4. **Staging Flooding / DoS:** An automated caller can flood the inbox with low-value or conflicting entries, exhausting storage or creating review paralysis. Staging must enforce per-session quotas.

### strategist

> OPTION: Narrow propose tool into L0 inbox
> 
> Reasoning:
> The goal is that research reliably reaches the KB, but nothing is validated on arrival. The write path should be as narrow as possible and should never raise trust.
> 
> Option 1 is the strongest. A dedicated propose tool has one job: write a candidate entry to an L0 inbox with required fields (claim, sources with URLs or internal references, retrieval time, calling seat and session, and the producing model). It cannot promote anything. Ratification stays with the operator. A dedicated tool keeps provenance clean and gives the operator one place to review.
> 
> Option 2 overloads record_session_summary. A summary is a session record, not a sourced claim, so mixing the two blurs provenance and makes review harder.
> 
> Option 3 is attractive for friction, but automatic capture of every research output would flood the inbox with unvetted text and would capture content the operator never meant to keep. Batch ratify belongs in the TUI as a review step, not as the capture step. I would take the ratify UI from option 3 and keep capture on option 1.
> 
> Option 4 costs nothing, but it is advisory. Agents can skip it, so it cannot make research "always" fill the KB. It is a useful complement, not a mechanism.
> 
> Recommended shape: the option-1 tool, plus the option-4 skill instruction so roles call it, plus a TUI batch-review screen. The KB entry is marked unvalidated and cannot be used as trusted context until the operator ratifies it.
> 
> Risks:
> 1. The MCP surface is read-only today. A propose tool is a write, so it widens authority. The spec must state that it writes only to L0 and cannot approve, promote, or change trust, and it must not let staged content raise its own trust.
> 2. Prompt injection through research text. Staged content can carry instructions. It must stay L0, be shown to the operator as data, and never be fed back as trusted instruction.
> 3. Source spoofing. The host can claim any source. The tool should record the caller and mark sources as claimed, not verified.
> 4. Inbox flooding and duplicates. Without dedupe and a rate limit, batch review becomes the new friction.
> 5. "Always" is not guaranteed by any option. Measure the share of research sessions that produce a staged entry before calling this solved.

> One-key batch ratify (Option 3) is rejected by all three seats. Spec 068 §3 also forbids any path that ratifies by itself. Option 2 is rejected by all three, and §5 already excludes overloading propose_note or record_session_summary.
> 
> The defects that remain concern "always", and none of them needs a new tool:
> (a) Calling the tool is optional for host agents. Make the instruction prominent in the attribution skill and the role packs, and add a reminder in the result of research-type calls (request_research, search_kb misses) suggesting that the host stage its findings.

## Verdict

**No deterministic escalation:** no unresolved P0 and the Round 2 recommendations agree. The decision is the operator's.

> The Council recommends Option 1, with changes, and finds that it largely exists already. Spec 068 (approved) defines propose_kb_entry: an MCP staging-only door that writes an L0 entry, not searchable until the operator keeps it, with daemon-set author, taint and validation, secret scrubbing, caps, dedupe and expiry. Delphi's own scout already stages claims the same way. The authority limits in the question therefore hold, and a new tool would duplicate it. Options 2 and 3 are rejected: spec 068 section 5 bars overloading propose_note or record_session_summary, and a one-key batch ratify defeats ratification. All three seats agreed on this mechanism and on rejecting those two options.
> 
> The real gap is the word "always": calling the tool is optional for a host. The seats split on the remedy. The architect and strategist would add a skill instruction (Option 4) plus a reminder in research-type tool results, and measure the capture rate before building more. The red-team, running on another model family, holds that prose cannot enforce capture (Governance 5.6) and wants a deterministic return hook, per-session quotas and dedupe, and daemon-bound caller and session metadata so sources cannot be spoofed. Its objections stand open and are copied in the Minority Report. Common ground: sources are shown as caller-claimed, never verified, and staged text stays L0 data. The end-to-end write path and kb_search invisibility were read from code, not run live.
