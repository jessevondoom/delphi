## Round 1 stances (blind)

### architect

> OPTION: Extend spec 068 import; agent summaries staged
> 
> No Pointers were given, so I checked the repo. Most of the operator path already exists. specs/068-research-capture-and-summary-pages.md and crates/delphi-engine/src/kb_import.rs import an operator's Markdown file into <ws>/local/summaries/ as kind: summary and write a bibliography sidecar (kind: bibliography). The daemon writes every trust field itself: source_type and taint are external_untrusted, origin operator_import, inclusion ratified, validation none, confidence low. It throws away the file's own frontmatter claims, and a test checks that a forged user_ratified is dropped. Ids are a title slug plus a hash. Re-imports produce new versions and keep the prior copy. Pages expire after 90 days and can be renewed. The workspace cap is 2000 pages. A page is index_worthy only if it links to a ratified, non-summary entry. Otherwise you need `kb search --all` to find it. So the council should extend this design, not build a second one.
> 
> My recommendation:
> 1. Operator path: keep `delphi kb import` as the single canonical act. A TUI drag-in should call the same daemon RPC, not run its own code. One operator step ratifies inclusion only. Validation stays none.
> 2. Agent path: propose_kb_entry gets kind=summary with a Markdown body. It goes to the L0 inbox under the existing caps, dedupe and scrubbing, with taint computed by the daemon. When the operator ratifies it, it runs through the same kb_import normalizer, with origin: agent_proposed and author set to the role. One normalizer gives one schema. The frontmatter fields (kind, sources, retrieved, author, taint, origin) come from the daemon, never from the submitter.
> 3. Linking: summaries point to atomic entries by id. Links that resolve to ratified atomic entries make the page index_worthy. Atomic entries never inherit trust from a summary. A summary never counts as a source when an atomic claim is validated, so trust cannot launder through a round-trip.
> 4. Search: results show a visible label (summary · not validated). Rank summaries below atomic entries of equal relevance, or show them in a separate group.
> 5. Watched folder: defer it. If it is built, it must only stage, with origin: folder_drop and an operator ratify step. Without that, any process that can write to the workspace gains a path into inclusion that the operator never acted on.
> 
> Risks:
> - A watched folder lets any local writer, including a sandboxed agent writing into the workspace, put content straight into the KB. That widens authority.
> - Readers may treat inclusion: ratified as "true" unless the label shows in every search result and every KB excerpt fed to a model.
> - Summaries restate claims with no line-level provenance. A model citing a summary can launder an unvalidated claim.
> - Two normalizers (TUI and CLI, or agent and operator) would drift. Keep one daemon code path.
> - The spec 068 index_worthy rule hides unlinked pages. Operators may expect "searchable immediately", so the receipt has to say this plainly. It already does.

### red-team

> OPTION: Shared schema; operator import, staged agent path
> 
> Reasoning: Combine options 1, 3 and a restricted 2. Skip auto-watching a folder for now (option 4 adds ambient ingestion for little gain over a one-step import command).
> 
> The central attack surface is that a summary is a laundering device. An agent reads tainted external content, writes a fluent human-legible page, and the operator accepts it because it reads well. The page then carries the authority of a "reference" while its claims were never checked. So the design must make "included" and "validated" visibly different, and must stop a summary from raising the trust of what it summarizes.
> 
> Proposed path:
> 1. One schema, frontmatter: kind (summary|atomic), id, sources (list of ids/URLs), retrieved, author, taint, summarizes (list of atomic ids), content_hash. The daemon computes taint and the hash; frontmatter claims about taint or tier from the file are ignored and overwritten.
> 2. Operator import (`delphi kb import file.md`, TUI drag-in): one step, counts as ratified for inclusion only. Stored with tier "operator-supplied, unvalidated" and the visible label. Taint is still computed: a file's taint is the maximum of its declared sources' taint, and the file as a whole is treated as external-origin content unless the operator authored it. The import act does not clear taint.
> 3. Agent path: propose_kb_entry with kind=summary lands in the L0 inbox, excluded from search, per-entry ratification, same caps, dedupe and scrubbing. Ratifying it is the same operator act, but the review view must show the source list and taint prominently, not just the rendered prose.
> 4. Linking: summarizes ids are one-way pointers. A summary never promotes the entries it cites. Dangling or later-retracted links surface a staleness flag on the summary.
> 5. Search: summaries are returned in a separate result class, always labeled, ranked below atomic entries by default, and never cited as evidence for a claim in another entry (no summary-of-summary chains counting as sources).
> 
> Risks:
> - Prompt injection survives in markdown (hidden comments, link text, instructions). Scrub and render as data; never let retrieved summary text be treated as instructions.
> - Operator fatigue: one-step import trains rubber-stamping. Show the taint and the sources at import time, not afterward.
> - Label erosion: if downstream consumers strip the label, "unvalidated" gets lost. Make the label part of the returned record, not UI-only.
> - Stale drift: the summary outlives the entries it describes.
> - Size: large files bypass caps; enforce a size cap and chunking.
> - Frontmatter forgery by an agent claiming operator origin through a file dropped in a workspace path; origin must be derived from the channel, not the file.

### strategist

> OPTION: One schema, operator import ratifies inclusion only.
> 
> Reasoning:
> 
> Use one entry schema for summaries and atomic claims. Frontmatter carries kind (summary | atomic), sources (list of atomic ids or raw source refs), retrieved (date), author (seat or operator), and taint (daemon-computed, never author-declared). A summary is a page-level container; atomic entries stay the unit of claim validity.
> 
> Ingestion has three doors that converge on one staging state. (a) `delphi kb import <file.md>` and TUI drag-in: the operator act is ratification for inclusion, recorded as such. The file is labeled kind=summary and carries a visible "not claim-validated" marker. (b) MCP propose_kb_entry with kind=summary: lands in the L0 inbox and waits for per-entry ratification like any agent submission. (c) A watched inbox folder: auto-stages only, never auto-ratifies. Dropping a file into a folder is not consent by itself.
> 
> Trust: a file the operator hands over gets taint computed from its provenance (operator-supplied, no external fetch) but its trust tier is "operator-included, unvalidated". An agent-submitted summary keeps the daemon taint and stays out of kb_search until ratified. Neither path lets the file raise its own tier. Frontmatter claims about trust are ignored.
> 
> Linking: a summary lists the atomic ids it draws on. The daemon checks those ids exist and records their validation state at import time. If an atomic entry is later rejected or changed, the summary is flagged stale, not silently edited.
> 
> Search and visibility: summaries are searchable once ratified, returned with a kind badge, and ranked below validated atomic claims for factual queries. Results always show "summary, not validated" next to any claim drawn from a summary.
> 
> Friction: import is one command or one drag. No second confirmation for operator imports, but the operator's ratification names the scope (inclusion, not validity) so the record cannot be read as validation.
> 
> Risks:
> - Summaries become a back door: readers cite a clean-looking page as if it were validated. Mitigated only by the visible label and ranking, which must be enforced in code, not left to the UI.
> - Operator-import convenience erodes the claim/inclusion distinction over time if the label is cosmetic.
> - Staleness detection depends on atomic ids being stable; renames will silently orphan links.
> - Injection through large markdown bodies: scrubbing must run on imported files too, not only on agent submissions.
> - Auto-staging a watched folder can fill the inbox; needs caps and dedupe by content hash.
> - Summaries of internal research may carry sensitive material; the import path needs the same redaction rules as propose.
> - Models may write summaries that restate unsourced claims; the daemon can check listed sources but cannot check the prose.

### red-team

> 
> 1. Agent-path ratification. If ratifying an agent summary runs through the same normalizer as an operator import, the record can read as "operator act, inclusion ratified" and lose the fact that an agent wrote it. The origin must stay agent_proposed and the taint must be the maximum of the agent's inputs. It must not be reset to the operator-import profile, which is external_untrusted with origin operator_import.
> 2. My own R1 line "taint is the max of declared sources" is weak. Declared sources are author-supplied. The daemon should use the taint of what the proposing seat actually read in that session, not the list in the file.
> 3. Watched folder. The architect and strategist both defer it or limit it to staging. Any local writer, including a sandboxed agent, can still fill the inbox or spoof the queue. Defer it. If it is built later it needs a content-hash dedupe and a hard cap, and origin must come from the channel.

Also, a summary that links to ratified entries becomes index_worthy and shows up in default search. This gives a linkage-based boost to prose that nobody validated. Link existence should not stand in for the page being trustworthy.

> 8. Rubber-stamping. One-step import is fine, but the receipt must show the taint, the source list and the "not validated" scope at that moment.

## Verdict

**No deterministic escalation:** no unresolved P0 and the Round 2 recommendations agree. The decision is the operator's.

> The Council recommends proceeding with changes. Extend the existing spec 068 and kb_import path (as the architect reports it; the strategist and red-team did not re-verify it) instead of designing a parallel one. Options 1 and 2 are both adopted, option 3 is adopted as the shared schema, and option 4 (watched folder) is deferred.
> 
> All three seats agreed on the following. One daemon normalizer serves the CLI import, TUI drag-in and ratified agent proposals. It derives origin and taint from the channel and overwrites any trust fields in the file's frontmatter. Operator import ratifies inclusion only: content stays externally untrusted and is not claim-validated, and the receipt must show taint, sources and scope. Agent summaries stay in the L0 inbox until ratified and keep origin agent_proposed. Summaries link to atomic entries through a daemon-checked summarizes field that pins the target version and flags staleness. A summary can never serve as a validation source or raise the trust of what it cites. The label must be a mandatory field in every search record sent to a model, enforced by a test, with summaries ranked below validated atomic claims. Scrubbing, caps and redaction apply to imports too.
> 
> Disagreements: red-team wants taint computed from what the seat actually read, not the declared source list, and objects that link-based index_worthy visibility boosts unvalidated prose. The architect wants the bibliography-instead-of-body reads kept and "searchable immediately" qualified by the index_worthy rule. The strategist's softer "operator-supplied" taint was rejected.
