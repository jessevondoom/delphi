## Round 1 stances (blind)

### architect

> OPTION: One schema, two entry doors
> 
> **Reasoning**
> 
> Take the options as one design. Option 3 is the spine, and options 1 and 2 are doors into it. Option 4 is a convenience on top, and I'd defer it.
> 
> **Schema.** One frontmatter for every KB item:
> - `kind`: `claim` or `summary`
> - `id`
> - `sources`: the URLs or paths the item relies on
> - `summarizes`: a list of atomic-entry ids (summary kind only)
> - `retrieved`
> - `author`
> - `source_type`: the taint tier, computed by the daemon
> - `validation`: one of `not validated`, `validated`, `disproved`
> 
> A summary is a first-class KB item with a different kind. It is not a different system.
> 
> **Two doors.**
> 1. **Operator import.** `delphi kb import <file.md>`, with the TUI drag-in as a front end on the same command. It is one step. The operator's act makes the item `user_ratified` for inclusion only. The daemon writes `author: operator`, `kind: summary` and `validation: not validated`, then indexes the item at once. The operator does not have to pre-write frontmatter. The daemon fills it in and stores the file hash.
> 2. **Agent propose.** `propose_kb_entry` accepts `kind=summary` with a markdown body. It goes to the L0 inbox, taint is computed from the span's inputs, and it stays out of `kb_search` until the operator ratifies it. This is the same flow as t_0001.
> 
> **Separate two things that are easy to merge: inclusion and validity.** Ratifying a file means "keep this in the KB". It does not mean the claims in it are true. Search results show a summary with a label such as `[summary · operator-imported · claims not validated]`. A summary's trust never rises above the least-validated entry it cites. Summaries are not facts, and they cannot feed `ratify_fact` or heuristics promotion (H-004). If an operator-imported file was itself written by an agent, the daemon records that in the `author` field.
> 
> **Linking.** `summarizes` ids are checked at import. A dangling id is a warning, not a block. Each atomic entry gets a computed back-reference from the summaries that cite it. If an atomic entry is later disproved, every summary that cites it is flagged stale.
> 
> **Search.** Default `kb_search` returns both kinds, with the label and `kind` in each result. A `kind` filter is available. Atomic entries rank above summaries for the same match.
> 
> **Watched folder.** Defer it. If it is added later, it should only stage items into the inbox and never auto-ratify them.
> 
> **Risks**
> - Operator-imported text bypasses the inbox scrubbing. It still needs secret and path scrubbing, size caps and a prompt-injection taint note at import. Also, "user_ratified" must not let the summary's body count as instructions to agents.
> - A fluent summary can carry more apparent authority than its sources justify. The label must be visible in the result, not only in the metadata.
> - Summaries go stale when the atomic entries they cite change, so the staleness flagging needs a deterministic check.
> - Two ways to bring the same file in can create duplicates, so dedupe by content hash.
> - The `kind` field is a schema change that existing `kb_search` consumers must tolerate.

### red-team

> OPTION: Explicit import with strict taint bounding
> 
> Markdown roll-ups represent an expanded composite attack surface. Unlike atomic claims, narrative markdown documents pack high token density, complex formatting, and latent instructions that easily conceal indirect prompt injections, semantic drift, and memory-poisoning vectors.
> 
> 1. **Explicit Ingestion Only (Reject Watched Folders):** Ambient watched inbox folders introduce a passive ingress vulnerability where untrusted subprocesses, build hooks, or git checkouts can silently stage files. Ingestion must require an explicit invocation: the CLI/TUI command `delphi kb import <file.md>` for operators, or `propose_kb_entry(kind="summary", ...)` for agents.
> 2. **Inclusion Is Not Verification (Anti-Laundering):** Operator import must record approval for *storage inclusion* only, never *claim validity*. Frontmatter must explicitly mark `validation: "not validated"` and preserve the authoring span's computed taint tier. Handing a file over through the CLI must never launder synthetic or federated text into `user_ratified`.
> 3. **Strict Schema & Cryptographic Claim Linking:** Summaries must conform to a deterministic frontmatter contract (`kind: summary`, `summary_of: [<claim-id>, ...]`, `author`, `source_mission`, `content_hash`). Ingestion must fail if referenced atomic claims do not exist or if frontmatter is missing or invalid.
> 4. **Fenced Retrieval & Taint Degradation:** When exposed in `kb_search`, summaries must be returned inside strict boundary tags (`<summary validation="not validated" tier="...">`) and accompanied by a visible warning. Agents reading unvalidated summaries must have their execution context bounded accordingly.
> 
> ### Risks
> - **Operator Rubber-Stamp Laundering:** Operators routinely import convenience summaries without reading every word. If CLI import automatically elevates trust or bypasses taint computation, adversarial payload content from untrusted research bypasses Tier 1 invariants.
> - **Ambient Filesystem Ingestion:** A watched folder creates an unauthenticated staging pipeline susceptible to symlink traversal, rogue worktree writes, and inbox flooding DoS.
> - **Indirect Instruction Injection:** Markdown summaries can embed hidden HTML comments, markdown formatting exploits, or prompt injections that trigger when future agents consume the KB entry.
> - **Stale Claim Desynchronization:** If an atomic claim referenced by a summary is disproved, the narrative summary will persist and silently propagate refuted claims unless bidirectional invalidation is enforced.

### strategist

> OPTION: Operator import primary; agent path gated
> 
> **Reasoning (scope and sequencing lens):**
> 
> The ruling in t_0001 already solved the hard problem: agent output never reaches searchable trust without a human act. The new ask is mostly a friction question, so the smallest correct extension is to reuse that machinery and add one new *kind*, not a second pipeline.
> 
> 1. **One schema, two doors.** Adopt option 3 as the foundation: a single frontmatter (`kind: atomic | summary`, `sources: [entry ids / URLs]`, `retrieved`, `author`, `origin: operator_import | agent_proposed`). Taint and trust tier are daemon-computed, never read from the file. Any `taint:` or `trust:` keys in a dropped file are stripped and logged.
> 
> 2. **Operator import is the MVP.** `delphi kb import <file.md>` (TUI drag-in is the same call). The operator's act counts as ratification of *inclusion* only. The entry is searchable immediately, but carries a visible label such as `summary · operator-imported · claims not validated`, and its taint reflects the author's content, not the operator's act. The operator can raise it to validated later via the existing per-entry ratification. That is "inclusion yes, claim validity no."
> 
> 3. **Agent path reuses propose_kb_entry** with `kind=summary`: it is staged in the L0 inbox and ratified per entry, exactly like atomic entries. Nothing new to build besides the kind field and size cap (larger body limit, still scrubbed and deduped).
> 
> 4. **Linking.** A summary's `sources` field holds atomic ids; the daemon verifies they exist and records backlinks. A dangling or unvalidated source is shown as such on the summary page. A summary never inherits validated status from the entries it cites.
> 
> 5. **Search.** Summaries are included in kb_search by default but ranked below validated atomic claims, with a `kind` filter and a label in every result so they cannot be mistaken for facts. A summary must never be cited as the evidence for a claim.
> 
> 6. **Defer the watched folder.** It is a convenience on top of import, adds a filesystem-trigger attack surface, and is not needed for the MVP. Stage-only if ever added.
> 
> **Risks:**
> - Label blindness: operators and agents treat "searchable summary" as fact; laundering of unvalidated claims via summaries citing each other.
> - Agents reading imported summaries as high-trust instructions; imported text must stay data-fenced.
> - Operator importing agent-written text raises the apparent tier unless taint is kept tied to content origin.
> - Large files bloat the index and dilute the ranking; need caps and chunking.
> - Scope creep into a wiki or doc system; hold to the one `kind` field.

## Verdict

**Escalated to the operator:** the Round 2 recommendations conflict.

- [Option A] ALTERNATIVE: one schema, explicit-only doors, inclusion-not-validity, no watched folder — architect
- [Option B] PROCEED-WITH-CHANGES — red-team, strategist

> **Verdict**
> 
> The Council recommends one shared schema with two explicit doors, and no watched folder. Operator import is `delphi kb import <file.md>`, with the TUI drag-in as a front end on the same command. Agents use `propose_kb_entry(kind=summary)`, which stays in the L0 inbox until ratified. Summaries are a `kind` of KB item, not a separate system. Each carries `sources` or `summarizes` ids, and the daemon computes backlinks. The operator's act ratifies inclusion only. Every result shows a visible label such as "summary · operator-imported · claims not validated", and the body is data-fenced.
> 
> **Agreed:** all three seats rejected the watched folder, or would stage it only into the inbox. They agreed that taint is computed from content origin and never read from the file. They also agreed on scrubbing, size caps, hash dedupe and fencing. Summaries rank below validated atomic claims. They cannot serve as evidence for `ratify_fact` or H-004 promotion. Disproving a cited entry makes the citing summaries stale.
> 
> **Disputed:**
> - **Dangling ids.** Architect and Strategist would warn but still import, so URL-sourced roll-ups work. Red-Team would block, because a fabricated citation looks like grounding.
> - **Authorship.** Red-Team objects to writing `author: operator` for a file the operator only imported. Architect had proposed it.
> - **Stale summaries.** Red-Team wants them suppressed or heavily warned in search. Strategist prefers a passive flag computed at search time.
> 
> Architect concurred with its own alternative. Red-Team and Strategist asked to proceed with changes, and Red-Team did not concur. The operator must settle these points.

## Decision and next steps

**Decision:** needs the operator: Should import tolerate dangling source ids and flag stale summaries passively, or block dangling ids and suppress stale summaries in search?


If **ALTERNATIVE: one schema, explicit-only doors, inclusion-not-validity, no watched folder**:

1. `architect`: Write the spec for the shared schema, with `included_by` kept separate from the content author, dangling ids as warnings, and a stale flag computed at search time.
2. `builder`: Implement `delphi kb import` and `kind=summary` in `propose_kb_entry`, with scrubbing, a size cap, hash dedupe and label and fence rendering in `kb_search`.
3. `red-team`: Review the spec for phantom citations and the authorship fields before approval.

If **PROCEED-WITH-CHANGES**:

1. `architect`: Amend the spec so import blocks on dangling ids, records the original author or marks it "unknown, imported by operator", and suppresses stale summaries in default search.
2. `strategist`: Check that the stricter blocking does not break one-step import of URL-sourced roll-ups, and decide whether to allow an explicit override flag.
3. `builder`: Implement the import command, the summary kind, fenced and truncated search rendering, and the backlink and stale check.
4. `red-team`: Re-review the amended spec against the open P1 items.
