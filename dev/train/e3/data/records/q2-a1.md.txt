> OPTION: Fix retrieval first; few new tools
> 
> Reasoning (architect). I read specs 062, 064, 041, 038 (headings and open items), 072 §5, and the server code in crates/delphi-engine/src/mcp_host.rs, mcp_project.rs, kb.rs. I read 003 and 013 only for scope, not in full. The surface is not thin. It has 40+ tools: search_kb, kb_retrieve, search_project, search_memory/query_memory, list_roles/get_agent/get_skill, route, request_help, consult_orchestrator, spawn_agent_pack, request_research/research_result, council_*, specs_status, scaffold_status, plus prompts/ and resources/. Adding more tools is not the main need. The main defect is that the surface breaks its own specs.
> 
> (1) RAG: this is the real problem, and it is structural. There are two retrieval paths. search_kb goes through the daemon (064 §5, conforming). kb_retrieve (072 §5) runs inside the MCP process and calls `Kb::open` (kb.rs:519), which opens the index read-write: it sets the WAL pragma, runs schema init, and creates the file if it is missing. That breaks 064 §2.3 (the daemon is the only writer), §3.1 (one retrieval service), §5.1 and AC-6 (no daemon means nothing is opened). kb_retrieve also attaches no embedder, so it is lexical only. It passes zone "context" without excluding context/facts (§5.2), as far as the call site shows. It also labels any project spec whose frontmatter says `approved` as status "validated", confidence "high". That raises trust from content read from outside, which 064 §2.1 and §7.3 forbid. Fix: route kb_retrieve through retrieval.rs over HostLink, use the §5.2 allowlist, take status from ratified.lock or the KB status only, and keep one implementation behind both tool names.
> (2) Specialties: mostly sufficient through get_agent, route and request_help. The gaps are 041 `[extends]`/registry maturity and the fact that a host can ignore a pack. These close through guidance, not tools.
> (3) Research and strategy: request_research covers facts. There is no defined "strategy report" contract: request_help with strategist returns at most 8000 characters with no evidence pointers (062 §6, amended S6). A small result-schema change is enough: add claim/source ids.
> (4) Spec-driven guidance: specs_status and scaffold_status exist. What is missing is a read-only "may I build X?" check (the spec_link logic) and a skill or prompt for external projects (specs/external, 070). Do this through a prompt or skill first, and add a tool only if the check needs to be deterministic.
> 
> Priority: P0 kb_retrieve conformance, then 2 to 3 small result and schema changes, then guidance-only work.
> 
> Risks:
> - If the operator picks "sufficient", a read-write index handle stays live in a process that must never write, and frontmatter-derived "validated" labels mislead host RAG.
> - Adding tools widens the surface further when duplication is already the problem.
> - Guidance-only fixes cannot enforce anything, because hosts can ignore packs.
> - Q-4 (long calls) is still unverified for several hosts, so research and council results depend on polling.
