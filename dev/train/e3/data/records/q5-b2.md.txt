### architect

> OPTION: Approve with amendments
> 
> I could not read the draft (the spec slice was unavailable), so this ruling rests on the host's summary. It is advice on the design, not a review of the text.
> 
> **Reasoning.** The split is sound. The §1.3 failure is that "no spec" blocks work whose risk is low and whose output is reviewable on sight, such as a deck or a document. A spec gate adds no safety there. It does on executable content, so keeping it for software is right. Moving to a closed allow-list of artifact types, with unlisted types defaulting to software, is the safe default. The verbatim, daemon-written operator-prompt log is a good substitute control. It gives provenance without agent self-reporting.
> 
> **Amendments I'd require:**
> 1. **Executable-content test.** Define "software" by capability, not file extension. Macro-enabled docs, HTML with script, SVG with script, notebooks, and spreadsheets with external-data or formula execution are software. The allow-list must name formats exactly, for example `.docx` but not `.docm`.
> 2. **Markdown carve-out boundary.** Markdown, scaffolds and `scratch/` stay exempt only when they contain no executable content and are not a governed path (`specs/`, `memory/`, `agents/`, `skills/`, `themes/`). Otherwise the exemption becomes a bypass: a "plain file in scratch" that a build later executes.
> 3. **Log integrity.** The log is append-only, written by the daemon, and carries a hash chain. Agents have no write path to it. It records the operator's prompt verbatim, the artifact path, the role and the timestamp. Agents never author its content.
> 4. **Secrets.** Verbatim prompts may contain secrets. Add a redaction or scrub rule, and keep the log local and never exported by default (§5.3).
> 5. **Reclassification.** If an artifact task later gains executable content, it moves to software and needs a spec before that change.
> 
> **D-1 (log location):** Put it in the workspace home, under daemon-only `local/`, outside the project checkout and outside any path an agent can write. Do not put it in `missions/`, which agents can write, and do not commit it to Git.
> 
> **D-2 (external project spec location):** Use `specs/external/<project>/`. It matches the existing §1.3 text, so the governed-path and ratification rules apply unchanged, and no new rule is needed.
> 
> **D-3 (`(system)` entries):** Allow them, but as a separate entry kind. They must be daemon-generated, labelled as not operator prompts, and kept distinct from the verbatim operator entries. That keeps "operator-prompt-only" true. Never record agent-authored text in them.
> 
> **Risks:**
> - **Allow-list drift.** Each new format added to the list is a possible bypass, so additions should need ratification.
> - **Log trust.** The log could be mistaken for an approval record. It records provenance only.
> - **Tiny `(system)` entries** could grow into a transcript channel.
> - **Mixed tasks.** A task that produces both a deck and a script needs a clear rule: the whole task is software.

### red-team

> OPTION: Approve with amendments
> 
> Exempting passive artifacts (decks, reports, diagrams, images) from the heavyweight "No Spec, No Build" cycle removes operational friction without degrading software integrity, provided active execution cannot be smuggled under artifact types. Software implementation—whether building Delphi internal components or guiding external client code—must remain strictly gated by approved, audited specs. 
> 
> We recommend approval subject to the following binding amendments and rulings:
> 
> 1. **D-1 (Log Location):** Place the prompt log at `local/logs/artifact-prompts.jsonl`. It must reside in daemon-owned storage outside agent-writable worktrees and scratch directories, with append-only permissions enforced by `delphi-core` to prevent tampering, deletion, or truncation by compromised agents.
> 2. **D-2 (External Project Spec Location):** Anchor external specs strictly in `specs/external/<project>/` within the central Delphi governance tree. External project workspaces and guest repositories must never host their own gating specs, which would subject approval states to untrusted branch checkouts or PR tampering.
> 3. **D-3 (Log System Entries):** Automated, scheduled, or subagent prompts must be explicitly recorded with immutable provenance labels (e.g., `[system:<subsystem>]` or `[agent:<role>:<task-id>]`). They must never be logged or formatted as human operator prompts. The log must preserve unambiguous distinction between authentic human directives and synthetic dispatches.
> 4. **Artifact Sanitization Gate:** The closed allow-list must enforce deterministic AST/static rejection of active code: HTML and SVG must strictly forbid `<script>` tags, inline event handlers, and remote object loads; document formats must reject macros and executable polyglots.
> 5. **Deterministic Non-Executability in Scratch:** The exemption for scaffolds and `scratch/` files must be backed by runtime enforcement: files created under this exemption must have execution bits stripped, forbid shebangs, and be blocked from execution runners to prevent un-specced software development in scratch space.
> 
> ### Risks
> 1. **Artifact Smuggling:** Without strict parser-level rejection of active payloads, hostile or compromised agents can smuggle malicious scripts into HTML/SVG reports or macro-enabled documents, bypassing spec gates.
> 2. **Audit Laundering:** If autonomous subagent executions log synthetic instructions under operator-like entries, accountability collapses and human oversight over artifact generation becomes illusory.
> 3. **Scratch Laundering:** Ambiguity in "scaffolds without executable content" invites Builder to construct production code piecewise in `scratch/`, circumventing Red-Team and Strategist review before promoting code into the build.
