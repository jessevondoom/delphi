### architect

> OPTION: New tools/resources, prompts as wrapper
> 
> Caveat: the spec slices (062, 064, 041, 003) were unreadable to me, and I didn't check 013/038. This is a design stance from the four outcomes and general MCP principles, not a gap audit against the spec text. The Council should check each gap below against the specs before acting on it.
> 
> **Reasoning**
> 
> "Sufficient" is unlikely. The four outcomes need different mechanisms, so I'd split the gaps by mechanism.
> 
> 1. **RAG over the full knowledge base (highest priority).** The only retrieval I could see is `kb_search`. It returns pointers with a validation status, capped at 10 results. A host agent needs three things on top of that:
>    - A fetch-by-pointer read.
>    - Scoping filters (validated only, by path or domain).
>    - Hybrid retrieval, covering `context/`, `missions/`, project research and Xenia in one call, with taint and provenance labels preserved.
>    
>    This needs new tools or resources. Prompts can't provide it. Expose KB documents as MCP resources (`delphi://kb/<path>`) so hosts can subscribe and read them directly.
> 
> 2. **Agent specialties and expertise.** Hosts can't use roles they can't discover. I'd add `list_roles` and `describe_role` as read-only tools or resources. They would cover scope, blind spots, counterweights and routing hints from the 041 registry. A `consult(role, question)` tool would give advisory single-role answers. It must stay read-only and tainted-ingress-safe. Dispatching real work stays gated.
> 
> 3. **Research reporting and strategy.** The write_* tools and `request_research` already exist. The gap is mainly orchestration. MCP **prompts** (such as `research-report` and `strategy-brief`) can encode that workflow cheaply. `request_research` already requires operator approval, so keep that.
> 
> 4. **Spec-driven development guidance.** This is mostly a prompts and resources problem. Expose GOVERNANCE, the spec template and the "No Spec, No Build" workflow as resources. Add prompts such as `draft-spec` and `review-spec`. Add a `check spec` tool wrapper, since `check` already exists.
> 
> **Priority:** (1) retrieval tools and resources, (2) role discovery and consult, (4) spec resources and prompts, (3) report prompts.
> 
> **Recommendation:** use new tools and resources for 1 and 2, and prompts for 3 and 4. Prompts alone fail on 1 and 2.
> 
> **Risks**
> - Reading KB content lowers the task's trust ceiling to L2 or lower. Hosts must see the taint labels, or the KB becomes an injection path into the host.
> - Exposing `consult` and dispatch to external hosts widens the attack surface. Every mutating or outbound action should stay approval-gated (§5.4), and Council rulings are advice only.
> - Resource subscriptions and large dumps hit lost-in-the-middle limits. Use pointer-maps and bounded results (H-002).
> - Tool sprawl. Keep the surface small, ideally 4–6 new tools, and apply a simpler-alternative test to each.
> - Spec drift. Any new tool needs an amended 062/064 before building (No Spec, No Build).

### red-team

> OPTION: Close gaps via new tools/resources
> 
> ### Reasoning
> 
> Relying on "prompts and plugin guidance only" directly violates Governance §5.6 (*Enforcement Is Code, Not Prose*). A host agent operating outside Delphi cannot enforce taint lattices, blind-spot counterweights, or merge gates through system prompt instructions alone. When a host agent faces complex context or adversarial inputs, prompt-only constraints suffer attention dilution and sycophantic collapse. Delphi must expose deterministic tools and typed MCP resources to safely serve external host agents.
> 
> The gaps across specs 062, 064, 013, 038, and 041 break down into four critical areas:
> 
> 1. **RAG & Knowledge Retrieval (Spec 064, `[H-004]`):** Raw search dumps trigger context loss (`[H-002]`) and bypass Information Flow Control. The MCP surface must expose bounded, provenance-tracked RAG tools that return explicit taint metadata (`source_type`, confidence, tier). Without structured resource boundaries, low-trust external text easily poisons downstream host decisions.
> 2. **Spec-Driven Governance (Spec 062, GOVERNANCE §1.3):** Host agents currently lack a deterministic mechanism to verify whether a task has an approved spec before executing code. Delphi must provide a spec-verification tool (`check_spec_status`) that programmatically blocks implementation when `Implements-Spec` is missing or unratified.
> 3. **Agent Specialties & Routing (Spec 041, Spec 003):** Host agents cannot replicate canonical roles (e.g., Red-Team's falsifiable-critique contract or Architect's simpler-alternative rule) via generic prompts. Delphi needs an explicit consultation/dispatch tool exposing structured role evaluations with enforced counterweights.
> 4. **Research & Strategy Synthesis (Spec 013, Spec 038):** Strategic planning requires bounded artifacts (e.g., structured reports, decision cards) rather than open-ended dialogue turns.
> 
> **Prioritized Remediation:**
> - **P0 (Blocking):** Taint-aware retrieval resources (Spec 064) and deterministic spec-gate tools (Spec 062).
> - **P1 (Major):** Structured role-consultation and Council dispatch tools (Spec 041, Spec 003).
> - **P2 (Minor):** Structured research and strategy artifact generation endpoints (Specs 013, 038).
> 
> ### Risks
> 
> 1. **Confused Deputy & Privilege Escalation:** External host agents may invoke mutating or privileged Delphi tools without operator presence. Outbound actions and memory promotions must remain strictly gated behind operator ratification (`[H-004]`).
> 2. **Context Bleed & Taint Laundering:** Host agent scratchpads could strip provenance headers before passing data into Delphi memory. Ingress must default to tainted (`external_untrusted`).
> 3. **Tool Surface Bloat:** Exposing too many granular tools degrades external agent routing accuracy; tools must remain cohesive and schema-constrained.

### strategist

> OPTION: New tools, sequenced; prompts second
> 
> **Caveat:** The spec slices (062, 064, 041, 003) could not be read here, and 013 and 038 weren't supplied. I'm ruling on strategy and scope, not on verified gaps. Each gap below is a hypothesis to check against the specs and the actual tool list before anything is built.
> 
> **Stance:** "Sufficient" is the least likely answer, since the host is reporting felt friction. "Prompts and plugin guidance only" is cheap, but it can't add capability. The four goals differ in kind, so I'd split them.
> 
> 1. **RAG over the full KB (P1, tools).** This needs a real tool. Retrieval has to be a deterministic daemon function that returns pointers and passages with a trust tier and validation status on each. Prompt guidance can't do that. First check that `kb_search` already covers `context/`, `missions/` and project research, and that it can return passages and not just pointers. Any gap there is an implementation gap in spec 064, so fix it before adding surface.
> 
> 2. **Specialties and expertise (P2, mostly resources and prompts).** Expose the role registry (spec 041) as read-only MCP resources: role descriptions, scopes and blind spots. Add one prompt per role, or a "consult role X" tool that routes through dispatch. Personas don't need new machinery. Doing this through the registry avoids a second source of truth.
> 
> 3. **Research reporting and strategy (P3, prompts plus existing tools).** `request_research` and the `write_report` tools already exist. What's missing is workflow guidance: a prompt template for "research, then synthesize, then recommend". Keep the operator-approval gate on research jobs.
> 
> 4. **Spec-driven development guidance (P2, resources and prompts).** Publish the spec template, the No Spec No Build rule and the `check spec` verifier as resources and prompts. Don't add a build-orchestration tool until usage shows a need.
> 
> **Sequencing:** audit the actual MCP surface against the four goals (one day). Then ship retrieval fixes. Then ship registry and spec resources and prompts. Defer anything that mutates state.
> 
> **Risks:**
> - **Scope creep:** four goals invite a big "host mode" project. Hold each tranche to one verifiable outcome.
> - **Trust leakage:** KB content returned to a host agent is data and should be tainted. Hosts must not be able to promote it, or ratify anything, through MCP.
> - **Council and dispatch exposure:** tools that start dispatches are outbound and cost money. They need approval gates and budget caps.
> - **Two sources of truth:** prompts that duplicate the specs will drift. Generate them from the specs.
> - **Unverified premise:** I haven't seen the specs, so I may be proposing something that already exists.
