## Round 1 stances (blind)

### architect

> OPTION: Hybrid: Delphi drafts, Claude cross-reviews
> 
> The question is a false binary. Which model writes the README matters less than the loop it runs in. A README is a user-facing artifact, and it must describe what the system actually does today. Governance gives Writer that job, with a rule to document only what is built and to keep Red-Team caveats.
> 
> My recommendation:
> 
> 1. **Delphi drafts through its own pipeline.** The system writes its own README, and the Writer role owns it. Scout or Investigator first produce a pointer map of what exists: specs, the CLI surface, installed tools. The draft is grounded in those pointers rather than in a model's general impression of the project. An README is an artifact (a document), so it needs no spec. Each edit is logged.
> 
> 2. **A different model family reviews it.** This follows [H-008]: an author family should not be its own sole critic. If Delphi's Writer runs on Claude, the critic should be another family. If Writer runs on another family, Claude is a good reviewer. The point is that a reviewer from a different lineage catches claims the author family glosses over.
> 
> 3. **Verify every claim.** Each command, flag and feature in the README gets checked against the spec or the actual CLI output. Anything that is only planned goes in a clearly labelled "Not yet built" section, or gets cut.
> 
> 4. **The operator approves.** If the README lands in a repo, the merge is the operator's call.
> 
> Why not Claude alone, working outside Delphi? It has no live view of the system's real state. It would likely produce a polished README that overstates capability. Why not Delphi alone with no outside check? That gives self-description with correlated blind spots, and it skips the review layer the system itself requires. It would also fail to show whether the system can document itself honestly. That's a useful property to test.
> 
> Simpler alternative considered: have Claude write it in one shot and skim it. That is fastest, and fine for a throwaway. It is weak for something that will be the project's front door.
> 
> **Risks:**
> - A self-written README can drift from reality as the code changes. Mitigate by regenerating on release and by checking its commands in CI.
> - Both models may share a blind spot about the project's value or audience. The operator should read it for tone and for omissions.
> - The Writer may favor polish over truth, or repeat spec aspirations as facts. The claim-by-claim check is the guard.
> - Two passes cost more than one. For a README that is acceptable.
> - If only one model family is configured, label the review `homogeneous`, as the charter requires.

### red-team

> OPTION: Delphi writer under adversarial verification
> 
> Having an unconstrained single agent (such as standalone Claude) write documentation for a system it just touched is a classic anti-pattern for truthfulness. Single-model sessions suffer from heavy sycophancy, anchoring on intent rather than reality, and routinely document aspirational architecture, unbuilt features, or non-existent CLI flags as if they are functional ("happy-path bias"). 
> 
> Delphi’s governed architecture is specifically counter-weighted against this failure mode. Under Delphi governance:
> 1. The **Writer** role operates under a strict "truth before harmony" mandate, explicitly barred from documenting unbuilt or speculative behavior as working.
> 2. The **Investigator** and **Red-Team** act as counterweights: documentation claims must map to ground-truth code, CLI help outputs, and passing test suites rather than prompt assumptions.
> 3. Handoffs separate the implementation context from the documentation synthesis, preventing prompt-pollution where obsolete drafts get recycled into the user-facing README.
> 
> Relying on an external or unverified single-pass prompt in Claude Code lacks invariant enforcement, drift detection, and adversarial review. Delphi should generate the README through its standard pipeline, subject to an adversarial accuracy check against actual repository state.
> 
> ### Risks
> - **Self-referential blind spots:** If Delphi documents itself without running code, it risks accepting its own design specs as ground truth instead of verifying actual runtime behavior and installation prerequisites.
> - **Over-formalization and bloat:** Delphi’s pipeline can produce overly academic, spec-heavy documentation that obscures quickstart essentials needed by human developers.
> - **Verification gap on external harnesses:** If Delphi lacks read access to executable host binaries or CLI help flags during drafting, assertions about syntax and command-line behavior cannot be falsified deterministically before publication.

### strategist

> OPTION: Writer drafts, verified against code, operator ratifies
> 
> The question is a false binary. "Me or Claude" matters less than who owns truth and approval. A README is user-facing documentation, so the writer role is the natural author, run on whatever model fits. Which model does the drafting matters little. What matters is the process around it.
> 
> My recommendation:
> 1. **Have the system draft it, since the operator wants that.** A Delphi writer agent, or Claude through Delphi, gets the specs, the code and the changelog as pointers and drafts the README. The host agent (me or the Sonnet host) can do this too. Model family is a secondary choice.
> 2. **Ground every claim.** The writer's blind spot is polish over truth. Each feature claim should point to a spec or to code that exists. Nothing unbuilt may be described as working, and Red-Team caveats stay in.
> 3. **Use a different model family to check it.** Under H-008, the author's family should not be the only reviewer. A second model, or Red-Team, checks each claim against the repo.
> 4. **Operator approves before it lands.** A README is not a governed path, so this needs no spec. It is still the public face of the project, so the operator reads the diff before merge.
> 5. **Keep it small and regenerable.** Aim for a short README: what it is, install, quickstart, links to the specs. Link to the specs instead of restating them, so there is less to drift. If the system is meant to rewrite it on its own, add a check that the README's commands and paths still exist. If the check is run twice by hand, turn it into a script (H-005).
> 
> On scope: don't build an auto-regeneration pipeline now. That would be gold-plating, and it would need a spec under No Spec, No Build. Do a one-off draft with a verification pass, and revisit automation only if the README drifts.
> 
> **Risks**
> - Hallucinated features or commands. The model reads aspirational specs as shipped behavior.
> - Same-family self-review hides errors, because the drafter and the checker share blind spots.
> - The README drifts from the code over time. Without a check or a refresh trigger, it goes stale quietly.
> - The host's question is unclear about what "this system" means. I assumed Delphi or the host project. If it means a self-updating loop, the scope grows and a spec is needed.
> - Secrets or local paths leaking into the README (§5.3).
