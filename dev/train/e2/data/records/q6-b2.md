### red-team

> OPTION: Approve E1-E2 only; defer E3-E5
> 
> **Reasoning**
> 
> D-1 (declarative marketplace metadata and drift-tested ecosystem sync in E1–E2) represents inert catalog schema definitions. Provided manifests are statically validated in CI, E1 and E2 expand no execution boundary and can proceed.
> 
> In contrast, D-2 (E3 installer modifying host configurations outside the workspace) and D-3 (E5 bundled launcher scripts) introduce severe security and authority-widening regressions:
> 
> 1. **Host Boundary Breach (D-2 / E3):** Delphi Governance §5.1 and §5.4 enforce strict workspace isolation and require explicit gates for actions that alter host state outside the project boundary. Allowing `delphi mcp --install` to mutate user-level host agent configuration files (such as `~/.claude.json` or host IDE settings) turns Delphi into a confused deputy. Even with operator invocation, automated mutation of external config files creates persistence risks, clobbers existing host settings, and invites race conditions across running host agents. E3 must be deferred until deterministic diff previews, schema verification, rollback snapshots, and atomic file-locking are fully specified and verified.
> 2. **Unsandboxed Execution via Launchers (D-3 / E5):** Allowing shell or wrapper launcher scripts in a plugin breaks Governance §5.5 ("Worktrees Are Not Sandboxes"). Executable scripts distributed in plugin bundles bypass deterministic binary auditing, evade Delphi's taint lattice, and execute directly within the host's unsandboxed environment. Host integrations must exclusively invoke registered, pre-audited Delphi binaries with verified parameters rather than intermediate executable scripts.
> 3. **Q-1 through Q-5 Gate:** Any unresolved questions touching on host privilege escalation, config mutation atomicity, or unauthenticated plugin launch vectors must strictly block approval of E3 and E5.
> 
> **Risks**
> 
> - **Persistence Hijacking & Escapes:** Modifying host configs outside the workspace establishes persistence vectors that execute outside Delphi runtime governance and auditing.
> - **Supply-Chain & Injection via Launchers:** Executable launcher scripts in plugin directories create a vector for local privilege escalation or injection into the host agent's tool loop.
> - **Host Toolchain Corruption:** Concurrent or unvalidated writes across diverse host configurations risk silent corruption of host agent environments without a clean rollback path.

It publishes what already exists and adds no new authority. A drift test makes it deterministic code, which fits §5.6 and H-005. It is also cheap to reverse, because it only adds files.

> - **D-2 (operator-run `delphi mcp --install` editing host config outside the workspace): defer.** The request sounds modest, but it changes the trust model.

>   - This is the kind of host-affecting change that §5.4 and §5.5 require a synchronous approval for.
>   - If it ships, it needs a spec of its own. It shouldn't ride along in a marketplace spec, so that its Red-Team review isn't diluted.
>   - The convenience gain is small. Today the operator pastes a snippet, which is a single copy-paste step.
> 
> - **D-3 (a launcher script in a plugin): defer.** A script shipped through a marketplace executes on the user's machine whenever the plugin is enabled. That makes it a supply-chain surface. A plugin that only holds config and docs has no such surface. A launcher should wait until it can be pinned, hashed and reviewed, and until we know why a plain `command` entry in the MCP config isn't enough.
> 
> - **Q-1..Q-5:** I can't see their text. As a rule, any open question that touches D-2 or D-3 should block approval of those parts only. Open questions about E1-E2 should block approval only if they affect the generated content's correctness. Q-5 of spec 062 is being extended, and I'd treat it as blocking for the installer.
> 
> **Risks / missing safeguards to check**
> 
> 1. **Authority widening via the installer.** Delphi would be editing the host's config, which can grant itself persistent tool access in a different tool. The installer needs to be dry-run by default, show a diff, make a backup, be idempotent, and have a clean uninstall. It must never run from an agent or from within a task, only from the operator at the console.
> 2. **Durable enablement.** Persistent auto-enablement removes the per-session consent that an operator gives today. The spec should state which tools the enabled server exposes, and whether any of them are mutating or outbound.
> 3. **Marketplace tampering.** A root marketplace manifest that points at the repo means that anyone with commit rights can change what users install. Pin the version and ref, and require signed releases or a protected branch.
> 4. **Drift test scope.** The test must cover the manifest, the launcher hash and the snippets. A partial test gives false assurance.
> 5. **Taint.** Generated files that quote outside content must not carry a higher trust tier than their source.
> 6. **Scope creep.** The marketplace, the installer and the launcher are three separate deliverables with different risk levels, and they should be sequenced as separate milestones.
