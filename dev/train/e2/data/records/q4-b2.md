## Round 1 stances (blind)

### architect

> OPTION: One schema, two entry paths
> 
> **Reasoning.** The options are not exclusive. The simplest design that keeps t_0001's invariants is one schema with `kind` as a discriminator and two doors. Those two doors are operator import and agent propose. A watched folder is a third door, and I would cut it.
> 
> **Schema.** Every entry carries frontmatter: `id`, `kind` (`claim` | `summary`), `author`, `source_type` (taint, computed by the daemon), `sources` (URLs or paths), `retrieved`, `summarizes` (a list of atomic ids), and `status`. A summary's body is markdown. Summaries are stored separately from atomic entries so a page is never mistaken for a validated claim.
> 
> **Operator import.** `delphi kb import <file.md>`, with a TUI equivalent that calls the same daemon function. The daemon stamps `author: operator` and `kind: summary`, and it computes the taint from the import act itself, not from the file's contents. The import counts as ratification of inclusion, so the entry is searchable at once. The record carries a separate field, `claims_validated: false`, and the search result always shows the label `summary · operator-imported · unvalidated`. Any frontmatter inside the file is treated as a hint. The daemon strips or overrides `source_type`, `status` and `author`. This follows the rule that taint is computed, never declared.
> 
> **Agent path.** `propose_kb_entry` accepts `kind: summary`. It goes to the L0 inbox, is excluded from search, and is ratified per entry, exactly as t_0001 ruled. If the summary's text came from a low-taint span, it inherits that taint. A summary can never raise the trust of the claims it describes.
> 
> **Links.** `summarizes` holds atomic ids, and the daemon builds the reverse index. Dangling ids are allowed but flagged. If a linked atomic entry is later disproved, the summary shows a warning. That keeps the "not claim-validated" caveat honest over time.
> 
> **Search.** By default, `kb_search` returns atomic entries first and summaries in a separate, labeled group. A `kind` filter is available. Summaries are never returned as `<fact>` elements.
> 
> **Friction.** Import is one command. The watched folder adds a standing ingestion surface and a silent-staging route, and it duplicates `import`. If the operator wants it, it should only stage into L0 and never ratify.
> 
> **Risks.**
> - Operators may read the "searchable" label as "true." The label and the `claims_validated` field must be impossible to hide.
> - An imported file with no verifiable sources could carry injected instructions. Results must show it as data, and the same scrubbing and size caps should apply.
> - The operator-import act raises taint to `user_ratified` for inclusion. That could be confused with raising it for claims. Use a separate field, or a distinct tier name, for "included by operator".
> - Summary drift: a stale summary survives after its atomic entries change.
> - Agents might promote content from summaries into heuristics, so `[H-004]` must treat summaries as below `internal_empirical` regardless of import.

### red-team

> OPTION: Explicit import, inherited taint, partitioned retrieval
> 
> ### Reasoning
> Ingesting whole markdown summaries introduces significant attack surface for memory poisoning and unearned authority laundering. When an agent condenses research into human-readable prose, it introduces framing biases, subtle hallucinations, and potential prompt injection payloads that human operators rarely audit line-by-line.
> 
> 1. **Strictly Explicit Ingestion:** Ingestion must require an explicit, intentional CLI or TUI command (`delphi kb import <file>`). Watched filesystem directories must be rejected entirely; passive polling creates local TOCTOU race conditions and allows rogue scripts, untrusted processes, or leaky build steps to silently inject staged payloads into Delphi's memory boundary.
> 2. **Inclusion Ratification $\neq$ Factual Validation:** Operator import ratifies solely that the document belongs in storage, never that its claims are true. The file must be permanently labeled `kind: summary` and `claims: unvalidated` unless individual constituent claims undergo formal deterministic verification or explicit per-claim ratification.
> 3. **Immutable, Inherited Taint:** In accordance with §4.3 and `[H-004]`, taint must be computed and inherited from the underlying sources, not laundered by the operator's import command. If an agent authored the file from external scrapes, its taint remains `external_untrusted` or `internal_generated`. Operator import cannot elevate an unverified document to `user_ratified`.
> 4. **Unified Schema and Bidirectional Linking:** Summaries and atomic entries must share a canonical schema requiring metadata headers: `kind: summary`, `author`, `source_mission`, `taint`, and `summarizes: [claim_id, ...]`.
> 5. **Partitioned Search and Retrieval:** Bulk markdown summaries must not pollute atomic claim lookups. `kb_search` must flag summaries with fenced metadata (`<kb_summary taint="..." validated="false">`) or require an explicit flag (e.g., `--include-summaries`), preventing dense, unverified narrative prose from diluting or overriding verified atomic facts in agent context windows.
> 
> ### Risks
> - **Authority Laundering via Rubber-Stamping:** Operators will naturally treat convenient one-step import as an implicit seal of approval, exposing downstream agents to memory poisoning (AgentPoison/MemoryGraft).
> - **Taint Erasure:** A loose implementation could mistake operator invocation (`kb import`) as operator authorship, laundering low-trust web artifacts into high-tier memory.
> - **Context Flooding and Attention Hijacking:** Verbose markdown summaries will easily outrank succinct atomic facts in semantic embeddings, causing retrieval-augmented hallucination and lost-in-the-middle context degradation (`[H-002]`).
> - **Watched-Directory Injection:** If a background folder watcher is adopted, compromised sub-processes or build artifacts could stage adversarial context without operator awareness.

### strategist

> OPTION: One schema, two doors, labeled kinds
> 
> **Reasoning (scope and sequencing view):**
> 
> The host's four options are not alternatives. They are one design with one cheap core and optional extras. I'd sequence it so the first milestone is small and the rest earn their way in.
> 
> **Milestone 1 (ship now): shared schema plus operator import.**
> - One schema with `kind: atomic | summary`. Summary frontmatter has `sources: [entry ids or URLs]`, `retrieved`, `author`, and daemon-computed `taint`. Agents and operators cannot set taint.
> - `delphi kb import <file.md>` (and later a TUI drag-in that calls the same command). The operator's act counts as ratification of inclusion only. The page is stored with `status: included`, `validation: not validated`, and `ratified_by: operator`. It is searchable immediately and always shown with a visible `[summary · not claim-validated]` label.
> - Taint: an imported file gets `user_ratified` for inclusion provenance, but its claim-confidence stays at the computed content taint. The two must be separate fields (`inclusion` and `claim_status`). Otherwise "operator handed it over" quietly launders agent-written, web-derived claims into the highest trust tier. That is the main risk.
> 
> **Milestone 2: agent path.** `propose_kb_entry` accepts `kind: summary` into the same L0 inbox with the same per-entry ratification, caps and scrubbing. Summaries get a larger size cap but a stricter per-day count.
> 
> **Linking.** Summaries point to atomic ids through `sources`. Links are one-way and resolved at search time. A summary is flagged "stale" when a cited atomic entry is disproved or withdrawn. This is cheap and valuable.
> 
> **Search.** Summaries are included by default but ranked below validated atomic facts and shown with a label. `kb_search` can filter by kind. A summary never counts as evidence for `ratify_fact` and is never a promotion source for heuristics, REVIEW or skills (H-004 stays intact).
> 
> **Defer: the watched folder.** It is a second ingest surface, with its own scrubbing and dedupe edge cases, and it duplicates `kb import`. Drop it until operators say the one-step command is too much friction. Staging without ratifying is the safe version if it is ever added.
> 
> **Risks**
> - Trust laundering through operator import, as described above. Mitigate with separate fields and a label that can't be hidden.
> - Summaries become the retrieval default and crowd out atomic claims. Mitigate with ranking and the kind filter.
> - Stale summaries after atomic entries change. Mitigate with the stale flag.
> - Imported files can carry secrets, local paths or injected instructions. Scrubbing must run on the operator path too, and the content is treated as data.
> - Scope creep into a file-management system (folders, editing, versioning). Keep it as import, label, link and search.

## Verdict

**Escalated to the operator:** 1 unresolved P0 finding(s).

All seats (architect, red-team, strategist) recommend PROCEED-WITH-CHANGES; the open items below need your sign-off.

> The Council recommends one shared schema with two entry doors, and it cut the watched folder. Summaries (`kind: summary`) sit beside atomic claims and cite them through `summarizes` ids. Operators get `delphi kb import <file.md>`, with the TUI calling the same function. Agents get `propose_kb_entry` with `kind: summary`, which stays in the L0 inbox until ratified. Search returns summaries in a separate, labeled group, never as `<fact>` elements. Summaries are never evidence for `ratify_fact` and never a promotion source under H-004. Scrubbing, size caps and treating content as data apply to both doors. Stale or dangling links are flagged at search time.
> 
> All three seats agreed on:
> - The shared schema.
> - Dropping the watched folder. If it returns, it stages to L0 only and never ratifies.
> - Keeping inclusion separate from claim validity.
> - Running the same scrubbing on operator imports.
> 
> They did not agree on:
> - **Taint on import.** Architect wanted the import act to count as ratification of inclusion, held in a separate field. Red-Team holds an open P0 that import must not raise taint at all, and that taint is inherited from the sources. Strategist sits between them: separate `inclusion` and `claim_status` fields, with content taint left unchanged.
> - **Default search.** Red-Team wants summaries opt-in. Architect and Strategist want them included by default in a labeled group.
> - **Sequencing.** Strategist wants operator import first and the agent path second.
> 
> The operator must decide whether import records inclusion only, with content taint inherited, or whether it can set a higher tier.
