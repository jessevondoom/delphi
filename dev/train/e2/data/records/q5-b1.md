### red-team

> OPTION: Approve with amendments
> 
> ### Reasoning
> 
> Exempting artifacts (documents, decks, images, media) from formal specification unblocks operational velocity, but creates distinct attack surfaces—executable content smuggling, indirect prompt injection, and audit trail circumvention. Approval must be conditioned on four mandatory amendments:
> 
> 1. **Strict Content Hygiene on Exempt Formats:** The allowlist must not merely check file extensions; it must enforce static validation against active content. Any format supporting executable scripting (e.g., SVGs with `<script>` tags, HTML with active DOM scripting, documents with macros, or polyglots) must be rejected or stripped deterministically. Exempt artifacts must never execute within the host environment.
> 2. **D-1 (Log Location):** The verbatim prompt log must be stored in daemon-owned, append-only storage outside the workspace worktree (e.g., `.delphi/audit/artifact-prompt.log` or the daemon’s private run directory). Placing this log in a workspace-accessible path permits untrusted scripts or compromised subagents to truncate, tamper with, or forge the audit trail.
> 3. **D-2 (External Project Spec Location):** External project specs must reside centrally under Delphi's governed path (`specs/external/<project>/`), never inside the external project's target repository. Storing specs inside external checkouts allows untrusted external branches or PRs to silently modify specification constraints, bypassing Tier-2 verification and ratification invariants.
> 4. **D-3 (Log System Entries):** System-triggered and subagent-delegated operations must be logged explicitly with their origin span, taint rating, and causal chain. Logging exclusively literal human operator prompts creates a catastrophic blind spot: an indirect prompt injection originating from untrusted web or federated inputs could drive autonomous artifact generation without appearing in the audit log, masking adversarial exfiltration or payload staging.
> 
> ### Risks
> 
> - **Execution Smuggling:** Attackers exploit permissive MIME types or rich media formats to plant web/local exploits bypassing "No Spec, No Build."
> - **Audit Erasure & Spoofing:** Workspace-accessible logs allow malicious or hallucinating builders to scrub historical generation traces.
> - **Taint Concealment:** Omitting autonomous or system-prompted events permits untrusted inputs to generate poisoned artifacts under assumed operator authority.

> 
> 3. **The log must be deterministic.** The daemon writes it, agents cannot edit it, and it is append-only. It records operator prompts only, verbatim. Define what happens if the log write fails. I would fail closed for artifact edits, since an unlogged edit defeats the compensating control.
> 
> **D-1 (log location):** Put it in daemon-only local state, such as `local/`, alongside proposals. Do not put it in `missions/` or `context/`, which agents can read and write. Keep it per mission, outside Git, and subject to the secret-hygiene rule (§5.3), since verbatim prompts may contain secrets. Provide a redaction path that is operator-only.
> 
> **D-2 (external project spec location):** Keep `specs/external/<project>/`. §1.3 already says this, a single location is simpler, and the specs stay under the same ratification and review rules. Splitting them into the external repo would put them outside Delphi's trust controls.
> 
> **D-3 (log "(system)" entries):** Do not mix them into the operator-prompt log. The requirement is operator-prompt-only. If system-initiated edits need tracing, put them in a separate daemon event log. If the host wants them in the same file, mark them unambiguously as non-operator, and never as verbatim operator text. Prefer the separate log.
> 
> **Risks.**
> - Prompt-to-artifact attribution is weak. One operator prompt can drive many edits, so link each edit to the prompt that caused it. Otherwise the log is only decorative.
> - Logs of verbatim prompts can leak secrets or personal data.
> - Scope creep: a media allow-list that grows without review. Adding to it should be a Red-tier change.
> - Amending §1.3 is a constitutional change (§5.7). The operator must approve the diff, and the host's recommendation cannot stand in for that.
> - The spec needs an "Implements-Spec" carve-out. Define how a mixed task (code plus docs) is classified. It should be software as a whole.
