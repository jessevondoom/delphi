## Round 1 stances (blind)

### architect

> OPTION: Daemon-side capture into a KB inbox
> 
> **Reasoning.** The failure is that saving depends on someone choosing to do it. Options that rely on agent discipline or a new tool the agent must remember to call (the "no new tools" option, and partly the first two) will leak, because the agent decides what counts as worth staging. The fix is structural. The daemon should capture research outputs as a side effect of research happening, and agents should not have to propose anything.
> 
> My design is a hybrid, with the daemon doing the capturing:
> 
> 1. **Capture in the daemon.** When a research span finishes (the `request_research` path, or any task whose read tools touched internal sources), `delphi-core` writes a record to a KB inbox. It holds the findings, the source pointers, the span id, the role, the timestamp and the computed taint. Because the daemon writes it, the provenance is trustworthy. The agent cannot declare or raise taint (§4.3), so this fits the charter.
> 2. **Status.** Inbox entries are `not validated` and sit at the lowest tier the span's inputs allow. They are searchable through `kb_search` with that label, so they are usable as leads right away. They are never promoted to heuristics, lessons or skills without verification or ratification (H-004).
> 3. **Ratification.** The operator ratifies in batches, through the existing `/retro` and `validate_claims` flow. Trusted-source claims can go through `ratify_fact` for deterministic checking, so most entries are cleared without the operator reading each one. The TUI one-key batch ratify is a thin view over this inbox, not a separate capture path.
> 4. **MCP stays read-only for ratification.** An MCP caller such as a Claude Code agent can at most trigger a stage-only `propose_kb_entry`. That tool is an optional escape hatch for research done outside Delphi's own spans. It can never ratify and can never write above L0.
> 
> This keeps the MCP authority limits intact, gives full provenance, needs no operator action at capture time, and puts a gate only on promotion. It is also a Strategist-friendly scope: one inbox, one capture hook, and reuse of the existing ratification flow.
> 
> **Risks.**
> - Inbox flooding. Mitigate with dedup by source and claim hash, a size cap, and expiry of unreviewed entries.
> - Poisoning by indirect injection from internal sources. Mitigate with computed taint, no mutating tools for low-taint spans, and no promotion without verification.
> - Leaking sensitive internal material into a shared scope. Keep the inbox at workspace scope only, and scrub before any Xenia or team export.
> - Capturing by summary. Store the findings verbatim with pointers, not an agent's paraphrase, so errors don't become "accurate-looking" records.
> - The daemon cannot judge "what is research", so over-capture is likely. Prefer a coarse rule (a research span ended) and filter at review time.

### red-team

> OPTION: Dedicated MCP propose tool at L0
> 
> Staging external research into Delphi's central knowledge base must be governed by a dedicated, deterministic MCP tool (`propose_kb_entry`) that places entries strictly into an isolated L0 (`external_untrusted`) inbox. 
> 
> From a defensive and adversarial standpoint, the competing options fail critical security invariants:
> 
> 1. **Prompts are not security boundaries (Option 4):** Relying on agent descriptions or skills to stage findings violates Governance §5.6 (*Enforcement Is Code, Not Prose*). External host agents like Claude Code will drift, omit citations, hallucinate metadata, or bypass formatting constraints. Only a programmatic tool contract can enforce mandatory provenance schemas.
> 2. **Auto-capture and batch ratification (Option 3) invite poisoning via audit fatigue:** Automatic capture vacuums intermediate hallucinations and noise. Combining auto-capture with a "one-key batch ratify" mechanism is an anti-pattern: rubber-stamping fatigue guarantees that poisoned context (MemoryGraft, prompt injections from fetched external content) gets promoted to verified truth without scrutiny.
> 3. **Overloading existing tools (Option 2) breaks memory hygiene (§4):** `propose_note` and session summaries exist for role coaching, retrospective distillation, and execution telemetry. Overloading them with domain research muddles role-private lessons with shared factual context, degrading information flow control (IFC) and taint accounting.
> 
> A dedicated MCP staging tool ensures that the daemon deterministically tags incoming payloads with an immutable provenance frontmatter (host identity, source URLs, raw query, timestamp) and clamps the initial taint lattice to L0. Staged entries must remain sequestered from standard retrieval until validated.
> 
> ### Risks
> 1. **Review Fatigue and Rubber-Stamping:** Even with manual promotion, an unthrottled inbox will overwhelm the operator, eventually inducing blind approvals that circumvent the L0 quarantine.
> 2. **Inbox Flooding / DoS:** Compromised or looping external host agents could spam the staging inbox, consuming storage and burying legitimate research.
> 3. **Index Boundary Leakage:** If retrieval tools (`kb_search`) inadvertently index unvalidated L0 inbox files without strict status filtering, low-trust payloads will bleed into active reasoning contexts, triggering downstream taint downgrades.

### strategist

> OPTION: New staging tool, plus TUI batch ratify
> 
> **Scope view (Strategist):** The goal is that research always lands in the KB with minimal operator friction. That needs two things: an automatic capture path, and a ratification path that costs the operator almost nothing. Each option covers only part of that.
> 
> **Recommendation, in two phases:**
> 
> 1. **Phase 1: add a narrow `propose_kb_entry` MCP tool.** It writes only to a KB inbox at L0, and the inbox is not loaded into any prompt. Each entry carries a claim or summary, source URLs or paths, the retrieval date, the originating mission and host, and a daemon-computed taint. The agent cannot set taint or status. This is the smallest change that gives the host a structured, provenance-carrying route into the KB. It also fits existing authority: it stages, it never promotes, and it is no more privileged than the existing `ratify_fact` and `propose` patterns. Because it is a typed tool, the host can call it reliably and the schema can be checked.
> 
> 2. **Phase 2: TUI batch review.** Show the inbox as a queue with one-key accept, reject or defer per entry, and batch accept per mission. Entries marked "pending validation" remain searchable through `kb_search`, labelled "not validated". This matches the stated goal that most entries may stay pending. Do not build TUI auto-capture of raw output until Phase 1 proves out. Raw output has weak provenance and will flood the queue.
> 
> **Why not the others:**
> - **Extending `record_session_summary`/`propose_note`** mixes research artifacts with lessons. It blurs the schema, and it risks routing research into the rule-promotion path, which `[H-004]` guards.
> - **Instructions only** is prose enforcement (§5.6). It will be skipped under pressure, and "always" can't be guaranteed that way. Use it only as a supplement, to tell roles when to call the tool.
> 
> **Risks:**
> - **Inbox flooding:** the operator drowns in low-value entries. Mitigate with a per-mission cap, deduplication by source, and a batch reject.
> - **Poisoned content laundered through an agent:** a staged entry from an external page could later be ratified without scrutiny. Taint must stay at the lowest input tier and be shown in the review UI. Ratifying an entry should not by itself raise it to `user_ratified` without the operator seeing its sources.
> - **Scope creep:** a new tool needs an approved spec first (§1.3), and MCP read-only authority may need an explicit, ratified exception for inbox writes.
> - **Agents skipping the tool:** if only prose says "stage findings," some research will still go unsaved. Consider having the daemon nudge when a research session ends with nothing staged.
