### red-team

> OPTION: Pursue only 1, 2, 6 now
> 
> ### Reasoning
> From an adversarial and robustness standpoint, rushing all six actions without baseline evaluation infrastructure is premature optimization driven by external hype. Delphi must prioritize structural resilience and observability over unmeasured context tricks.
> 
> 1. **Action 1 (Spec 062 Tool Errors & Truncation Hints) is critical defensive hygiene.** Opaque tool errors and silent truncation induce infinite retry loops, model hallucination, and blind parameter guessing. Providing actionable error schemas and truncation boundaries directly mitigates agent thrashing and context pollution.
> 2. **Action 2 (Spec 039/033 Failure Logging) closes a major observability blind spot.** Logging structured failure kinds with hashed argument keys provides tamper-evident telemetry on agent dysfunction and repeat failures while strictly preserving secret hygiene (Charter §5.3). We cannot harden harness loops without deterministic failure attribution.
> 3. **Action 6 (Docs-Only Edits) carries zero blast radius** and formalizes assumptions across specs without consuming build cycles or introducing untested code.
> 
> Conversely, Actions 3, 4, and 5 must be deferred:
> - **Action 3 (KB Chunk Contextualization):** Running LLM-generated summaries over ingested chunks risks memory poisoning and hallucination injection into the knowledge base without validated retrieval gains, directly threatening taint hygiene (`[H-004]`).
> - **Action 4 (Tool Examples):** Adding few-shot examples into tool schemas permanently bloats context windows on every call and invites cross-family schema rejections (e.g., Gemini's strict array schema validation).
> - **Action 5 (Evaluation Ordering):** Measuring before specs 045, 048, and 049 provide actual baseline infrastructure creates brittle evaluations against non-existent harness code.
> 
> ### Risks
> 1. **Information Leakage via Actionable Errors:** In designing "actionable" tool errors under Action 1, there is a risk of leaking internal system paths, environment variables, or unredacted taint payloads across MCP boundary layers to untrusted callers.
> 2. **Cross-Family Schema Crashes:** Tool detail enums or modified error signatures risk triggering fatal `400` errors on heterogeneous seats (specifically Gemini's strict array item requirements and Claude reasoning signatures (`[H-003]`)).
> 3. **Telemetry Denial of Service:** High-frequency tool retry cascades under Action 2 could flood error logs or exhaust disk storage if rate-limiting and bucket caps are omitted.
> 4. **Benchmark Distraction:** Chasing external Anthropic blog metrics without ratified internal evals (048) risks misallocating token budgets to phantom problems while core harness loop deficiencies remain unaddressed.

## Verdict

**No deterministic escalation:** no unresolved P0 and the Round 2 recommendations agree. The decision is the operator's.

> The Council recommends option 2: build actions 1, 2 and 6 now, and defer the rest until the 045/048 baselines exist. The work is worth doing only at this size. All three seats chose it, and the Round 2 reviewers called for changes rather than rejecting it.
> 
> **Why:**
> - Action 2 comes first. It is the only way to measure whether any later action helps.
> - Action 1 follows. It is a small amendment to an existing spec and adds no new authority.
> - Action 6 is docs-only and can run in parallel. It should fold in action 5, the 048 measurement ordering, with scripted-CI evals first.
> - Action 3 waits for the 048 and 064 baselines. Action 4 is dropped until the logs show invalid_args concentrated in specific tools.
> 
> **Where the seats agreed:**
> - Define the failure-kind taxonomy once, in spec 039, and have 062 reference it.
> - Enforce "arg-key names and hashes only" in code, with a per-workspace salt and caps on log size and rate.
> - Cap error and hint text, and never leak paths, environment values or tainted payloads. Add golden-file tests on the wording.
> - Make the detail enum a plain two-value string enum, and give every array an items type.
> - Cite the Anthropic posts in 049 as host-verified and not validated, because anthropic.com is not a trusted source.
> - Limit the work to one amendment per spec and no new specs.
> - Add a stop condition that reopens the deferred items, such as an invalid_args rate that stays high or schema tokens above about 10k.
> 
> **Where they did not agree:** Architect concurred. Red-Team and Strategist did not, and their P1 findings stand as filed. The disagreement was over how strict the controls must be: Red-Team stressed the oracle risk from actionable errors and the taint risk from the 049 citations, and Strategist stressed the scope cap.

## Decision and next steps

**Decision:** Build actions 2, 1 and 6 now, with the stated controls, and defer actions 3, 4 and 5 until baselines exist.
