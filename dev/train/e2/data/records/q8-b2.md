> Conversely, Actions 3, 4, and 5 must be deferred:
> - **Action 3 (KB chunk contextualization):** Contextualizing chunks before spec 064 retrieval evals exist imposes ongoing LLM generation token overhead without an empirical retrieval baseline.
> - **Action 4 (Tool-manifest examples):** Static examples permanently inflate prompt token footprints across every span. Without schema-token thresholds, this trades baseline context efficiency for unmeasured marginal gains.
> - **Action 5 (048 measurement ordering):** Specifying evaluation order before spec 048 benchmarking is implemented in code produces procedural overhead without operational footing.
> 
> ### Risks & Failure Scenarios
> 1. **Adversarial Error-Feedback Injection (Action 1):**
>    - *Failure scenario:* If actionable tool error messages reflect untrusted external tool responses or dynamically suggest follow-up actions, a malicious MCP endpoint can exploit the error channel to execute prompt injections.
>    - *Remediation:* Restrict actionable hints to static, deterministic error templates and schema-defined format corrections; never reflect raw or untrusted payloads in remediation advice.
> 2. **Telemetry Leakage via Low-Entropy Hashing (Action 2):**
>    - *Failure scenario:* Saltless hashing of low-entropy arguments (boolean flags, enum values, short IDs) allows offline rainbow-table reconstruction of parameters.
>    - *Remediation:* Log parameter key names and validation error classes only, or salt hashes using an ephemeral session secret.
> 3. **Phantom Optimization Without Baselines (Actions 3–5):**
>    - *Failure scenario:* Deploying chunking or prompt adjustments without automated benchmarks produces undetected regressions in retrieval precision and token spend.
>    - *Remediation:* Maintain a hard dependency gate: Actions 3 through 5 remain blocked until spec 048 benchmark suites execute deterministically in CI.
