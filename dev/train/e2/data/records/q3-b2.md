## Round 1 stances (blind)

### architect

> OPTION: Daemon-side auto-staged KB inbox, batch ratify
> 
> **Reasoning (architect view):** The root problem is that saving depends on agent or operator discipline. Anything relying on an agent choosing to call a tool (options 1, 2, 4) fails silently, which is the current failure. So the capture must be a deterministic daemon behavior, not a prompt convention. §5.6 of the charter says the same thing: prose-only rules don't count as enforced.
> 
> Design:
> 1. **Capture in the daemon.** Whenever a research-class run completes, whether through the TUI or MCP, the daemon writes the output to `kb/inbox/<id>.md` itself. The entry holds the sources, the retrieval pointers and the producing role and task. Frontmatter is computed, not declared (H-004): `source_type` comes from the lowest-trust input in the span. Internal sources therefore give `internal_generated` at most, and any web input drops it lower. Status is `not validated`, at L0.
> 2. **MCP stays read-only in authority.** The daemon performs the staging as a side effect of the research call. The MCP caller gets no new write power and no ability to set trust. This respects the authority limits and avoids a new attack surface (an agent-callable propose tool is a poisoning channel, though a staged one).
> 3. **Ratification stays with the operator.** The TUI shows an inbox count, with a one-key "validate all via `validate_claims`/`ratify_fact`" batch and per-entry reject. Unreviewed entries remain searchable by `kb_search`, labeled `not validated`, so they are useful at once as leads and never as facts.
> 4. **Provenance.** Each entry records the mission, the task, the source URLs or paths, a content hash, and the originating client (e.g. host:claude-code). Entries are deduplicated by hash.
> 5. **Optional supplement.** Add `propose_kb_entry` later, so a host agent can add curated notes. It goes through the same inbox with the same computed taint.
> 
> This is the TUI auto-capture option (3), extended to MCP and made daemon-side. Option 4 can accompany it as guidance only.
> 
> **Risks:**
> - Inbox flooding and noise. Mitigate with dedup, a size cap, TTL expiry for entries never touched, and a minimum-sources filter.
> - Sensitive internal material landing in a shared KB. Keep the inbox workspace-scoped, never team-scoped, until it is ratified. Apply secret scrubbing (§5.3) on write.
> - Unvalidated entries being treated as fact. `kb_search` must keep labeling them clearly, and they must never be promotable into heuristics or lessons (H-004).
> - Batch ratify becoming rubber-stamping. Show a diff or summary per entry and keep the claim-level validator in the loop.
> - It needs a spec before any build (§1.3), and it touches the definition of what counts as a research-class run.

### red-team

> OPTION: Add dedicated L0 staging MCP tool
> 
> From an adversarial security standpoint, an explicit, deterministic staging tool (`propose_kb_entry`) is the only mechanism that preserves Information Flow Control (IFC) and defends against memory-poisoning vectors such as AgentPoison and MemoryGraft.
> 
> Relying on TUI auto-capture with "one-key batch ratify" creates an immediate rubber-stamping failure mode. Confronted with large diffs, operators under cognitive load will reflexively batch-approve, promoting untrusted external content into authoritative tiers without scrutiny. Auto-capture also indiscriminately vacuums up conversational noise, intermediate model hallucinations, and unverified scraping payloads.
> 
> Prompt-only instructions ("instruct roles to stage") directly violate Governance §5.6 ("Enforcement Is Code, Not Prose"). Under context decay, multi-turn drift, or external prompt injections, agents routinely ignore prose admonitions.
> 
> Overloading `record_session_summary` or `propose_note` breaches memory compartmentalization (§4.1). Conflating shared knowledge base entries with private episodic lessons or linear change logs corrupts schema boundaries and circumvents Rule of 25 pruning limits (§6.2).
> 
> A dedicated MCP staging tool enforces structural security invariants:
> 1. **Deterministic Schema Enforcement:** Mandates bounded fields (source URIs, query context, retrieval timestamps, raw text) before acceptance.
> 2. **Deterministic Taint Assignment:** The daemon stamps all entries at L0 (`external_untrusted`) based on context origin, preventing client hosts from claiming higher trust (`[H-004]`).
> 3. **Quarantine Isolation:** Staged proposals remain in an inbox partition completely isolated from live `kb_search` indexing and always-loaded prompts until deterministically verified or explicitly ratified.
> 
> ### Risks
> 
> 1. **Review Fatigue and Taint Escalation:** A growing backlog of staged entries will pressure operators into blind bulk-ratification, trivially elevating L0 untrusted data to `user_ratified` system truth.
> 2. **Inbox Flooding / DoS:** Unconstrained external agents running automated loops could flood the inbox with low-quality or adversarial submissions, exhausting daemon storage and operator review bandwidth without rate limits.
> 3. **Persistent Indirect Prompt Injection:** Raw external research may carry dormant injection payloads. If stored without sanitization and subsequently indexed or summarized, it risks hijacking downstream Delphi agents.
> 4. **Retrieval Leakage:** If search tools allow querying the unvalidated staging inbox without explicit L0 warnings, uncorroborated assertions will bleed into planning contexts as pseudo-facts.

### strategist

> OPTION: Staged KB inbox tool, plus TUI batch-ratify
> 
> **Reasoning.** The failure is a missing path, not missing instructions. Research already exists and is valuable, but nothing in the system turns it into a staged KB entry. Option 4 (instructions only) adds no capability. Agents would be told to stage findings, but no tool exists to do it. That is the weakest option and also the least enforceable. Option 2 (stretching record_session_summary / propose_note) overloads tools built for a different purpose. Session summaries are narrative and notes are lessons, so research artifacts with sources would blur two schemas and muddy provenance.
> 
> The best first deliverable is Option 1: a narrow `propose_kb_entry` tool. It takes a claim or finding, its sources (URLs or internal paths), and the mission or task id. The daemon computes taint and provenance itself and writes the entry to an L0 inbox with status "not validated". This fits the authority model:
> - MCP stays effectively read-only for trusted memory, because staging is not promotion.
> - Taint is computed, never declared. Internal sources get `internal_generated`, and anything from the web or federated input is stamped lower.
> - Nothing reaches heuristics, REVIEW or lessons without ratification (H-004).
> - Existing `validate_claims` / `ratify_fact` can then drain the inbox.
> 
> Then add a thin slice of Option 3 for friction: the TUI lists the inbox and offers one-key batch ratify or reject, with the sources and computed trust shown. I would not auto-capture everything. Capturing raw outputs floods the inbox and makes batch approval a rubber stamp. The agent-chosen, sourced staging in Option 1 keeps entries meaningful. Option 4 can follow as a cheap skill line telling roles to call the tool.
> 
> **Sequencing.** Phase 1 is the tool plus inbox schema. Phase 2 is the batch-review UI. Phase 3 is the skill nudge. Each phase gives standalone value. Phase 1 alone ends the manual external markdown copying.
> 
> **Risks.**
> - Inbox flooding makes review a rubber stamp. Mitigate with per-mission caps, dedupe and a required source field.
> - A staging tool could become a poisoning channel. Staged entries must stay quarantined, never loaded into prompts, and taint must be computed by the daemon.
> - Batch ratify of a mixed-trust batch could launder low-trust content. Show trust per entry and require separate confirmation for entries below `internal_empirical`.
> - Spec work is needed (No Spec, No Build), and scope creep into a full KB redesign is likely.
> - Agents may skip the tool, so a deterministic check at mission close (nonempty research and empty inbox raises a warning) may be needed.

## Verdict

**Escalated to the operator:** 1 unresolved P0 finding(s); the Round 2 recommendations conflict.

- [Option A] ALTERNATIVE: daemon-side auto-staged quarantine inbox, with optional propose_kb_entry feeding — architect
- [Option B] PROCEED-WITH-CHANGES — red-team
- [Option C] ALTERNATIVE: daemon-side capture of completed research runs into a deduped, workspace-scoped  — strategist

> The Council recommends closing the capture gap in code, but it split on how to do that, so the choice goes to the operator.
> 
> **Agreed.**
> - Option 4 (instructions only) adds no capability and §5.6 says prose is not enforcement, so it can only be a cheap follow-up.
> - Option 2 (stretching `record_session_summary` or `propose_note`) mixes research artifacts with narrative summaries and lessons, which breaks memory compartmentalization (§4.1).
> - Staged entries must be workspace-scoped, sit at L0 with daemon-computed taint (H-004), and never be promotable to heuristics, lessons or REVIEW.
> - Staging gives the MCP caller no new trust authority.
> - Duplicate hashes, per-mission caps, secret scrubbing and TTL expiry are needed.
> - Any build needs a spec first.
> - Batch ratification must not raise taint on its own. It should run through `validate_claims` or `ratify_fact`, with per-entry trust and sources shown.
> 
> **Not agreed.**
> - *Capture mechanism.* The Architect and Strategist want the daemon to capture completed research runs itself, because an agent-called tool fails silently when agents skip it. The Strategist would limit capture to runs that cite at least one source. The Red-Team wants an explicit, schema-validated `propose_kb_entry` tool, and holds that auto-capture pulls in injections and noise. That is the open P0.
> - *Search visibility.* The Architect and Strategist would let `kb_search` show staged entries labeled "not validated". The Red-Team would exclude the inbox from general search.
> - *Review UX.* The Red-Team wants claim-level review. The others accept a batch review, with a separate confirmation for entries below `internal_empirical`.

## Decision and next steps

**Decision:** needs the operator: Should staging be automatic daemon capture of sourced research runs, or an explicit agent-called `propose_kb_entry` tool, and should the inbox appear in default `kb_search`?


If **ALTERNATIVE: daemon-side auto-staged quarantine inbox, with optional propose_kb_entry feeding**:

1. `architect`: Draft a spec defining a research-class run, the inbox schema, computed taint, scrubbing, caps and dedup, with `propose_kb_entry` as an optional feeder.

3. `builder`: Implement daemon capture and the inbox once the spec is approved.

2. `red-team`: Review the spec for flooding and claim-level review adequacy.
3. `builder`: Implement the tool and the claim-level review view after approval.
4. `strategist`: Define the mission-close check, since agents may skip the tool.

1. `architect`: Spec phase 1 only: capture of completed research runs that cite at least one source, with a hash dedup, a size cap and a TTL, searchable only when labeled "not validated".
2. `red-team`: Test the spec for injection sanitization and for taint laundering through batch ratification.
3. `builder`: Implement phase 1 after approval, leaving out the review UI and the skill nudge.
